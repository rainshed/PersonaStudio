# Personal recommendation benchmark

The `evaluations/v1` HTTP API and “评测与反馈” page implement explicit accuracy feedback → immutable case revisions → frozen suites → user-started single-candidate or A/B evaluation. Model outputs never act as a judge: `scoring.mjs` compares a validated binary outcome with the label derived from the original decision and the user's explicit positive/negative feedback.

`cases.mjs` owns feedback transactions, idempotency, optimistic revisions, withdrawals, case deletion, suites and local JSON backup. `service.mjs` owns candidate configuration, previews, persistent runs and shared TaskRuntime admission. `repository.mjs` owns SQLite storage; the application migration registry applies it. `notifications.mjs` records actual queued/running transitions without notifying on imported history. `http.mjs` mounts the local management API. No Agent tool is added for rating papers or changing labels.

## Feedback, datasets and experiments

The page has two tabs: the live recommendation dataset and experiment records. Feedback is collected beside the recommendation decision while reading daily papers or single-paper analyses. Satisfied keeps the original binary decision; dissatisfied inverts it. Nonbinary decisions and other generated content have no feedback controls. Existing non-recommendation feedback remains stored as history but accepts no new writes.

Every explicit recommendation feedback enters the default dataset immediately. The dataset displays arXiv links and editable expected answers; removing a row withdraws feedback and a later explicit vote can add it back. Cases are deduplicated by base arXiv id, Persona identity and selected tag scope. The latest explicit answer wins across sources and paper versions, while different interest scopes retain separate cases. Existing recommendation feedback is collected on service initialization without invoking a model.

`GET /dataset` returns current cases and a virtual suite. `POST /dataset/snapshot` freezes the current samples in the selected tag scope immediately before saving or running an experiment. Automatic suites use immutable case revisions, so later answer edits do not change their denominators or labels. Withdrawal/deletion still stops pending execution; completed results retain their original answers. Legacy explicit suites retain their existing revision checks.

`experiments.mjs` supplies live host/model catalogs, validates independent model and reasoning selections, and saves revisioned experiment drafts. The editor shares `PromptTemplateEditor` with Settings and uses the actual language-specific task, shared and screening-rule composition consumed by the selected dataset. Overrides are validated against that composition and frozen into each candidate. Settings remain unchanged until an explicit application. Legacy connection/version API requests still work.

`applications.mjs` requires a completed local experiment, previews exact changes, checks for concurrent settings edits and applies the selected model to the task types included in the experiment (screening and/or single analysis), plus modified prompt versions. Model routing preserves unrelated task choices. Applying another backend explicitly previews that the app-wide analysis host will change; shared-prompt edits likewise identify their wider scope. Prior routing, backend and prompt versions are retained with the run for an explicit restore. Stale restore requests are rejected rather than overwriting newer settings. Failed multi-store applications attempt to restore model routing and backend and explicitly report incomplete rollback. Imported runs cannot apply configurations.

Drafts are included in the local JSON backup. Schema migration 10 adds their storage without changing existing samples or results.

## Current inputs and tag scopes

Every new evaluation uses `current-recommendation/v1`. `current-input.mjs` derives the task from the feedback source, even if it has no historical input snapshot: daily samples run the current screening agent, and single-analysis samples run the current single-analysis agent. Model routes and active prompts come from current settings, with candidate overrides applied only to the experiment. Current subscription preferences are used when that subscription still has the sample's tag scope; otherwise the sample's language and task preferences are retained.

Only the selected tag set and matching mode must agree. Tag order does not matter. `scope_key` selects one group in the dataset and snapshot API; mixed-scope experiments are rejected before model calls. Knowledge revisions, historical Persona connection identities, prior tool queries and original model or prompt configurations are not prerequisites. The current Persona connection is used. Users maintain their own expected labels when interests change.

On execution, each paper's metadata and current scoped knowledge context are prepared and saved inside the experiment. Both candidates share these current inputs; a later experiment prepares them anew. The agents can fetch full text and make new knowledge queries through normal production readers. Queries stay in the same tag scope and the knowledge revision opened for this experiment, without any requirement to replay historical queries. Full text is shared if fetched. Experiment readers do not write production reports, notes or recommendation decisions. Feedback reasons, expected labels, previous generated answers and subsequent discussions never enter prompts or tools.

The current input record is internal and omitted from ordinary report responses. Explicit backup includes it; permanent sample deletion removes its input and task plan from runs. Old snapshots remain optional historical records. Previously started legacy runs retain their recorded execution protocol when explicitly resumed, while all new runs use current inputs. Saving feedback, importing data, creating snapshots, editing options and previewing an experiment never calls a model.

## Execution and accounting

Preview freezes candidate prompt bodies plus dependencies and model settings for 30 minutes. Start consumes that preview id or a caller-supplied persistent `idempotency_key`; repeated identical requests return the same run. Changed requests conflict. A/B shares case revisions and inputs prepared for the current experiment. Different prompt/model changes are shown as separate candidate configurations and do not establish causal attribution.

Evaluation uses the shared TaskRuntime at background priority, one evaluation at a time. Hosts retain the shared model-capacity admission. Fallback is disabled. The configuration captured for the current experiment is used throughout; later settings edits take effect in the next experiment without blocking this one. Recommendation evaluation rejects hosts without tool support. Codex counts one App Server turn, which can contain multiple model/tool rounds; Harness counts model request attempts. Candidate `attempt_unit` makes this distinction explicit, so counts are not interchangeable across hosts. The hard host-execution cap defaults to 20 host-metered executions per autonomous case/candidate and 2 for legacy screening; the UI can lower or raise it. One case times out after 10 minutes; a run after one hour. Cancellation, feedback withdrawal and shutdown abort in-flight work. Budget pause and explicit resume preserve completed entries. Both call and token ceilings can be explicitly increased in the evaluation form before resuming. Unknown interrupted outcomes are never silently reissued; the user must create a new run to retry them.

Token budgets check observed host usage before the next host execution, so one Codex turn (possibly multiple model rounds) or one Harness model request can cross the threshold. If the host does not return token usage, a token-budget guarantee cannot be made; the call cap still applies. `token_usage_complete` exposes this. Costs are never estimated from invented prices: total cost stays null if any attempt lacks cost; `known_cost`, `unknown_cost_calls` and `cost_complete` expose partial accounting. Attempt ids deduplicate repeated host callbacks. Each candidate has separate aggregate usage and per-case attempts, durations, outcomes and errors.

Runs with no valid decisions are failed, mixed outcomes are partial, and only fully evaluated runs are completed. Historical completed runs with no valid decisions are displayed as failed too. The primary score is accuracy among valid decisions and displays no results when none are valid. Coverage remains visible alongside it. All metrics retain their recorded denominators: total pass rate, binary coverage and accuracy of valid binary decisions are shown together, with TP/TN/FP/FN and false-positive/negative rates. Missing input, abstention, invalid output, timeouts, cancellation and withdrawal remain visible and do not become false negatives or correct decisions. A/B pairs by case id plus benchmark revision and exposes improvements, regressions, both-pass and neither-pass cases.

## Backup and deletion

JSON exports contain scoped evidence and private feedback; keep them with other private application data. Model credentials are excluded. Imports are bounded to 50 MB, 10,000 cases/inputs, 50,000 revisions, 1,000 suites, 2,000 runs, 200,000 run items and 100,000 feedback events. Input hashes, label derivation, paper grouping, source versions, revision references, suite membership, candidate identities and run-item states are validated transactionally. Imported runs are historical/read-only and never queued. Existing subjects preserve their local state; imports cannot resurrect withdrawn/deleted cases, evidence owned only by deleted cases, or deleted run outputs. Case deletion removes benchmark source details and old feedback revisions while retaining a tombstone; still-referenced business history follows its separate lifecycle.

Tests use temporary SQLite databases and deterministic local fixture hosts only; no personal production data or paid model calls are used. Run `node --experimental-strip-types --test tests/evaluations.test.mjs tests/recommendation-dataset.test.mjs` from `web`.
