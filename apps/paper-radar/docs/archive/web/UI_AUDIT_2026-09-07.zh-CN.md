# Paper Radar UI 检查清单

检查日期：2026-09-07。范围：本机真实服务 `http://127.0.0.1:4317/` 的每日论文、订阅编辑、订阅管理、日期与历史切换，以及相关详情代码。

本轮是问题检查，没有修改功能实现。浏览器实测环境为 Codex 内嵌浏览器，视口约 708 × 776；没有将结果扩大解释为所有手机浏览器均已复现。手机 Safari / Chrome 与 Tailscale 地址仍应参加修复后的验收。

证据标记：**实测**表示通过页面操作观察到；**代码**表示实现中发现的问题或风险，尚未执行对应的完整浏览器场景。P1 应优先修复，P2 为随后处理的可用性问题。

## 用户提出的四个问题

### 1. “生成最新一批”的反馈与实际任务状态不一致（P1，实测 + 代码）

- 首次点击能够创建任务，说明本次环境中按钮并非完全没有绑定事件。
- 创建并取消本批任务后，再点“生成最新一批”，页面短暂出现新任务，然后回到既有的已取消任务。
- 顶部却继续显示“任务已保存，离开页面后仍会继续。”；实际任务仍为 `cancelled`，没有继续处理。
- 按钮的忙碌状态只覆盖创建请求，后台筛选仍在运行时，按钮会恢复为“生成最新一批”。

原因：创建响应与后续去重复用之间有状态差异。`generate()` 根据创建响应的 `reused` 设置一次提示；后台 `bindReport()` 随后可能复用已取消记录，提示没有随最终任务状态更新。

建议：点击即显示“正在检查最新公告”；随后明确区分新建任务、已有任务运行中、打开已完成日报、已有任务已取消。已取消的任务应明确显示“继续未完成部分”，不能承诺自动继续。无新批次时明确显示已有日报日期。

验收：首次生成、运行中重复点击、已完成重复点击、取消后重复点击均有准确反馈，提示、按钮和任务状态一致。

### 2. Subject 候选无法正常选择（P1，实测 + 代码）

- 编辑订阅使用原生 `input + datalist`。本次点击下拉箭头、键盘展开及输入前缀，都没有出现可用的候选列表。
- 分类接口实际返回 155 个分类；手动输入完整 `cond-mat.stat-mech` 后，页面能够显示 `Statistical Mechanics`。问题集中在选择交互，不是分类数据缺失。
- 新建与编辑共用同一表单，因此都受影响。
- 日报顶部的下拉框其实是“当前订阅”，不是 Subject 列表；目前只有一个订阅，因此只有一个选项。缺少可见标签，容易误认为分类不可选。

建议：改为项目自己的可搜索选择组件，支持代码和英文名称检索、明确的已选状态与无结果提示，只允许提交有效分类。顶部加“当前订阅”标签，并提供“修改分类”和“新建订阅”的清楚入口。

验收：内嵌浏览器和手机浏览器都能展开、搜索、选择并保存分类；回到页面后显示保存值。

### 3. 日期与当前日报没有保持同步（P1，实测 + 代码）

- 使用原生日期控件的键盘操作选择 2026-09-06，可以正确出现“该公告日期没有已保存的日报”。因此不能认定所有日期操作均失效。
- 接着点击历史中的 2026-09-07 日报，正文切到 9 月 7 日，但日期框仍显示 9 月 6 日。
- 日期切换请求期间，旧内容继续显示，没有明确的加载提示。
- 日期筛选只查询已保存日报，界面没有提前说明这一点，也没有突出哪些日期有记录。

原因：`chooseRun()` 只更新任务，不同步日期；查询时 `selectedRun` 又优先于日期。刷新后日期筛选也会丢失。

测试限制：自动化直接填充原生日期控件曾出现输入显示值与受控值不同步；改用原生键盘操作后能正常查询。这一自动化现象不能单独作为实际用户输入事件失效的证据，需在用户手机的原生日历操作中复验。

建议：区分“当前日报日期”和“历史日期筛选”，点击历史记录时同步两者。日期切换显示加载状态；提供有记录的日期列表及“返回最新”。空日期明确表示“最新”，不要让空框与正文日期形成歧义。

验收：选日期、打开历史、切订阅、返回最新、刷新之后，日期、正文、历史选中项始终一致。

### 4. 新增订阅入口难以发现（P1，可发现性，实测 + 代码）

- 功能已存在：侧栏有“新建订阅”，“我的订阅”页也有按钮；实际能够打开新建表单。
- 有一个订阅后，每日论文主界面只显示“编辑订阅”和“生成最新一批”。
- 当前窄窗口下侧栏默认折叠，新建入口被隐藏，用户很容易认为无法新增。

建议：每日论文顶部常驻“新建订阅”，订阅切换器也提供新增入口。保持桌面和手机的主要操作一致。

验收：已有一个或多个订阅时，不展开导航也能找到新建入口；新建成功后自动选中并显示新订阅。

## 建议修复顺序

1. 先修用户提出的四项，并一并修好加载、取消和空结果状态。
2. 同一轮处理详情串报告风险、全文分析错误展示及推荐就绪提示。
3. 再完善导航持久化、状态命名与元数据展示。

修复验收应以浏览器交互为主，不只检查 API 返回。至少覆盖内嵌浏览器与手机浏览器，并包含无日报、运行中、已完成、已取消、失败和多个订阅的情形。无需为了验收 UI 将整批论文全部送入模型；可以用隔离的测试数据覆盖状态。
