# 自动日报：实现与运行

更新日期：2026-09-08。实现依据为[自动日报开发设计](../design/PAPER_RADAR_AUTOMATIC_DAILY_DESIGN.zh-CN.md)。功能运行在本机 Node 服务内，沿用现有 SQLite 和 Tailscale 入口。

**定时先检查 arXiv 公告的实际内容。公告与上一次相同，只保存检查记录，不创建日报任务、不读取 Persona、不调用模型。**

## 开始使用

1. 在“模型设置”配置每日筛选模型，在订阅中选择 arXiv 分类和有效的 Persona 标签，并将订阅设为“可运行”。
2. 在“每日论文”或“我的订阅”的“自动日报”卡片展开“自动设置与检查历史”。
3. 设置每日检查时间、明确的 IANA 时区（例如 `Europe/Vienna`）和过去 24 小时调用上限，勾选“开启自动日报”后保存。

自动开关默认关闭，时间建议为 07:30，时区建议来自浏览器，自动上限初值取该订阅的单批上限。建议值只用于表单，保存后才生效。首次启用在下一次设定时间检查最新公告，不追溯缺失的历史日报。保存会验证配置和标签，不发送模型请求。

“立即检查”可以在自动开关关闭时使用，但订阅必须可运行。它执行同样的更新判断和额度检查；发现需要处理的新内容时可能调用模型。60 秒内重复点击复用检查记录，进行中的检查也会被复用。

界面分别显示最近检查、下次检查、最新完成日报的公告日期和过去 24 小时用量。检查历史与待处理更新各自分页；缓存来源显示实际抓取时间。打开页面、轮询或刷新不会发起检查或模型请求。

电脑需要开机、联网并保持唤醒。关闭网页不影响执行；睡眠期间不保证执行。服务恢复后只合并执行一次到期来源检查，不补跑每天错过的模型任务。

## 更新判断

`announcement-content-v1` 对分类集合、公告日期、论文 ID/版本、公告类型、标题、摘要、作者顺序、分类、许可与跨分类匹配计算独立内容指纹。论文顺序、XML 变化、feed 和 entry 的 `updated`、抓取时间、解析器版本、订阅名称、时间设置、模型设置及 Persona 修订不直接触发自动分析。

来源检查复用现有官方 ATOM 获取、限流、在途请求和 60 秒下载缓存。首次比较与以后比较均先要求所有订阅分类完整且公告日期一致。下载失败、日期不一致、来源不完整及旧日期回退分别保留原因，不显示为“暂无新公告”。空 feed 不能证明官方已发布空批次，因此保守记录为来源问题。

每个订阅的分类集合有独立比较基线；共享下载不会让另一个订阅漏跑。每次更新还有永久的去重记录，键为订阅、分类集合、日期和内容指纹。重复观察、来源修订回退、服务重启、取消或删除日报都不会重新准入已处理更新。

来源确有变化后，还要判断适用候选、已存在任务和额度：

- 首次检查已有兼容手动日报时直接关联；手动与定时竞争使用事务内同一套兼容判断。
- 仅删除候选或只改变未纳入的版本动态，不需要新分析。
- 新修订中的已完成论文复用兼容筛选缓存；此前未完成且内容未变的论文标为需要明确继续，不借新公告自动重试。
- 模型、标签、严格度或提示词变化本身不会重跑同一来源；使用已有“按当前订阅重新筛选本批”入口明确生成新版本。

比较基线、更新记录和日报准入在同一个 SQLite 事务内提交。保存失败会整体回滚并显示“任务保存失败，请重新检查”，不会把未成功入队的来源消耗掉。规范化规则升级时重建旧来源的比较指纹；无法重建则记录来源问题，阻止隐式重跑。

## 额度与恢复

自动初筛同时遵守订阅的单批请求上限和每订阅滚动 24 小时自动请求上限（1–2000）。每次实际平台尝试前，在同一事务内预留自动额度并增加单批计数。平台失败、内部重试、校验修订与备用模型都按实际尝试计数；缓存命中不计数。额度不足时在发送前拒绝，不能先调用后记账。

进程意外停止留下的未确认预留记为 `unknown`，继续占用原来 24 小时窗口，避免重复花费。删除日报不清除用量记录。此上限控制请求次数，不是 token 或货币费用上限；平台未提供的价格不作估算承诺。

发现更新时没有额度：只记待处理更新，不创建日报。已经入队后耗尽额度：保留所有候选、已完成结果和暂停原因。

提高额度、等待额度恢复、保存设置或下次来源检查都不会恢复旧任务。用户在“已发现更新待处理”点击“继续处理（调用模型）”，才会继续原任务或处理存档更新。任务仍受自动额度约束，已经完成的结果保留。原订阅范围改变时要求使用当前设置重新筛选，避免隐式扩大 Persona 范围。

关闭自动开关阻止新定时检查和准入；已提交日报仍可在日报页单独取消。取消保留结果，后续检查不自动复活任务。删除后的更新记录保留为 `dismissed`；重新生成要使用手动入口。

自动日报完成摘要初筛、介绍和推荐理由。详细报告与讨论由用户主动发起，沿用独立任务与计量；任何运行和页面操作都不推断反馈。

## 调度与持久化

`server/daily/scheduler/` 包含 `clock.mjs`、`source-check.mjs`、`repository.mjs`、`service.mjs` 和 `http.mjs`。设置校验在服务中，分页和请求标识复用每日推荐的 contracts。

本机调度扫描间隔为 30 秒。无更新、来源失败、不完整或返回旧日期时，在最多 2 小时窗口内每 30 分钟重查，最多 4 次。补查只重新检查来源，不能恢复旧模型任务。错过多个日期时不形成补跑队列。

IANA 时区转换独立于服务器系统时区。夏令时跳过的时间顺延至当天首个有效时刻；重复时间仅使用第一次。更改时间、时区或开关增加设置 revision，过期检查不能准入；已入队的日报使用固定快照。

SQLite v5 只新增以下表及其索引：

| 表 | 用途 |
| --- | --- |
| `daily_schedules` | 订阅自动设置、revision、下次执行时间 |
| `schedule_checks` | 检查状态、实际来源、日期、结果和关联日报 |
| `schedule_requests` | 立即检查、到期检查和明确处理的幂等键 |
| `schedule_source_cursors` | 每订阅分类集合的完整比较基线 |
| `schedule_updates` | 已发现更新、准入、阻塞及删除后的去重记录 |
| `automatic_attempt_reservations` | 每次自动平台尝试的额度预留 |

既有来源修订和筛选缓存继续使用。检查历史和去重数据暂不自动清理，避免清理导致重复处理；长期保留策略后续独立实现。来源仍采用完整获取后的内容比较，尚未增加条件 GET。

重启时，排队检查可继续，检查中的记录转为中断并安排来源重查；已经准入但未开始的日报继续队列。运行中断的日报不自动重试，保留明确继续入口。复用现有进程锁，不启动第二个持库服务。

## API

接口沿用同源、JSON 和 `X-Paper-Radar: 1` 校验；POST 需要 `Idempotency-Key`。设置修改需 `expected_revision`，冲突返回 409。没有新增无保护的定时触发接口。

| 接口 | 返回或操作 |
| --- | --- |
| `GET /api/subscriptions/:id/schedule` | 设置、有效启用状态、滚动用量、最近检查、最新完成日报 |
| `PATCH /api/subscriptions/:id/schedule` | 保存自动设置，不运行模型 |
| `POST /api/subscriptions/:id/schedule/check` | 创建或复用检查，202 |
| `GET /api/subscriptions/:id/schedule/checks` | 检查历史；`limit` 1–100、`offset` |
| `GET /api/schedule-checks/:id` | 单次检查、来源覆盖、实际抓取时间及关联任务 |
| `GET /api/subscriptions/:id/schedule/updates` | 更新记录分页；`needs_action=1` 在分页前筛选待处理更新 |
| `POST /api/schedule-updates/:id/process` | 明确处理或继续指定更新，202 |

`/api/capabilities` 的 `daily_scheduler: true` 表示该进程已加载模块，不代表任何订阅已经开启自动运行。公开响应不包含私有订阅快照或模型凭据。
