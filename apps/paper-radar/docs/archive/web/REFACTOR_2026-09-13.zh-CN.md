# PaperRadar 0.2：重构说明与验收

本次沿用既有数据与功能，通过兼容入口逐步整理模块边界。没有把自主 Agent 改回固定的阅读、总结、复核流水线。

## 目标与实现

| 目标 | 实现位置与行为 |
| --- | --- |
| 统一任务管理 | `server/tasks/` 管理持久任务的调度、优先级上下文、并发准入、关闭和异常隔离；分析、讨论、日报、回测注册到同一执行器。`recovery.mjs` 集中定义恢复规则。 |
| 宿主与业务分离 | 通用工具和 Agent 执行规则位于 `server/agents/`；`server/hosts/` 选择宿主；`dsh/`、`codex/` 只实现接入。`@paper-radar/host-contract` 提供有版本的共享协议，不再跨目录引用插件的内部源码。 |
| 共享数据规则 | `lib/contracts/` 同时为前后端提供输入、订阅、任务状态、报告组件状态和推荐判断规则。业务数据库位于 `server/storage/`，迁移按明确版本顺序执行。 |
| 前端分层 | 主入口只判断运行模式；真实与演示页面共用导航外壳和证据展示，订阅与模型编辑器拆为独立组件。统一的请求轮询管理取消、重试、对象切换与失效响应。 |
| 反馈评测闭环 | 明确的推荐准确性反馈关联冻结输入和标签修订；可冻结测试集、预览预算并主动运行单版本或 A/B 回测，查看逐例结果与确定性评分。 |
| 证据更容易核对 | 阅读器展示摘要、正文、图注、表格或公式文字的实际来源，并显示已记录的章节、页码、行号或字符位置；不将图注文字称为图像理解。 |
| 可复现交付与验证 | 组件版本清单、锁定依赖、统一检查入口和可独立安装的源码发布包；保留两个 Git 历史，通过发布清单记录各自版本与校验值。 |

## 任务和模型名额

任务执行与模型请求采用不同的限制：

- 每个宿主有独立的分析与讨论任务通道，通道随并行设置调整。这样长报告不会阻止新讨论进入模型等待队列。
- 所有通道、每日初筛工具和评测共用该宿主的执行名额。通道增加不代表允许绕过宿主并行上限。
- 名额单位取决于宿主：Codex 为整轮 Agent 执行，DSH 为单次模型尝试，独立模型为包含重试的生成请求。Codex 内部的模型调用不对外提供逐次准入控制，因此不能保证新讨论在正在执行的 Agent 内部两次调用之间插入。
- 默认优先级为讨论 30、手动分析 20、手动日报 10、自动日报与评测 0。等待时间增加会逐步提升优先级，避免后台任务一直得不到资源。
- 已启动请求不会因更高优先级任务到达或调低并发而被取消。同一讨论顺序保持不变；不同讨论可以并行。
- 日报协调器最多同时处理两个不同订阅，同一订阅串行。每篇初筛仍遵守宿主名额、既有自动预算与结果复用规则。
- 取消后不发布迟到结果；重启保留排队任务，将失去执行进程的在途任务标记为中断。明确重试会利用已保存内容，不声称恢复原宿主会话。
- 某项任务或队列的异常被隔离并记录，不会造成无限自动重试或阻断健康队列。

只读接口 `GET /api/tasks` 返回各通道的运行、排队和异常摘要，遵循现有来源保护，不包含模型设置、提示词或证据正文。`GET /api/capabilities` 分别给出 API 版本与应用版本，并声明任务运行和反馈评测能力。

独立模型接入也使用同一优先级准入机制。排队前冻结模型设置；凭据或连接版本变化时仍按原有规则拒绝复用新凭据执行旧任务。

回测报告分别标注宿主的计量单位：Codex 计整轮 Agent，DSH 和独立模型计模型尝试。不同单位的次数不能直接比较。Token 与费用仅在宿主提供数据时累计，未知值明确标记；预算阈值在宿主回报检查点检查，不能作为 Codex 内部每一次模型调用的硬性预算控制。

## 数据与兼容性

数据库版本为 9。打开旧版数据库时，先使用 SQLite 一致性备份保存含 WAL 内容的旧状态，位置为业务目录下 `backups/before-v9-*.sqlite`，权限为 0600，再执行迁移。版本高于当前应用的数据库会拒绝打开，不降级覆盖。

第 9 版的迁移账本与版本号在同一事务中提交；旧迁移的执行时间记为未知。账本写入失败会回滚该次迁移，修复后可以重新启动。

原有论文、订阅、结果、讨论、显式反馈和幂等请求标识保留。`server/analyses/database.mjs` 保留兼容导出，实际实现为 `server/storage/database.mjs` 的 `RadarDatabase`。旧 `dsh` 通用工具入口同样保留轻量重导出。

任务是否完成、是否推荐、某个报告栏目是否可用分别表达。部分完成可以有有效总结；错误和证据不足不自动变成“不推荐”。历史结果缺少新字段时保持原有语义，不补造曾经没有取得的证据或模型设置。

反馈回测输入不依赖工作台最近 30 条捕获记录。撤销或修改反馈会使旧测试集相应成员失效；回放不会查询最新 Persona，也不会从网络补入原始运行未保存的论文正文。原批次删除后，已收录的样例仍有独立快照。

## 使用与验证

安装和发布见 [宿主边界与交付](HOST_BOUNDARIES_AND_DELIVERY.zh-CN.md)。反馈回测的操作和范围见 [评测模块说明](../../../web/server/evaluations/README.md) 及“评测与改进”页面；前端结构与界面验收见 [前端生命周期说明](frontend-lifecycle.md)。

在 Web 项目执行 `npm run check`，依次检查类型、代码规范及全部自动化测试；`npm run build` 构建前端。插件独立运行 `npm test`。测试有明确超时，失效宿主不会令测试无限挂起。

测试覆盖任务公平性与并发、排队取消/删除、关闭竞态、连接设置冻结、宿主退出、历史迁移备份、反馈修订、隔离回放、预算暂停、撤销、备份恢复和证据定位。浏览器验收使用临时数据库与模拟模型，真实模型调用及用户现有业务数据不参与自动验收。

回测的自动分数针对推荐判断；它不会自动认证论文解释的科学正确性。论文内容仍通过可核对的来源、明确反馈和具体案例来评估。
