## 当前实现说明（2026-09-13）

首版已经接入明确准确性反馈、修订与撤销、不可变回放输入、固定测试集、单候选和 A/B 回测、确定性评分、逐例报告、预算与取消恢复、本机备份恢复和完成通知。入口为“评测与改进”，实现接口为 `/api/evaluations/v1`；详情见 [实现与验证说明](../../../web/server/evaluations/README.md)。

本文最初以摘要初筛为目标。当前产品已经使用自主初筛，所以实现同时保存旧摘要初筛和自主初筛的输入，两个协议分别建立测试集。自主回放只能读取原始冻结的 Persona 与已取得的论文材料；原始运行没有保存全文而候选需要补读时，结果明确标记“输入不可用”，不会联网补齐或当成有效对照。回放与生产共用执行与引用校验协议；没有模型裁判或隐式偏好学习。

预算统计以宿主计量单位为准：Codex 按任务轮次计量，DSH 按模型请求计量，不能把两者的次数直接当成相同的供应商调用数。Token 阈值在宿主报告后检查，可能跨过一个执行单位；缺失用量和费用会明确显示，费用只汇总宿主实际返回的部分。已中断且调用结果未知的条目不会在恢复时自动重发。

固定清单遵守当前反馈撤销与修订，个人样例不代表全部论文的总体准确率。初始历史输入不足的样例仍保存反馈，但不伪造可回放状态。备份恢复验证引用、标签推导、论文分组和固定分母，导入运行只作历史展示。详细 API、限制、计量语义和隔离测试见上述实现说明；本文件其余章节保留原设计依据。

## 1. 目标与决策依据

Paper Radar 已经能够保存用户对推荐准确性、研究总结、推荐理由、联系与潜在交叉的四项独立反馈。首版评测只使用第一项：用户认为这一次推荐或不推荐的判断是否准确。

该任务有明确的二元期望答案，不需要判断两段文字是否语义等价，也不需要让另一个模型评判推荐理由。因此可以先形成完整闭环：

```mermaid
flowchart LR
    A[初筛结果与原输入] --> B[用户评价准确或不准确]
    B --> C[冻结样例并推导期望判断]
    C --> D[固定版本的测试集]
    D --> E[候选提示词或模型重跑初筛]
    E --> F[代码比较二元判断]
    F --> G[查看改善与退步案例]
    G --> H[在工作台修改并试验下一版本]
```

### 1.1 已确认方向与本设计的实施建议

| 类型 | 内容 |
| --- | --- |
| 已确认方向 | 借鉴 AI Persona，通过用户反馈建立自己的测试集，检验推荐质量 |
| 已确认方向 | 优先实现推荐准确性的二元评测，不增加额外模型裁判 |
| 沿用现有需求 | 四项反馈独立、可选；理由可选；未评价不等于负反馈；阅读行为不产生评价 |
| 本设计建议 | 最小首版先接入每日摘要初筛 `paper-radar.screen`，全文判断后续独立接入 |
| 本设计建议 | 首次明确评价自动建立样例；保存反馈不调用模型；回测由用户主动启动 |
| 本设计建议 | 优先复用现有 SQLite、模型连接和 Prompt Workbench，不新建独立服务 |

首版对象选择是为了控制实施规模，不表示全文推荐判断不能使用相同方法。后续可以为全文判断增加独立适配器，仍采用二元评分，但必须使用它自己的输入和结果版本。

### 1.2 本次范围

首版包含：

1. 推荐与未推荐结果上的准确性反馈、修改和撤销。
2. 自动推导标签，保存可重放的初筛输入和用户看到的结果。
3. 个人样例管理、冻结测试集、备份与恢复。
4. 单版本批量回测，以及同一测试集的 A/B 比较。
5. 确定性评分、覆盖率、失败分类、逐例对照和用量报告。
6. 与 Prompt Workbench 的提示词改进入口衔接。

首版不包含总结、理由或交叉内容的语义评分；不训练模型，不自动改写或启用线上提示词，不根据反馈自动改变订阅严格度或 Persona，不评测论文来源发现、检索召回和每日排序。点击“准确”只确认推荐判断，不确认整份报告的科学事实与文字质量。

## 2. 评价对象与标签规则

### 2.1 明确评价的是哪一次判断

一个评价对象是：

> 在当时的论文摘要、Persona 标签范围、个人资料和推荐严格度下，这一版本的初筛推荐判断是否准确。

不是“这篇论文永远是否值得推荐”，也不是“用户是否喜欢这段推荐理由”。同一篇论文在不同订阅、标签范围、时间或严格度下，可以有不同的合理判断。

日报卡片保留原有按钮：

- 推荐：`这次推荐的判断准确吗？` → `准确 / 不准确`。
- 不推荐：`这次不推荐的判断准确吗？` → `准确 / 不准确`。
- `needs_fulltext`：显示“需要全文确认”，没有可用于本测试集的二元判断；不开放该版本的准确性反馈按钮。
- 未执行、失败、取消、无有效结果：不展示可提交的准确性反馈。

用户不评价时不建立样例，不从展开报告、讨论、停留时间或未点击推导任何标签。推荐与未推荐区域都保留反馈入口，未推荐列表可以折叠，但不能隐藏到无法评价。

### 2.2 唯一标签公式

| 系统原判断 | 用户评价 | 期望判断 |
| --- | --- | --- |
| `recommended` | `positive`，准确 | `recommended` |
| `recommended` | `negative`，不准确 | `not_recommended` |
| `not_recommended` | `positive`，准确 | `not_recommended` |
| `not_recommended` | `negative`，不准确 | `recommended` |

```text
actual = 原结果 outcome == recommended
expected = actual                  当反馈为 positive
expected = not actual              当反馈为 negative
```

公式仅在原结果属于上述两个合法值时成立。不得将 `needs_fulltext`、`undetermined`、缺失值或错误状态强制转换为 false。

原判断由服务端从指定的不可变初筛版本取得，客户端不能提交或覆盖 `actual`、`expected`。修改评价时始终从原判断重新计算，不能反转上一次已推导的标签。

### 2.3 理由与其他反馈的边界

不准确理由只用于查看和改进提示词，不改变标签，不加入回测输入，不进入评分、缓存键或自动样例筛选规则。修改或清空理由，在输入、被测版本和输出相同的情况下，必须得到相同分数。

研究总结、推荐理由、联系与潜在交叉的反馈继续正常保存，但不为本测试集生成标签。例如“推荐准确、理由不满意”仍得到“应推荐”。

不根据讨论中的纠正或全文分析结果，自动修改旧初筛反馈；用户主动修改原反馈才产生新的标签修订。

下表描述设计时的代码状态，不表示新增评测能力已经存在。

| 现有位置 | 已有基础 | 需要增加或调整 |

| `web/server/daily/repository.mjs` | `daily_item_versions` 与 `daily_feedback` | 反馈修订、样例及运行持久化；删除历史时保护已收录输入 |
| `web/server/daily/list-decisions.mjs` | 日报列表归属由初筛决定；全文判断单独保存 | 沿用现有分离，不能以全文判断覆盖初筛测试对象 |
| `web/server/analyses/persona.mjs` | `screeningSnapshot()` 保存范围内元数据、证据及覆盖状态 | 回测读取冻结内容，不重新查询实时 Persona |
| `web/server/prompts/store.mjs`、`http.mjs` | 提示词版本、依赖展开、阶段输入捕获、单阶段实验和模型调用 | 复用模板和模型能力；增加批量测试运行，不依赖临时捕获记录 |
| `web/components/radar/daily-real.tsx`、`daily-details.tsx` | 日报与详情中的反馈入口、保存状态 | 显示准确的反馈目标、样例状态、修订冲突和保存结果 |

需要特别处理以下差异：

1. 工作台的业务 `captures` 只保留最近 30 条，不能作为个人测试集唯一的数据来源。
2. 初筛版本保存的展示证据是模型引用的子集；回测必须保存模型实际可见的完整初筛 Persona 输入，不能仅使用最后引用的几条证据。
3. 当前初筛反馈后端仅检查维度和值，需补充原 outcome 是否二元的服务端校验；不能只依赖前端隐藏按钮。
4. `getVersion()` 对关联详细分析的版本会使用 analysis 反馈。样例服务必须核验版本 `kind === screening`，不能把分析反馈重定向后误收为初筛样例。
5. 现有工作台 A/B 实验适合单阶段试跑，但不等于已经具备固定测试集、批量评分和持久反馈修订。

## 4. 输入冻结与样例建立

### 4.1 首次反馈的保存流程

1. 用户对一个已展示的初筛版本点击“准确”或“不准确”。
2. 服务端核验版本归属、原判断、反馈修订和幂等键。
3. 取得该版本对应的冻结输入，按公式推导期望判断。
4. 在同一事务中保存反馈、样例修订及输入的长期引用。
5. 事务成功后返回“已保存为测试样例”；不调用 LLM，不自动开始回测。

没有必要再增加一个“加入测试集”按钮。首次使用时以简短说明告知：准确性反馈会保存为个人测试样例，撤销后不再用于后续回测。

如果历史结果的原判断可核验、但输入不完整，仍可保存明确反馈和标签，样例标记 `input_missing`；返回“反馈已保存，缺少回放输入”，不能显示为可回放。缺少原判断或无法确认评价对象时，拒绝产生二元标签。

### 4.2 必须保存的内容

| 内容 | 冻结要求 |
| --- | --- |
| 论文 | 基础 arXiv ID、明确版本、标题、摘要、类别、原始证据 ID，以及模型实际收到的 paper 对象 |
| 订阅条件 | 当时的 subject 范围、标签及匹配规则、语言、推荐严格度；保留订阅 ID 和 revision 作追踪 |
| Persona | identity、revision、scope、完整初筛 records 和 evidence、覆盖状态；不是只保存版本号或对象 ID |
| 阶段参数 | `paper-radar.screen` 的原始变量、输出协议及版本；首次生成的 `issues` 为空 |
| 提示词 | 原版本正文、共用规则依赖及展开结果；不只保存未来可能失效的版本引用 |
| 原结果 | 用户当时看到的初筛输出、outcome、结果版本、原始调用及修正记录的归属 |
| 原运行信息 | 实际模型标识、可取得的采样参数、时间、流程版本、缓存来源及内容 hash；不复制凭据 |

初筛只使用摘要和 Persona 元数据，首版不会为了建立测试样例额外下载全文或读取范围外个人材料。记录论文 URL 只用于溯源，回测不能用该 URL 获取最新内容代替快照。

### 4.3 在业务执行时记录，在反馈时长期保留

新增独立于工作台 `captures` 的初筛输入快照。业务准备第一次模型请求时建立快照，最终 `daily_item_versions` 保存 `input_snapshot_id`；同一流程的修正请求保存其本次错误信息与调用关联。

快照以内容 hash 去重，位于现有 `radar.sqlite`，不属于可随模型缓存清理的记录。没有反馈的快照按普通业务历史生命周期保存；存在活跃业务引用或个人样例引用时不能清理。反馈建立后，即使原日报删除，也能用样例自身引用恢复输入。

命中生产缓存时，新的结果版本必须关联与实际缓存结果匹配的输入快照，并保留来源，不能使用同名但内容不同的最新输入。多个页面引用同一初筛版本只产生一个样例。

### 4.4 回放输入与结果材料分离

存储中可以同时拥有输入、原结果、反馈和理由，但回放器只接受白名单投影：

```text
生成输入 = 冻结论文 + 冻结 Persona + 冻结任务条件 + 本次候选提示词
评分输入 = 期望判断 + 本次流程状态 + 本次经校验的 outcome
改进参考 = 原输出 + 用户反馈理由 + 历史报告
```

原输出、期望判断、满意度、理由、反馈后的讨论和新 Persona 信息，均不得拼入生成输入。

不能将历史最后一次修正调用直接当成新的首次输入。新版本从空 `issues` 开始，只允许看到本次新输出产生的结构或引用错误。

## 5. 标识、修订与数据生命周期

### 5.1 标识与唯一性

| 标识 | 含义 |
| --- | --- |
| `subject_key` | `daily_screening:{screening_version_id}:accuracy`；服务端唯一确定评价对象 |
| `case_id` | 首次有效反馈创建的稳定样例 ID，同一 subject 不重复建样例 |
| `input_snapshot_id` | 包含全部回放输入的不可变快照 |
| `feedback_revision` | 评价、理由或撤销变化的历史修订 |
| `benchmark_revision` | 期望判断或经核验的回放输入发生变化时产生的样例修订 |
| `group_id` | 以基础 arXiv ID 分组，跨论文版本、订阅和重筛版本保持同组 |
| `suite_id + version` | 固定 case ID、benchmark revision 和输入 hash 的测试集清单 |
| `eval_run_id` | 一次固定测试集、候选配置和执行协议的运行 |

同一论文的不同初筛版本可以各有反馈，但不是彼此独立的新论文。报告同时显示样例数和独立论文数；开发集与留出集按 `group_id` 切分，不能把同一论文的不同版本拆到两边。

### 5.2 修改与撤销

- 从“准确”改为“不准确”，或反向修改：更新反馈修订，从原判断计算新的标签，并新增 benchmark 修订。
- 仅修改理由：只增加反馈修订，不改变 benchmark 修订、回放输入 hash 或评分规则。
- 撤销：保留可追溯状态，但样例退出后续回测；再次明确评价可恢复，同一 subject 沿用原 case ID。
- 重新生成或重新筛选：产生新结果版本，原反馈和标签留在旧版本；不自动迁移到新结果。
- 原订阅或 Persona 修改：不改写旧样例。对新条件的判断应通过新的业务结果收集反馈。
- 补齐可核验的历史原输入：产生新的 benchmark 修订；不能使用当前 Persona 猜测缺失内容。

撤销不等于删除。删除个人样例时，撤销其评测资格并清理只由该样例引用的评测内容；原业务结果按业务历史自己的删除规则处理。报告可保留不含正文的执行元数据和统计，已清理的明细显示“已删除”，不能承诺仍可重放。

删除原日报默认保留已收录的个人样例，并在删除界面说明这一点；不能因外键级联而静默丢失用户测试集。

### 5.3 事务与并发

首次保存、标签更新和撤销使用现有数据库的同一事务。现有反馈接口与评测页的操作必须调用同一个领域服务，不能各自修改一份不一致的数据。

请求携带幂等键与 `expected_feedback_revision`。重复相同请求返回同一结果，不重复创建样例或修订；过期页面返回冲突并保留未保存文本，不能覆盖后来的反馈。相同幂等键对应不同内容时返回冲突。

前端可以立即显示选中状态，但“已保存”及“已加入测试样例”必须等待服务端确认。数据库或快照保存失败时，反馈与样例写入一起回滚；`input_missing` 是已确认的历史数据缺口，不得用于掩盖新写入失败。

### 5.4 历史数据

新增记录从接入后的首次反馈开始自动收录。首版提供一次性“整理已有准确性反馈”的本机操作，不在升级或打开页面时自动批量调用模型。

只处理可核验的既有明确反馈：必须能确认初筛版本、二元 outcome 及评价值。可从原日报持久记录准确恢复完整输入时收为可回放；输入不全则收为 `input_missing`；目标含糊、非二元判断或详细报告评价列为不适用。

整理过程不推断从未提交过的反馈，不伪造旧修订历史，不覆盖后来撤销的记录；按 subject 幂等执行。浏览器 Demo、合成 fixture 和工作台实验不自动转为真实个人样例。

## 6. 回测执行协议

### 6.1 固定阶段回放

首版只提供 `daily_screening` 模式：使用原摘要、原 Persona 快照与原条件，重跑初筛阶段。测试的是这些输入已经准备好之后的推荐判断，不代表来源发现、Persona 检索或整个推荐系统的端到端质量。

实现时从现有 `DailyService.screen()` 提取可复用的初筛执行逻辑，将“构造请求、模型调用、结构与引用校验、有限修正”与“生产任务、日报版本、额度预约和业务缓存写入”分开。生产和评测使用同一初筛逻辑，注入各自的输入与记录端口。

初始协议沿用当前初筛的最多两次生成：一次正常生成，结构或引用不合格时最多修正一次。修正所用错误只能来自本次运行，不包含人工理由或期望标签。该修正属于被测初筛流程，不是增加一个模型裁判。

不会额外执行总结、全文分析、语义审阅或讨论。`needs_fulltext` 是允许的业务输出，但在二元回测中记为“未给出二元判断”，不自动读取全文、不重新强迫模型选一项。

### 6.2 候选与版本固定

支持一次选择一个版本，或 A/B 两个版本：

- 比较提示词：使用同一模型、采样设置、冻结输入、输出协议和流程版本。
- 比较模型：使用同一提示词、冻结输入、输出协议和流程版本，明确展示各模型实际支持的参数。
- 同时改变模型和提示词时标为“组合方案比较”，不把改善归因于某一项。

提示词连同共用规则一起冻结。候选引用不存在、变量不兼容或依赖不完整时，在执行前报错，不能静默替换成当前启用版本。

新候选仍按原案例严格度与范围执行。故意把原案例改成新严格度属于新任务，不能继续用旧标签宣称提高准确率。

运行保存实际 provider、model、已知模型版本、参数、提示词展开内容、输入 hash、输出协议、初筛流程及评分规则版本。供应商未返回的信息标记未知，不承诺不同时间的模型调用逐字一致。

### 6.3 测试集与开始前检查

冻结测试集时保存精确的样例修订；清单名称相同不代表测试内容相同。测试集可以标为“开发”“留出”或“未区分”；小样本默认允许未区分，但报告不能声称是独立留出测试。

开始前展示样例数、独立论文数、正负标签分布、缺失输入数量、A/B 配置、最大调用次数和预计用量。点击“开始回测”才发起请求，预览和保存测试集不调用模型。

若当前反馈已经撤销、删除，或 benchmark 修订与测试集不同，开始前返回需要更新清单的提示。旧清单不自动替换样例，也不允许用它绕过撤销。仅修改理由不导致清单失效。

### 6.4 隔离、预算与恢复

- 使用 Paper Radar 原有模型连接；默认关闭备用模型，避免结果混入未选模型。当前连接变更时停止受影响调用，要求重新开始或明确恢复。
- 使用独立低并发评测队列，首版默认并发 1，并遵守共享模型服务容量；不改变生产队列和自动日报调度状态。
- 独立记录调用与 token 预算、每次请求超时、整次运行时限；实际请求仍受供应商账户额度约束。开始前按每案例最多两次生成计算调用上限。
- 每个候选默认每案例跑一次；修正不能因为答案与期望标签不一致而触发。重复试验创建新运行，保留所有结果，不挑最佳一次作为原运行成绩。
- 默认不复用生产模型输出缓存，真实执行被测阶段；幂等恢复只复用同一次评测已完成的条目。
- 不读取实时 Persona、重新抓取论文、写日报版本、提交正式分析任务、更新反馈或向 AI Persona 提案。
- 支持取消；预算耗尽暂停；服务退出后标记中断，不后台自动重发。明确恢复时固定原配置，仅执行未完成项。
- 网络中断且无法确认供应商是否已处理的请求记为“结果未知”，不能作为普通未调用项无提示重发；手动重试需保留原尝试及可能发生的用量。

每次实际模型调用前再次检查样例是否撤销或删除。运行中撤销时取消该样例后续调用，尽力中止在途请求；已经发出的请求不能声称被撤回。报告记录此变化，不能悄悄缩小分母。

## 7. 评分与报告

### 7.1 逐例评分

```text
if 输入缺失、取消、错误或输出校验失败:
    outcome = null
    decision_correct = null
    case_pass = false
else if outcome == needs_fulltext:
    decision_correct = null
    case_pass = false
else:
    decision_correct = outcome == expected_outcome
    case_pass = decision_correct
```

只有经过本次输出协议及引用校验的合法二元判断，才进入判断正确率。非法 JSON 中恰好出现 `recommended` 不算有效结果；有限修正成功后使用最终有效结果，并记录全部尝试。

原反馈为“不准确”不等于回测必然失败。它用于推导期望值；新结果符合该期望即通过。

### 7.2 指标定义

定义：

- `N`：本次启动时固定的有效标签样例数，包括清单内已标明缺少回放输入的样例。
- `V`：取得经校验的合法二元输出的样例数。
- `C`：二元输出符合期望的样例数。
- `TP`：应推荐，实际推荐；`TN`：不应推荐，实际不推荐。
- `FP`：不应推荐，实际推荐；`FN`：应推荐，实际不推荐。
- `V = TP + TN + FP + FN`，`C = TP + TN`。

| 指标 | 公式 | 解释 |
| --- | --- | --- |
| 全量通过比例 | `C / N` | 首要指标；未完成、无判断及失败不计成功 |
| 二元判断完成率 | `V / N` | 是否对选定案例稳定给出有效二元判断 |
| 有效判断正确率 | `C / V` | 仅在有效二元输出上的正确率，必须与前两项同时展示 |
| 误推荐比例 | `FP / (TN + FP)` | 有有效判断且期望不推荐的案例中，错误推荐的比例 |
| 漏推荐比例 | `FN / (TP + FN)` | 有有效判断且期望推荐的案例中，错误排除的比例 |

所有百分比显示分子与分母，分母为 0 显示 N/A。同时分别展示期望推荐与期望不推荐两组的样例数、完成数、正确数，避免多数类别掩盖另一类的问题。

`needs_fulltext`、校验失败、请求失败、超时、输入缺失、取消／未执行、运行中撤销分别统计；这些状态不塞入 FP 或 FN。每个条目只有一个最终状态，完成数与各类未完成数之和必须等于 N。

例：10 条样例，8 条获得二元判断，6 条正确，另有 1 条需要全文、1 条请求失败：全量通过比例为 6/10，有效判断正确率为 6/8，完成率为 8/10。不能仅展示 75% 正确率。

### 7.3 A/B 比较

两侧使用同一清单、同一标签修订，并分别报告调用数、完成率和费用。按 `case_id + benchmark_revision` 配对展示：

| A | B | 分类 |
| --- | --- | --- |
| 不通过 | 通过 | 改善 |
| 通过 | 不通过 | 退步 |
| 通过 | 通过 | 保持通过 |
| 不通过 | 不通过 | 均未通过 |

每条保留未通过原因，区分“判断错了”与“模型请求失败”；不能把解决超时解释为推荐偏好理解改善。需要单看判断差异时，另外展示双方均有有效二元输出的子集及覆盖数量。

运行尚未完成、被取消或中断时，报告显示“部分结果”，不自动推荐启用候选版本。不同清单的历史结果可以分别查看，但不直接计算一个具有因果含义的改善百分比。

### 7.4 报告的解释范围

报告名称使用“个人已评价样例表现”。这些样例来自自愿反馈，不能声称代表全部论文或线上总体准确率。

默认展示总样例数、独立论文数、订阅／严格度／时间范围，以及正负标签分布。用户可以按这些业务字段查看分组结果，不根据不满意理由自动挑选更有利的测试范围。

已用于阅读失败原因、修改提示词的样例属于开发依据。后续可以保留未参与调整的新论文作为留出集；按论文分组，并记录测试集用途。使用留出案例继续调整之后，不再把该结果描述成对未见样例的验证。

## 8. 页面与用户流程

### 8.1 日常反馈

维持四项反馈，不增加原因分类或人工期望选择器。初筛准确性按钮绑定 `screening_version_id`，详细报告里的反馈明确显示“全文分析判断”，首版不进入初筛测试集。

反馈保存后可轻量显示“已保存为推荐测试样例”，提供查看样例入口。撤销后显示已撤销；历史数据不足时显示已保存反馈但不可回放。用户不需要离开日报完成额外操作。

### 8.2 评测与改进入口

Paper Radar 增加一个“评测与改进”入口，包含四个视图：

| 视图 | 内容 |
| --- | --- |
| 测试样例 | 原判断、用户反馈、自动期望、论文与条件、可回放状态；修改反馈、撤销、删除、备份 |
| 运行评测 | 选取或冻结测试集，选择一个或两个候选配置，预览预算并开始 |
| 评测报告 | 指标、覆盖与异常、用量、逐例原判断／期望／A／B 对照 |
| 改进参考 | 查看不准确理由与失败案例，打开 Prompt Workbench 修改提示词 |

“测试样例”可按原推荐／未推荐、期望判断、订阅、严格度、日期和输入状态筛选。理由在管理和改进视图可读，但评测请求使用独立无理由投影。

Prompt Workbench 提供通往同一组页面的入口，继续负责提示词编辑、版本保存和显式启用；测试集、反馈和批量报告由 Paper Radar 保存，不在工作台重复维护主数据。

### 8.3 改进流程

1. 日常查看推荐与未推荐结果，按需要提供准确性反馈。
2. 积累样例后，建立一个固定测试集。
3. 在工作台根据开发案例和理由修改提示词，保存候选版本。
4. 在同一测试集上比较当前版本和候选版本。
5. 查看全量通过比例、完成率、误推荐、漏推荐及退步案例。
6. 用户选择是否在工作台启用该版本；回测服务不自动发布，也不重生成历史日报。

## 9. 存储与接口建议

### 9.1 复用现有 SQLite

首版在当前分析数据目录的 `radar.sqlite` 内增量迁移，具体迁移版本以实施时的最新 schema 为准，不使用文档中的历史版本号覆盖现有迁移。

建议的新增逻辑表如下，字段可按项目现有 JSON 存储方式实现：

| 表 | 职责 |
| --- | --- |
| `screening_inputs` | 不可变初筛输入、hash、协议与原流程信息；业务版本和样例共同引用 |
| `evaluation_feedback_events` | subject 的反馈修订、理由、撤销及幂等信息；与既有反馈当前值同事务更新 |
| `evaluation_cases` | 稳定 case、subject 唯一键、group、当前修订、活跃／撤销／删除状态 |
| `evaluation_case_revisions` | 不可变期望标签、原判断、输入引用、可回放状态及生成依据 |
| `evaluation_suites` | 固定版本的成员清单、输入 hash、用途和创建时间 |
| `evaluation_runs` | 候选配置、执行协议、预算、状态、评分版本及聚合报告 |
| `evaluation_run_items` | 每个案例与候选的输入指纹、调用尝试、原始输出、解析结果、分数和用量 |

活跃引用不能级联删除输入。归档与清理由同一服务检查业务、样例和运行的引用；已撤销样例不能通过备份导入或旧报告自动重新激活。

备份包括样例输入、反馈历史、清单和需要保留的报告；采用一致性数据库备份或应用导出，不能只复制正在 WAL 写入的主数据库文件。恢复时校验 schema、hash、引用、subject 冲突和撤销状态。模型密钥、OAuth 凭据、锁和无关日志不进入评测导出。

### 9.2 样例结构示意

以下标识为格式示例，hash 使用占位值：

```json
{
  "schema": "paper-radar.recommendation-case/v1",
  "case_id": "case-example-01",
  "subject_key": "daily_screening:dailyversion-example:accuracy",
  "mode": "daily_screening",
  "group_id": "arxiv:2501.12903",
  "benchmark_revision": 1,
  "source": {
    "screening_version_id": "dailyversion-example",
    "subscription_id": "subscription-example",
    "paper_version": "2501.12903v3"
  },
  "original_outcome": "recommended",
  "expected_outcome": "not_recommended",
  "input_snapshot_id": "screen-input-example",
  "input_hash": "<sha256>",
  "replay_status": "ready",
  "active": true
}
```

该对象供管理与评分使用；生成器仍只接收输入快照的白名单字段，不能接收整个 case 对象。

### 9.3 接口草案

新增命名空间 `/api/evaluations/v1`，不将批量回测硬塞进现有单阶段 `/api/prompts/v1`。

| 接口 | 作用 |
| --- | --- |
| `GET /subjects/:screeningVersionId` | 查询原判断、反馈修订、二元资格和已有样例状态 |
| `PUT /subjects/:screeningVersionId/feedback` | 写准确性反馈及可选理由，自动推导标签并保存样例 |
| `DELETE /subjects/:screeningVersionId/feedback` | 撤销准确性反馈，退出后续回测 |
| `GET /cases`、`GET /cases/:id` | 样例列表与详情 |
| `DELETE /cases/:id` | 删除个人评测样例，不删除业务日报 |
| `POST /suites`、`GET /suites` | 冻结及查看清单版本 |
| `POST /runs/preview` | 无模型调用地检查输入、版本、模型和预算 |
| `POST /runs`、`GET /runs/:id` | 主动运行与读取报告 |
| `POST /runs/:id/cancel`、`POST /runs/:id/resume` | 取消或明确恢复未完成部分 |
| `POST /imports/legacy-feedback` | 幂等整理可核验的既有初筛准确性反馈，不调用模型 |
| `POST /exports`、`POST /imports` | 本机评测数据备份与恢复 |

写反馈请求含 `value`、可选 `reason`、幂等键及 `expected_feedback_revision`；撤销也进行修订和幂等校验。服务端确定 subject、原判断、期望和输入来源，不接受客户端上传任意标准答案。

现有日报准确性反馈路径可以保留，但必须统一委托同一服务并采用相同版本校验；不能保留绕过样例同步或二元资格检查的旧写入分支。非首版维度继续走原业务逻辑，不强行建立案例。

反馈与模型运行沿用本机管理接口的访问约束，不增加普通 Agent 代替用户评价的 MCP 工具。Demo 页面不得调用真实模型或混入本机个人数据。

## 10. 实施顺序

| 阶段 | 交付内容 | 完成判据 |
| --- | --- | --- |
| R1：反馈与样例 | 二元资格、准确归属、完整输入快照、标签映射、事务、修订、撤销和样例页 | 点击反馈后能恢复原判断与原输入；不同页面和并发操作保持一致 |
| R2：单版本回测 | 抽取共享初筛执行逻辑、冻结清单、主动运行、预算、取消恢复、确定性评分 | 不调用裁判，能在真实模型连接下生成可追踪的逐例结果与指标 |
| R3：比较与工作台 | A/B、改善退步报告、改进参考、工作台入口、历史整理和备份恢复 | 完成从日常反馈到比较版本、人工选择启用的完整闭环 |

R1–R3 完成才称为本文首版交付。全文推荐判断适配器、来源／检索端到端回测、内容语义评测和自动优化另行设计，不作为首版完成条件。

## 11. 验收标准

### 11.1 标签与反馈归属

- 四种原判断和反馈组合得到唯一正确标签，反复修改始终从原判断计算。
- 未反馈、不满意理由单独编辑、其他维度反馈、阅读与讨论行为均不创建准确性样例。
- `needs_fulltext`、无结果和处理失败即使直接请求后端，也不能生成二元标签。
- 日报初筛与全文判断的反馈目标明确；全文分析完成不会改变旧初筛样例。
- 同一 subject 的重复请求只建立一个样例；过期修订不覆盖新反馈。
- 原始输入缺失与保存失败分别显示，不能提示虚假的“可回放”或“已保存”。

### 11.2 快照与数据生命周期

- 原任务、标签、严格度或实时 Persona 变化后，样例仍恢复原始输入。
- 模型实际看到的全部初筛 Persona 依据可恢复，不只保留输出引用的子集。
- 工作台清理超过 30 条 captures 或原日报删除后，已收录样例仍可回放。
- 生产缓存命中和多轮结构修正都能追溯正确输入；重放不携带历史修正错误或原答案。
- 事务失败不产生一边保存、一边丢失的反馈和样例状态。
- 撤销、删除、历史整理和导入不会意外复活样例；备份恢复保留必要依赖。

### 11.3 隔离与执行

- 评测使用固定输入和候选提示词，不访问实时 Persona、arXiv 或无关本机资料。
- 期望标签、用户评价、理由、原输出和后续讨论不进入生成请求。
- 生产与评测使用相同初筛协议和有限修正规则；不会按标准答案重试直到答对。
- 运行不写日报、详细报告、订阅、线上提示词或正式 Persona。
- 取消、预算耗尽、服务中断和结果未知的请求均有明确状态；不会无提示重发。
- 每次调用检查撤销状态，连接改变不会静默改用其他模型。

### 11.4 评分与比较

- 固定合成结果可以精确检验 TP、TN、FP、FN、所有分母与 N/A。
- 无效 JSON、无效引用、需要全文确认、错误和取消不会被当作正确二元输出。
- 将困难样例改成 `needs_fulltext` 不会提高全量通过比例；未完成数量始终可见。
- 所有条目的终态数量之和等于固定 N；运行中撤销不会静默改变分母。
- A/B 只对相同案例和修订配对，并列出改善、退步、均通过和均未通过。
- 修改理由不改变标签、生成输入、输入 hash 或给定输出的评分。
- 报告区分有效判断正确率、全量通过比例和完成率，展示个人样例范围及独立论文数。
- 合成 fixture 单独标记，不计入用户个人反馈统计；真实模型回测由用户主动启动，编写文档或保存反馈不触发调用。

首版完成后，系统应能回答：在同一批用户已经评价过的条件下，候选版本是否减少误推荐和漏推荐，是否引入退步，以及这些变化对应什么调用成本和完成率。
