## 1. 背景与问题

现有材料详情页同时提供“材料智能整理”和“用自然语言维护”。前者把当前材料作为分析依据，后者把当前材料记录作为维护对象。两者都进入 AI 对话页面，但名称没有说明输入、修改范围和预期结果的区别。

当前助手主要围绕一个对话输入框，以及入口携带的单个材料或记录工作。用户难以在同一页面明确选择多份依据、指定数据类型和修改范围，也难以判断材料究竟用于参考还是将被修改。

本次重构需要解决：

1. AI 维护入口和名称分散，用户需要理解内部功能分类才能开始。
2. 参考依据、维护对象和操作要求混在一起，维护边界不直观。
3. 已有材料以外的粘贴文本、任务附件等输入缺少统一使用方式。
4. 结果需要清楚说明具体变化、依据和不确定项，并与已有审核流程连贯衔接。

## 2. 产品定位与目标

AI 维护助手是用户主动发起 Persona 数据维护的统一工作区。

用户表达“根据什么、维护什么、希望怎么维护”，助手读取所需来源与相关正式记录，形成具体变更建议。用户可以继续用自然语言调整建议，审核通过后写入正式 Persona。

核心目标：

- 一处完成选择依据、限定对象、描述需求、查看结果和继续修改。
- 支持单份或多份依据，以及无需外部材料的直接陈述。
- 同时覆盖新增、补充、修改、纠错、合并、归档和关系维护。
- 优先复用已有记录，减少重复知识、重复偏好和重复关系。
- 每项变更可查看理由、来源、修改前后内容及关联依赖。
- 多轮修改围绕同一任务和同一组候选进行，复用一次人工审核。

## 3. 已确认的产品方向

| 事项 | 要求 |
| --- | --- |
| 功能归属 | 完整 AI 维护功能统一放入“AI 维护助手” |
| 输入结构 | 三部分：参考依据、维护对象、自然语言需求 |
| 依据 | 支持已有材料、粘贴文本、上传文件，可组合使用 |
| 链接入口 | 当前范围仅限 arXiv；输入其他链接时提示“目前只支持 arXiv 链接”，不进入下载或分析 |
| 无附件维护 | 用户的明确陈述可直接作为依据，不强制额外材料 |
| 对象 | 支持知识、偏好、材料、课程；允许多选和进一步限定范围 |
| 范围约束 | 用户选择控制可修改范围，AI 不自行扩大 |
| 附件与材料 | 任务附件默认不自动成为材料库记录，收录需单独表达意图 |
| 结果 | 展示具体变化、依据、理由和不确定项，支持继续对话调整 |
| 发布 | 有效候选自动进入既有待审核区，用户审核后生效 |
| 个人事实 | 材料内容不能直接证明用户掌握、喜欢或认同其中内容 |

材料页是否保留一个通往助手的快捷入口、首版文件格式及具体布局，属于第 15 节的实现选项，不视为已经逐项确认。

## 4. 信息架构与页面结构

### 4.1 统一入口

- 侧栏保留清晰可见的“AI 维护助手”，桌面和窄屏均可访问。
- 移除材料页原有“材料智能整理”“用自然语言维护”双按钮；其他记录页的相关入口也应统一命名和行为。
- 若保留详情页快捷入口，只提供“交给 AI 维护助手”，打开同一工作区，携带可见、可修改的上下文。
- “查看相关维护结果”可保留，定位到已有任务或同一审核详情。
- 进入页面、切换对象、选择依据和查看历史都不自动调用模型。用户点击“分析并生成候选”才开始本轮处理。图片是例外：用户明确点击“上传并读取”时，将原图交给已配置的材料模型识别文字；界面事先说明并提供原图与提取文字供核对。此时尚不生成维护候选。

### 4.2 新建任务页面

以下为内容结构示意，不限定最终视觉布局：

```text
AI 维护助手                                      最近任务

参考依据（可选）
[选择已有材料]  [粘贴文本]  [上传文件]
已添加的依据：标题／文件名、类型、可用状态，可查看或移除
不添加参考内容也可以直接描述你的偏好或修改要求。

这次要维护什么？
[ ] 知识   [ ] 偏好   [ ] 材料   [ ] 课程
进一步限定范围（可选）：选择具体条目、知识分支或偏好场景

你希望怎么维护？
[自然语言输入框]
[可点击并编辑的示例需求]

[生成维护建议]

开始后：任务摘要、处理进度、对话、变更建议与审核操作
```

首轮只要求选择至少一种维护对象并填写需求。具体记录和外部依据均可不选。操作类型从自然语言理解，不再增加必填的“新增／修改”等下拉框。

模型配置入口保持次要位置。处理阶段、模型运行信息等诊断内容按需展开，不占用主要任务区域。

## 5. 输入一：参考依据

### 5.1 来源类型

| 来源 | 交互要求 | 依据语义 |
| --- | --- | --- |
| 已有材料 | 搜索、多选，展示标题和原文可用性，支持查看原文 | 引用本轮所用的来源版本 |
| 粘贴文本 | 独立文本区域，可选填写标题；可添加多段 | 保存用户提供的参考文本，不自动认定文本作者是用户 |
| 上传文件 | 选择或拖入文件，可添加多个；展示解析状态 | 保存任务附件及用于分析的文本版本 |
| 用户本次陈述 | 来自需求及后续消息，无须重复填入依据区 | 只有用户明确表达的事实、偏好或采用意图才按本人陈述处理 |

来源可以混合，例如“两篇已上传论文＋一段个人评价”。每份依据具有独立身份和定位，结果应能区分究竟使用了哪份内容。

### 5.2 参考内容与操作要求分开

需求输入框用于指示本次维护；依据区用于提供被参考的内容。

粘贴文章、上传文件或材料中的指令性文字，不自动成为维护要求。引用文本中的第一人称也不自动代表当前用户。仅在作者身份或用途影响结果时提出有针对性的澄清，不要求所有附件填写复杂来源表单。

### 5.3 附件与长期材料的关系

- 添加文件或文本时，默认仅作为任务依据保存，不直接新增正式 Material。
- 可提供“同时收录到材料库”选项，默认关闭；用户也可在需求中明确要求收录。
- 开启收录时，应在维护对象中清楚显示“材料”，将收录作为本次待审核变更展示，并执行必要字段和重复检查。
- 关闭收录时，附件仍须可供本次结果及后续证据追溯；不能因未生成 Material 而丢失已采纳结果的来源。
- “上传成功”“可用于分析”“已收录材料库”是不同状态，界面必须区分。

### 5.4 可读性与覆盖范围

每份依据显示“处理中、可用、解析失败、需要补充文本”等明确状态。

无法读取时，应说明具体原因，并允许补充文本、替换或移除该依据。不得仅凭文件名生成仿佛已经阅读全文的结果。若部分依据不可用，用户应能明确选择仅处理可用部分；系统不静默忽略失败文件。

长文处理保留分段、进度和断点继续能力。结果能够查看实际阅读范围；仅处理部分内容时，明确说明结论基于该范围，不宣称已完整分析全部依据。

### 5.5 已有 Persona 作为比较上下文

系统根据维护对象和需求自动检索相关正式记录。用户不需要把每条已有知识或偏好手动选为依据。

已有记录用于定位、查重和比较，修改前必须读取当前完整内容。系统应区分“来源支持的内容”“已有 Persona 记录”和“模型归纳”，不得把已有的未确认推测循环用作新事实的证据。

### 5.6 已确认的链接范围（2026-09-09 补充）

正式页面的链接入口仅接受 arXiv abs／pdf 链接，复用现有论文导入流程；不接受裸论文 ID，不显示“或论文 ID”。普通网页、课程主页和非 arXiv 的 PDF 直链留待后续支持。

- 链接提示明确写出仅支持 arXiv；输入其他链接时显示固定错误文案：**目前只支持 arXiv 链接**。
- 拒绝的链接不加入依据列表、不下载、不交给模型，也不自动转入通用网页导入。
- 课程示例默认使用截图或大纲文件；用户也可以粘贴课程文本，页面不提示当前能够读取课程网址。
- 前端和服务端都校验链接范围；域名和论文路径沿用现有 arXiv 解析规则。

状态：已接入正式维护页，并提供论文、notes、课程三个可编辑需求示例。本节约束 AI 维护助手的新链接入口，既有材料管理中的通用 URL 导入仍保持原有行为。

## 6. 输入二：维护对象与范围

### 6.1 维护类型

| 类型 | 可维护内容 | 可选范围 |
| --- | --- | --- |
| 知识 | 知识条目、知识间关系、掌握程度和兴趣等已有字段 | 指定条目、知识分支 |
| 偏好 | 偏好规则、适用场景、参考示例 | 指定场景、偏好或示例 |
| 材料 | 摘要、标签、评价等已有字段及材料与知识的关系 | 指定一份或多份材料 |
| 课程 | 课程已有字段及已支持的课程与知识关系 | 指定课程 |

上述内容受现有数据模型约束，不因提供自然语言入口而自动增加不存在的字段或关系类型。个人状态字段还需满足第 9 节的依据要求。

选择类型而不指定记录时，允许在该类型内检索相关对象并提出新增建议；不表示可以无目的地批量修改全部记录。

### 6.2 读取范围与修改范围

- 允许按任务需要读取有关联的其他类型记录，但读取不授权修改。
- 修改已有记录、创建新记录和调整关系都须符合本轮显示的范围。
- 证据等支撑记录可随主候选生成，相关依赖须在结果中可见。
- 涉及范围外业务对象的修改，应说明需要扩展到什么范围，等待用户明确调整后再生成相应候选。
- 例如只选择知识时，可以参考论文，但不顺便重写论文摘要或新增写作偏好。
- 同一范围内的关联依赖应成组展示；跨类型关系如还需创建范围外的端点记录，必须先解决范围问题。

### 6.3 同一材料的两种角色

材料既可以是参考依据，也可以是维护对象，两者在页面中分别显示。

例如“根据论文正文更新这篇论文的摘要，并补充相关知识”，需要：依据选择论文；对象选择材料和知识；材料范围指定该论文。选择一份参考材料不会自动授权修改它。

从详情页进入时，建议材料页预填当前材料为依据，知识、课程或偏好页预填当前记录为维护对象。任何预填都应可见、可移除，不自动开始生成。

## 7. 输入三：自然语言需求

输入框名称为“你希望怎么维护？”，支持用户表达：

- 新增、补充和修改信息。
- 根据新依据纠正旧内容。
- 复用或合并重复条目。
- 添加、修改或移除关系。
- 调整偏好、适用场景和参考示例。
- 归档或恢复记录。
- 限定保留哪些内容、不要修改哪些字段，以及结果粒度。

示例仅填入输入框，用户可编辑，不自动提交：

| 场景 | 示例需求 |
| --- | --- |
| 论文补充知识 | 根据这两篇论文补充张量网络相关知识，优先复用已有条目，给出原文依据，保留我的掌握程度。 |
| 直接声明偏好 | 以后帮我解释公式时，先解释符号含义，再给推导过程。 |
| 从范例提炼偏好 | 我希望论文写作采用这段示例的组织方式，请提炼为论文写作场景下的偏好。 |
| 调整材料信息 | 根据这篇论文正文更新摘要，并检查它关联的知识是否准确。 |
| 整理重复知识 | 检查这三个条目是否重复；如果合并，保留最完整的描述并处理原有关系。 |

需求已明确时直接处理。对象指向、作者身份、证据冲突或修改意图不明确且会实质影响结果时，提出简短澄清。不得为了生成候选而猜测关键个人事实；仅询问或无须变更时允许给出零变更结果。

## 8. 维护任务流程

```text
选择参考依据＋维护对象＋填写需求
                    ↓
生成维护建议：检查输入、读取依据和相关正式记录
                    ↓
理解需求、匹配已有对象、生成具体变化
                    ↓
校验字段、依据、范围、版本及关联依赖
                    ↓
有效候选自动进入同一组待审核记录
                    ↓
查看差异与依据 ←→ 继续对话或编辑候选
                    ↓
复用现有审核：通过／修改后通过／拒绝／暂缓
                    ↓
通过的内容写入正式 Persona，保留来源和历史
```

存在阻断性澄清时，先在任务内处理问题，未解决前不自动送审本轮候选。没有变更时说明原因，不创建空的审核任务。

生成成功和发布成功分别显示为“已生成维护建议，待审核”与“已生效”。不得仅显示含义模糊的“已完成”。

## 9. 依据、个人事实与冲突处理

### 9.1 各类依据可支持的内容

- 论文正文可支持概念说明、方法、关系和材料摘要。
- 用户明确陈述可支持本人的偏好、掌握程度、兴趣和修改意图。
- 用户指定“把这段文字作为我的风格参考”时，用户指令支持采用意图，参考文本支持具体风格描述。
- 上传、收藏、阅读或引用材料本身，不足以认定用户掌握、喜欢或赞同其中全部内容。
- 没有充分依据时，个人状态保持未设置或原值；不得把缺少信息解释成低兴趣、不了解或否定偏好。

### 9.2 冲突与归纳

- 多份依据冲突时，展示冲突的具体主张和出处，不静默择一写入。
- 新依据与已有 Persona 冲突时，展示旧值、新建议及理由；用户明确要求纠正的，可形成待审核修改。
- 模型归纳应标明是归纳，并指向实际支持的来源片段。模型自己的分析文本不能替代原文证据。
- 证据不足时可以说明“尚不能确定”，并指出需要用户补充什么。

## 10. 结果展示与审核

### 10.1 任务结果概览

显示本次依据、维护类型与范围，以及新增、修改、归档、关系调整等数量。疑问和冲突单独列出，不混入已准备好的确定变更。

### 10.2 单项变更

每项至少展示：

| 信息 | 展示要求 |
| --- | --- |
| 对象与操作 | 对象名称、类型，以及新增／修改／归档等行为 |
| 具体内容 | 新增内容，或修改前后的字段差异；长文本按需展开 |
| 理由 | 说明为何需要该变化以及与需求的关系 |
| 依据 | 来源标题、可定位片段或用户原话，支持查看上下文 |
| 不确定性 | 归纳、冲突、缺失依据等实际问题，不用虚构精确置信分数 |
| 依赖 | 所依赖的新对象或关系，以及只采纳部分内容的影响 |
| 审核状态 | 待审核、已通过、已拒绝、已暂缓等实际状态 |

复用已有概念的结果应显示连接到哪个已有对象；同名但含义不同的条目不能直接合并。

### 10.3 合并要求

合并建议必须说明保留的对象、被归档对象、内容如何合并、关系和引用如何处理。用户审核的是具体变更组合，不是一个无法核对的“已去重”结论。

需要一起生效的合并操作应作为不可拆分的依赖组处理。若现有发布机制不能安全表达该组合，应返回整理建议和限制说明，不生成会留下悬空引用或不一致状态的可发布候选。普通维护不提供永久删除。

### 10.4 审核整合

- 有效候选自动进入既有“反馈与审核”工作台，不增加“确认草稿→提交→再审核”流程。
- 助手内优先复用同一审核组件；工作台和助手显示同一组候选和同一审核状态。
- 若首阶段仍需跳转，应直接定位当前任务，并提供回到任务的入口。
- 支持现有按项处理及依赖约束；修改 AI 候选本身不等于发布，最终审核操作才使其生效。
- 审核通过、拒绝或暂缓不推导用户满意度，也不自动新增评测样例。
- 普通正式记录的人工编辑仍按现有“保存即生效”规则处理。

## 11. 多轮维护、任务历史与恢复

### 11.1 同一任务持续修改

用户可继续说“第二条范围缩小一点”“只保留知识关系”等，调整同一份候选快照。每轮不重复追加一组等价待审核项。

- 全组尚无人工审核决定时，新结果校验成功后更新同一组候选，保留旧版本历史。
- 用户手工编辑的内容须进入下一轮上下文；AI 再次修改这些字段时，应明确展示差异。
- 用户可调整依据和范围，并明确发起新一轮生成。调整过程不静默改写上轮候选。
- 页面分别显示当前待审结果使用的依据／范围与尚未生成的新输入，避免把旧结果误认为基于新附件生成。
- 已存在批准、拒绝、暂缓或失效决定时，不覆盖原任务结果；提供“基于此任务新建维护”，继承可复用输入并保留关联。

### 11.2 待审候选的保护

生成期间已有候选保持原状。失败、取消、澄清或零变更结果不自动撤回已有候选。

移除部分候选须满足依赖约束；放弃整组通过既有审核操作拒绝。不能用空输出无提示地删除整组结果。

### 11.3 历史与状态

最近任务显示可读标题、更新时间、所用依据摘要、维护类型、处理状态和审核状态。历史任务可恢复查看输入、对话、结果和依据，不只显示技术 ID。

| 情况 | 用户可见行为 |
| --- | --- |
| 正在处理 | 显示当前阶段与可观测进度，允许取消和离开后返回 |
| 等待补充 | 显示具体问题，保留已有输入和候选 |
| 没有变更 | 说明原因，可继续补充需求 |
| 生成失败／取消 | 保留已完成分析，允许继续或修改需求后重新生成 |
| 待审核同步失败 | 保留候选，允许重试同步，无须再次调用模型 |
| 已待审核 | 展示候选及审核入口，允许在未锁定时继续修改 |
| 已有审核决定 | 展示实际决定和已生效内容，后续变更新建关联任务 |

继续分析前检查来源版本、需求、模型及 Persona 版本。来源或需求改变时重新处理受影响部分；仅正式 Persona 改变时，可复用仍有效的材料分析，但必须重新匹配记录和校验变更。

## 12. 数据与实现约束

本节定义实现必须满足的语义，不预先固定数据库表名或 API 契约。

### 12.1 统一任务模型

维护任务至少表达：

- 任务身份、标题、对话及版本。
- 多份依据的身份、类型、原始内容或来源引用、版本、解析和覆盖状态。
- 可维护类型、具体对象范围和本轮需求。
- 本轮实际读取的正式记录及版本基线。
- 候选、变更理由、证据定位、不确定项和依赖。
- 关联的待审核组、处理状态、审核状态及恢复信息。

现有单个 `material_id`、`record_id` 和个人候选开关不足以完整表达新输入。后续应统一表达“依据集合＋修改范围＋需求”，保留旧会话兼容。后台仍可按内容使用不同分析步骤，无须在界面暴露为不同产品模式。

### 12.2 来源持久化

- 使用已有材料时引用确定的 Source 版本；原文改变不能改写旧候选的依据。
- 新上传文件和粘贴文本保留可定位快照；已发布记录引用的来源按长期数据保存并纳入备份。
- 用户陈述保留原话及对应轮次，结果来源可追溯。
- 未采纳任务附件可按数据保留策略清理；不得清理仍被待审候选或正式记录引用的证据。
- 新附件来源独立于正式 Material 存在，需要在实现中明确其归属和发布时的引用衔接。

### 12.3 校验与写入

模型负责理解和提出建议；程序负责字段、对象类型、修改范围、稳定引用、版本、证据位置、依赖和重复提交校验。范围约束须由程序执行，不能仅依靠提示词。

正式变化继续经现有 Proposal／ChangeSet 与发布流程。只生成建议、解析附件和创建任务都不改变正式 Persona。开始与发布前的版本检查应防止覆盖模型运行期间发生的人工修改。

重复点击、网络重试和恢复不得重复生成等价待审组。任何阶段失败都应保留最后一份有效结果，不发布部分无效变更。

## 13. 现有入口与数据兼容

- 保留旧任务、对话、证据和人工审核历史，不因名称统一而重跑模型或重新发布。
- 旧“材料智能整理”链接映射到统一助手，保留当前材料作为依据的上下文；按旧任务语义显示原有修改范围。
- 旧“用自然语言维护”链接映射到统一助手，保留当前记录作为维护对象的上下文。
- 历史任务可注明原任务类型，新任务统一使用“AI 维护助手”及描述需求的任务标题。
- “反馈与审核”继续聚合维护结果；工作台和助手不生成两份独立可写候选。
- 模型连接、后台对话学习、偏好自动应用和评测功能不因入口统一而自动启停或改变配置。

## 14. 首版范围与分阶段交付

### 14.1 首版必须包含

1. 统一入口与三部分输入。
2. 多份已有材料、粘贴文本和本地文件作为依据，支持混合使用。
3. 无外部依据的直接维护。
4. 知识、偏好、材料、课程类型选择和具体对象限定。
5. 附件默认不自动收录材料库，以及明确选择收录的路径。
6. 相关记录读取、复用查重、明确修改范围和个人事实边界。
7. 具体变更、差异、依据、理由与依赖展示。
8. 有效候选自动送审、多轮同组更新、已有审核决定保护。
9. 任务历史、输入恢复、处理进度、失败恢复与旧链接兼容。

新增、修改、归档、恢复和关系维护沿用已有操作。合并属于目标能力；首版必须正确识别和解释合并需求，只有满足第 10.3 节的完整性要求才提供可发布合并。

### 14.2 建议实施顺序

| 阶段 | 交付内容 |
| --- | --- |
| 第一阶段 | 统一任务输入和范围模型，支持已有材料、多选对象和直接陈述，统一旧入口 |
| 第二阶段 | 接入粘贴文本和任务附件、来源保存、混合依据及可选材料收录 |
| 第三阶段 | 完成结果与审核衔接、多轮编辑、恢复、兼容和全部验收 |

阶段用于拆分开发；第一、二阶段的中间结果不能标记为完整首版已交付。

### 14.3 本次不包含

以下能力不属于首版承诺；后续是否纳入须另行定义需求：

- 任意网页或 URL 直接作为任务依据；首版仍可先通过现有材料导入流程收录后选择。
- 自动读取历史聊天、外部应用、邮箱或云盘。
- OCR、图片、音视频及复杂文档解析。
- 自动推断维护类型、自动扫描整个 Persona、后台持续维护和定时任务。
- 针对维护结果新增满意度反馈、评测样例自动收录或模型自我改进流程。

AI 自动批准或绕过人工审核发布不属于本设计目标，继续遵守现有审核边界。

## 15. 实现选项与建议默认值

以下细节尚未逐项确认。实现前可依据现有能力细化，不应把建议写成已经实现的功能。

| 事项 | 建议默认值或处理原则 |
| --- | --- |
| 文件格式 | 支持 Markdown、UTF-8 TXT、带文字层 PDF，以及 PNG／JPEG／WebP 截图；扫描 PDF 须补充截图或文字。界面准确列出实际支持格式，不暗示任意文件都可分析 |
| 文件数量与预算 | 支持多份；依据实际解析和模型预算确定单文件、总文本和附件数量上限，超限前明确提示，不静默截断 |
| 详情页快捷入口 | 可保留一个“交给 AI 维护助手”；完整流程始终在统一工作区 |
| 新任务对象默认值 | 无详情页上下文时不默认选择所有类型；用户至少选择一类 |
| 审核展示位置 | 优先在助手内复用审核组件；阶段性交付可先精确跳转到同一工作台详情 |
| 未采纳附件保留期 | 沿用或扩展项目数据保留设置；先保证待审与已发布证据不会丢失 |
| 合并发布能力 | 先检查现有依赖和发布机制；无法保证一致性时，提供建议并明确限制，不伪装为完整可发布合并 |

## 16. 验收标准

以下以真实可观察行为验收，既检查成功路径，也检查范围、证据和结果保护。

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 统一入口 | 侧栏可进入完整助手；材料页不再同时出现原有两个 AI 维护按钮 |
| A02 | 新建任务 | 页面明确显示三部分输入；选择对象并填写需求后即可发起 |
| A03 | 多份材料 | 可选择至少两份已有材料；结果能定位各自引用的来源 |
| A04 | 混合依据 | 一份材料、一段粘贴文本和一个支持格式文件可用于同一任务，来源身份不混淆 |
| A05 | 直接声明偏好 | 不添加附件，输入明确偏好后可生成对应候选，不要求重复填写依据 |
| A06 | 附件收录 | 默认只保存任务依据；明确选择收录才出现材料候选，批准前材料库不增加正式记录 |
| A07 | 同材料双角色 | 材料可同时作为依据和对象，两种角色可见且可独立调整 |
| A08 | 范围限制 | 只选知识时，输出不能修改偏好或材料摘要；程序能拒绝越界候选 |
| A09 | 具体范围 | 指定条目或分支后，不修改无关对象；需要新增依赖时清楚说明范围影响 |
| A10 | 类型覆盖 | 知识、偏好、材料、课程各完成至少一个新增或修改场景，字段符合已有模型 |
| A11 | 已有对象复用 | 依据涉及已有同义概念时优先复用；同名异义时不直接合并 |
| A12 | 个人事实边界 | 仅上传论文不生成“用户熟练掌握／喜欢”的事实；未设置值不被无依据填充 |
| A13 | 范例采用 | 用户明确要求采用文本风格时可生成偏好，分别追溯采用指令和风格依据 |
| A14 | 证据与冲突 | 结果展示来源片段；冲突或不充分依据可见，不伪造出处或静默选择个人事实 |
| A15 | 阅读失败 | 不支持或无法解析的文件明确报错；部分失败须由用户选择处理范围后继续 |
| A16 | 处理覆盖 | 长文显示实际覆盖范围；取消或恢复后不虚报全文已读 |
| A17 | 变更可核对 | 新增展示内容，修改展示前后差异，归档和关系调整展示对象及影响 |
| A18 | 自动送审 | 有效非空候选且无阻断性问题时自动进入待审组；没有额外草稿确认关卡 |
| A19 | 一次审核 | 助手与工作台状态一致；仅人工批准后正式数据变化；编辑候选不直接发布 |
| A20 | 多轮修改 | “第二条缩小范围”等要求更新同一组未审核候选，保留历史和手工编辑上下文 |
| A21 | 输入调整 | 新增附件或修改范围后，旧结果与新输入可区分；新一轮成功前不悄悄替换候选 |
| A22 | 结果保护 | 澄清、零变更、失败、取消不撤回已有待审组；有人工决定时不能覆盖 |
| A23 | 恢复与重试 | 刷新可恢复任务；送审失败可无模型重试；重复请求不产生重复待审组 |
| A24 | 版本变化 | 依据或正式记录已变化时重新校验，不能用过期结果覆盖最新人工修改 |
| A25 | 合并完整性 | 展示保留对象、归档对象和引用处理；不能安全成组发布时明确返回限制 |
| A26 | 来源生命周期 | 已采纳附件即使未收录材料库也可追溯；清理任务不破坏仍被引用的来源 |
| A27 | 兼容与被动浏览 | 旧任务与旧链接可查看且上下文正确；打开页面或历史不自动调用模型或发布 |

## 17. 与既有能力的关系

当前实现已经具备对话维护、单材料分析、证据定位、候选校验、自动送审、同组更新、人工审核和部分恢复能力，可在本次重构中复用。

统一任务输入、多来源依据、附件与材料的独立生命周期、显式维护范围、三部分输入界面及审核衔接已接入。附件现支持 UTF-8 TXT / Markdown、带文字层 PDF 和图片，单文件最多 20 MB，提取文字最多 750 KB；图片读取需核对。长材料复用既有分段理解、原文补读与恢复流程，超出阶段容量时明确要求拆分。选择同时收录材料时，须由用户明确选择阅读／作者关系。自动语义合并和来源自动清理未开放，详见[统一设计第 17 节](AI_PERSONA_UNIFIED_MAINTENANCE_DESIGN.zh-CN.md#17-首版实现与验证2026-09-09)。
