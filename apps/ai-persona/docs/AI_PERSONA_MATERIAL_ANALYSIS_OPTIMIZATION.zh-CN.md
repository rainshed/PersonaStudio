# 材料智能整理：精简输入、分阶段分析与断点继续

日期：2026-09-07。状态：已实现，并通过离线自动测试与隔离界面验收。

## 1. 问题与目标

现有材料整理把全文、Persona 目录、完整记录以及九类数据库 Schema 一起交给模型，最多重复三轮；成功前的分析和补读结果仅在内存中。一次调用超时后还会自动再尝试 120 秒。用户看到的阶段始终是“读取相关记录”，无法分辨长时间等待发生在哪里。

已观测到一次约 4.3 万输入 token 的请求在约 9 秒内成功，而下一轮约 241.5 秒后失败。因此不能把超时简单归因于输入长度，也不能承诺缩短提示词就一定更快。

本次目标：减少不必要的 Schema 和全文重传；让输入、输出和调用次数有明确预算；保存已完成步骤；区分超时与取消；显示真实阶段及安全的耗时信息。保留 Pi 模型适配层、现有模型选择与备用策略、草稿编辑和人工审核。

## 2. 流程与边界

| 输入情况 | 模型工作 | 程序工作 |
| --- | --- | --- |
| 短文本（带行号 ≤12,000 字符） | 一次生成候选，必要时有限补读 | 召回相关记录、校验、保存草稿 |
| 较长文本 | 先理解材料，再生成候选 | 保存分析，召回记录和证据片段 |
| 超过单段预算 | 按原始行号逐段理解，再统一生成候选 | 保存每段检查点，显示已完成覆盖范围 |

每段上限 60,000 字符，最多 20 段；不切断单行，不静默丢弃尾部。超大单行、段数或综合上下文超预算时明确提示缩小材料。切分优先在段落／标题附近，跨段结论保留原始行号与上下文，由候选阶段统一检查。暂不引入向量数据库、额外摘要模型、自动导入分析或批量队列。

短文本一次生成是低复杂度路径，不意味着语义质量已优于两阶段。两阶段也不保证一定更快；它主要减少复杂工作耦合和失败后重复阅读。

## 3. 模型输入输出

### 3.1 理解材料

输入只有：独立材料分析指令、用户目标、来源元数据、带原始行号的一段文本、紧凑分析输出约束。此阶段不接收 Persona 全库、对象 Schema 或个人偏好。

输出包含：本段概述、关键概念及别名、问题／方法／结论／限制／关系的证据化主张、尚不确定的事项。概念与主张附原始行范围。必须保留适用范围和限定条件；“本段未提及”不是“整篇不存在”；材料内容不具有指令权限。

### 3.2 召回与候选生成

程序用概念名、别名和用户目标对当前记录进行确定性的词项／短语召回，优先加载命中的完整记录及已有关系。模型负责判断语义同一性；词项命中不是自动合并依据。候选目录有上限并显式标记是否完整，支持模型提出补充检索词和记录 ID，不能把未命中当作新概念的证明。

较长材料的候选输入包含已保存的各段分析、对应原文证据及邻近行、召回的记录、既有草稿、精简字段契约。允许请求有限原文范围补读，不默认重传全文。短材料直接使用全文。

字段契约从现有 Pydantic 类型和允许字段生成，去掉数据库 ID、时间戳等由程序补齐的字段，保留必要的类型、枚举、必填约束和关系语义。材料默认仅开放知识、当前材料摘要和关系；启用个人候选时再加入对应字段与偏好类型。自然语言维护保留其通用能力但同样使用精简契约。

输出仍为完整替换草稿，仅在 values 中填写拟变更字段。上一份人工修改的草稿继续传入，不把“未输出某字段”解释成清空数据库。程序继续严格校验对象类型、版本、依赖、来源 hash、行范围、个人状态权限以及已有关系重复；模型不能直接发布。

## 4. 持久化与继续

检查点存入现有本机草稿 SQLite，无需建立第二个存储系统。保存各段有效分析、已补读的记录 ID／原文范围／检索词、每阶段调用元数据；不把完整重复提示词、流式正文或内部推理放入运行日志。

分析检查点键包含提示词版本、来源内容 hash、用户目标、个人候选开关以及生效模型连接／配置。候选补读检查点还绑定 Persona 版本和上次草稿内容。来源、模型或目标变化时重新分析；只有 Persona 变化时可复用来源分析，但重新召回与生成草稿。

“继续分析”只对失败／取消会话开放，不追加一条重复用户消息。重启后可以继续已持久化部分。旧会话没有检查点时从第一步开始；原来失败的那次历史调用没有保存分析正文，不能事后恢复。

任何检查点和最终草稿写入都核对当前 run_id、运行状态与版本，取消／新一轮之后的迟到结果不能覆盖。若分析期间正式 Persona 或来源变化，禁止交付过时可提交草稿。

## 5. 超时、重试与观测

继续通过同一个 Pi SDK 调用模型，改用其流式事件接口来观测事件到达，最终仍解析完整 JSON。只收集事件类型和时刻，不展示或记录思维正文；SDK 的 start 事件不等于上游首 token。

预算：场景判定 15 秒；连接测试 30 秒；自然语言维护 120 秒；材料提取及候选每次 180 秒。每个逻辑模型请求还受总预算约束（含备用连接），总预算不会因重试无限延长。材料流程逐步保存，因此允许用户停止后继续；不伪造进度百分比。

只对尚未收到内容的短暂限流／连接类错误有限重试；超时、已有内容后的失败、取消、结构错误不盲目重跑。备用连接仍必须由用户明确启用。超时与主动取消使用不同错误码／文案。

记录阶段、开始时间、结束／总耗时、输入字符数、输出预算、尝试次数、首内容事件时刻和供应商提供的 usage（未知为 null）。首内容事件是 SDK 可观测信号，不声称区分 DNS、排队或供应商内部推理。UI 展示当前阶段、已完成段数／覆盖范围、当前等待或已收到内容、历史阶段耗时，以及继续按钮。

## 6. 验证与交付

- 自动测试短材料一次生成、长材料两阶段、跨段原始行号、证据越界、预算错误、无重复概念／关系、个人权限与审核边界。
- 验证成功提取后第二步失败可继续，已完成段落不重跑；目标／来源／模型变化正确失效；Persona 变化只重新生成候选。
- 覆盖取消、迟到响应、并发版本冲突、手工编辑保留、运行失败元数据和结构错误。
- 通过真实 Pi → 本机 SSE 模拟服务测试跨语言调用与事件观测，使用临时 Persona 做界面验收。不默认消耗真实账户额度或上传私人材料。
- 给出输入体积／调用次数的可复现对比；真实供应商的语义准确率、P50/P95 延迟需另行真实样本评测，不用模拟延迟代替。
- 更新使用说明；安装到项目环境和用户实际使用的全局命令，重启 Studio／模型服务后检查健康状态。保留现有数据、连接与未提交改动。

## 7. 设计依据

[OpenAI 官方延迟优化指南](https://developers.openai.com/api/docs/guides/latency-optimization)指出，输入缩短不等于同比缩短耗时，生成量和串行请求次数同样重要。本设计因此保留短材料单次路径，采用任务相关输入与精简输出，并以可观测数据验证效果。本文不假定 Codex OAuth 经 Pi 支持所有 OpenAI API 专属能力，不强制接入原生 Structured Outputs 或修改模型。
