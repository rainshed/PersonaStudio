## 1. 目标与非目标

### 1.1 本次设计的目标

1. 用户在已启用学习的来源中提交消息后，系统能可靠接收事件，后台识别值得观察的信号。
2. 根据用户原话及必要上下文生成 Observation，识别行为要求、纠正、反馈、note 请求和知识讲解请求，并区分明确的一次性例外。
3. 对照正式 Persona、待审核候选及相关历史观察，决定新增、更新、复用、等待或忽略。
4. 对象与含义明确、结构合法的候选自动进入待审核区；是否值得长期保存由用户审核决定，批准后才进入正式 Persona。
5. 同一核心支持 Hook、Webhook、插件、轮询及聊天导出等不同接入方式。
6. 不阻塞正常对话，支持失败恢复、去重、预算控制、来源追溯与隐私控制。

“学习”指维护外部结构化记忆，不训练或微调模型。Observation 不是正式记忆，也不是新增的人审关卡。

### 1.2 首版范围

- 实现平台无关契约及一个真实 Codex 适配器；另用模拟平台验证可替换性。
- 学习用户主动输入的要求、纠正、反馈、明确陈述及 note／知识讲解请求；AI 回答仅作为理解、定位和评价对象，不作为批量新增知识点的来源。
- 形成新增知识候选后，由 AI 检索现有知识并提出关系建议；关系无需用户事先明确陈述，也不要求附带说明。
- 候选主要为 Knowledge Node、Relation、Preference；必要时允许生成所依赖的 Preference Context。
- 支持新建及用户明确要求的字段更新；默认不自动生成归档、删除、恢复、解除关系和语义合并操作。
- 偏好、知识和关系 proposal 只附简短备注，不生成聊天 Source／Evidence，不附原话、引用定位或证据快照；必要上下文仅用于临时分析与恢复。
- 自动采集默认关闭，用户选择来源及采集范围后启用；默认限定项目／会话，全局采集必须显式选择。

不包含：全平台接入、扫描全部历史聊天、自动批准、通用个人事实新模型、项目进度记忆、自动事实检索核验、多用户云服务，以及从未审核记忆直接修改当前回答。

既有 Studio 的用户主动保存行为保持不变；本文的人工审核边界针对自动学习产生的 AI 候选。

## 2. 架构决策

### 2.1 将三个独立变化点分开

| 变化点 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| 来源适配器 Source Adapter | 获取平台事件，识别消息来源，规范化消息，固定上下文边界，解析平台记录 | 判断用户的长期偏好，直接生成或发布 Persona |
| 传输入口 Transport | CLI／HTTP／MCP 的认证、协议解析、限流和结果封装 | 根据平台名称选择不同的学习规则 |
| 学习核心 Learning Core | 去重、排队、识别、Observation、相关记录检索、候选规划、校验与送审 | 打开平台日志路径，解析 Codex JSONL，理解 Hook 字段或读取平台账号 |

平台与传输不是同一概念：Codex 可以通过本地 CLI 或 MCP 接入；其他平台也可以使用同一 HTTP 接口。不能用一个 `CodexLearningService` 同时承载这三层。

来源适配器通过统一 `ContextProvider` 端口提供规范化上下文。核心选择已注册的上下文提供者，但不出现 `if provider == "codex"` 的业务分支。提供者实现必须由受信任配置注册，不能由消息指定动态代码、任意 URL 或文件路径。

### 2.2 复用现有项目能力

| 现有实现 | 本次处理 |
| --- | --- |
| `model_bridge.py`、`model_runtime/` | 继续复用 Pi 风格的模型连接、认证、选模、流式调用和安全运行信息 |
| `ai_service.py` | 复用字段契约和候选校验理念，抽取公共能力；不伪装成用户在维护助手里发起的新对话 |
| `agent.py` 的提案构造 | 复用严格字段、版本、依赖和引用校验；对话候选仅绑定学习批次，不接受原始证据 |
| `pending_sync.py`、`change_sets.py` | 复用预构造、幂等、同组替换和恢复日志；将任务归属由仅维护会话扩展为通用任务归属 |
| `proposals.py` 及审核页 | 保留现有人工批准、拒绝、暂缓、依赖顺序和历史保护 |
| `models.py` 的 Source／Evidence | 材料等现有功能保持不变；对话学习不复用或扩展原始证据发布流程 |

新增 `ProposalContext.kind=conversation` 与 learning_batch_id，区分对话学习任务；不要求 material_id、source_id 或 source_hash。既有材料内联证据要求保持不变。`ai_web.py` 的分析线程池随 Studio 生命周期结束，因此学习流程使用独立队列与 Worker。

## 3. 平台无关的事件契约

### 3.1 标准事件 ConversationEvent v1

以下为已实现的本机协议示例。示例中的标识均为占位值；这不是可直接公开到网络的服务。

```json
{
  "schema": "ai-persona.conversation-event/v1",
  "event_id": "evt_example_001",
  "source_connection_id": "conn_conversation_001",
  "event_type": "message.submitted",
  "conversation_id": "conversation_example",
  "scope_ref": "scope_project_example",
  "message": {
    "id": "message_example_001",
    "revision": "1",
    "role": "user",
    "origin": "human",
    "content": [
      {"type": "text", "text": "以后写技术笔记，都保留关键推导。"}
    ],
    "reply_to_message_id": "message_example_000"
  },
  "occurred_at": "2026-09-07T14:00:00Z",
  "context": {
    "ref": "ctxref_example_001",
    "boundary": "boundary_example_001"
  }
}
```

字段规则：

- `source_connection_id` 指向用户配置的来源实例，区分平台、设备／账号空间与允许学习的目标 Persona。同名会话在不同来源中不冲突。
- 来源连接使用可扩展的 adapter 标识和私有 adapter_config；核心不解析其中的平台路径或事件字段，新平台不必修改标准事件模型。
- `scope_ref` 是可选的不透明采集范围引用，例如已登记的项目或频道；由受信任适配器映射，限定模式下核心校验它属于来源连接的允许范围。需要项目级授权但无法确定范围时，不退化为全局许可；只有来源连接显式配置全局模式才能免除项目／会话列表过滤。采集范围不等于候选偏好的适用场景，后者必须另有语义依据。
- `event_id` 在同一来源实例内稳定，重传时不变；服务端另分配内部标识。不能每次重试生成新 UUID。
- `event_type` 首版为 `message.submitted`、`message.revised`、`message.retracted`；后两者只在来源实际支持时启用。
- `message.id` 和 `revision` 是不透明标识，不要求 UUID 或整数。若平台没有原生值，由适配器生成并持久化映射，不能伪装为原生字段。
- `role` 区分 `user`、`assistant`、`tool`、`system`；`origin` 区分 `human`、`automation`、`unknown`。角色为 user 不等于一定由人主动输入。
- 消息角色和 origin 由受信任采集端及可验证的来源元数据确定，不能让提取模型自行授予“真实用户”身份。
- `occurred_at`、`reply_to_message_id`、`context.ref` 可为空；缺失时显式保留未知。服务端生成 `received_at`，不得把接收时间冒充原始发生时间。
- 首版仅分析文本；未知内容类型拒绝或标记不支持，不对附件进行隐式下载或 OCR。
- submitted／revised 事件携带该版本完整的允许采集文本，不使用平台专属增量补丁；retracted 事件可省略 content，但必须指明被撤回的消息。删除标记不按“无内容事件”忽略。
- 上下文标识是不透明引用，不是可由核心直接访问的路径或 URL。
- 严格校验契约版本和业务字段，未知字段拒绝；平台诊断留在适配器及本机安全诊断表，不通过事件 metadata 扩张模型输入。

应用服务校验调用方绑定的 Principal 与来源连接一致，事件不允许提供任意数据目录。首版本机 CLI／HTTP 处于同一用户的信任边界，不能据此声称实现了远程身份认证。将来远程传输必须先认证并绑定 Principal，不能信任请求自报的 source_connection_id。

来源连接新增平台无关字段 `scope_mode: restricted | all`，默认 `restricted`。`all` 只免除该来源的项目／会话过滤，不绕过来源身份、启用状态、模型外发、上下文读取权限、预算或人工审核。原有列表保留，切回限定模式后重新生效；Worker 在每次模型外发和送审前重读配置，拦截范围缩小后已不允许处理的旧任务。旧连接缺少字段时仍受原限制，旧 `allow_all_conversations` 只保留无 scope 标准事件的兼容回退，不能作为全局开关。模式只允许由来源配置设置，标准消息事件不能携带它自行提升权限。

来源连接另有平台无关策略 `trust_user_messages: bool = false`，与采集范围及采集端能力独立。用户在 Studio 一次性开启「信任来源」后，允许该连接中未验证人工来源的用户消息继续候选整理，不再逐条确认。此策略只能通过本机来源配置修改，标准事件不能携带它自行提升权限；新建及缺少该字段的旧连接默认严格模式，不静默扩大信任。

来源信任不是身份验证：原消息 `origin`、`verified_human_origin` 能力和逐条 `human_confirmed` 标记保持原值。处理检查点另存 `origin_basis`：`trusted_source`、`verified_human` 或 `confirmed_human`，Studio 说明通过的是用户信任策略还是实际来源验证。非 user、明确 automation、敏感内容仍按原规则忽略；采集启用、来源范围、模型外发、上下文读取、预算及最终人工审核不变。

保存已启用且受信任的来源时，在同一配置事务中将本来源仍在允许范围、正文未清理的 `waiting_origin` 任务重新排队，保留信号检查点、版本递增，返回 `resumed_events` 数量；不恢复已取消、失败、已完成或其他来源的任务。Worker 在候选分析前重读信任策略，送审前再次检查来源配置；撤销信任不能被在途模型请求的迟到结果绕过。严格模式保留单条人工确认，已有审核决定不受信任开关影响。

### 3.2 来源能力声明

能力由适配器注册时声明，并经版本化契约测试验证，不接受事件自行提升能力。

| 能力 | 含义 | 缺失时的处理 |
| --- | --- | --- |
| `stable_event_identity` | 能稳定识别同一事件的重传 | 使用采集端持久映射；无法可靠区分时标记 identity_weak，不承诺完全去重 |
| `message_revisions` | 能识别修改、撤回和版本 | 保留采集快照；不声称能发现上游后续编辑 |
| `verified_human_origin` | 能区分主动用户输入与自动消息 | origin 保留 unknown；用户可显式信任来源继续候选整理，否则需单条来源确认，不伪造已验证事实 |
| `context_snapshot` | 能给出采集时的上下文快照 | 自包含消息仍可分析；依赖上下文的信号等待补充 |
| `bounded_context_read` | 能读取不越过指定边界的历史消息 | 不允许核心退化成无边界读取整个会话 |
| `reply_links` | 能定位被回复、纠正或评价的消息 | 使用有限上下文推断并标记歧义，无法消除时不送审 |
| 来源跳转（扩展项） | 能跳回来源消息 | 非必要能力；候选审核使用简短备注，不以原始聊天或外链可用为前提 |

可替换性不等于所有平台能力相同。信息少的平台允许功能降级，但不得要求核心猜测来源事实。

## 4. 上下文接口与快照

### 4.1 ContextProvider 端口

已实现的内部协议：

```python
class ContextProvider(Protocol):
    def resolve_context(
        self,
        source_connection_id: str,
        context_ref: str,
        boundary: str,
        request: ContextRequest,
    ) -> ContextSnapshot: ...
```

`ContextRequest` 只描述语义需求和预算，例如“被回复消息”“前两轮”“包含指定已知消息 ID 的上下文”；不接受模型指定 shell 命令、任意路径或下载地址。

`ContextSnapshot` 包含快照 ID、来源、会话、边界、规范化消息列表、每条消息 ID／revision／role／origin／内容、上下文覆盖情况和缺失项。输入摘要在阶段检查点中计算，不要求连接器提供 hash。来源跳转是未来扩展项，首版契约不接收该字段。

核心对快照重新计算 hash，检查所属来源、会话和消息版本。快照可以来自：

- 采集端随事件保存的最小消息集合；
- 与适配器同部署的本地读取器；
- 受认证的外部连接器后续上传的快照。

远程平台不需要映射到本地文件系统。未来若提供远程读取器，应使用预注册端点及认证，不开放由事件控制的回调 URL，避免 SSRF 和跨来源访问。

### 4.2 固定分析时间边界

每次学习只分析“当前用户输入 + 截至这次输入之前的必要上下文”。后台队列延迟不能把后续 AI 回答、用户的新修正混入旧事件。

适配器在采集时保存边界或最小快照。可补读的历史必须证明没有越过该边界；只拿到后来生成的无版本会话时，不能声称还原了当时的上下文。

若当前消息尚未写入平台会话记录，以事件 payload 为当前输入；适配器负责去重，不把同一输入附加两次。多设备、分叉会话和压缩记录也遵守相同规则；生成的会话摘要只能帮助导航，不能据此扩大用户主动选择的知识范围。

## 5. 接收、队列与公共接口

### 5.1 单一应用服务

CLI、HTTP 和 MCP 都调用同一组应用服务方法，使用相同认证范围、校验、幂等及持久化逻辑：

```python
ingest_event(event, principal) -> IngestReceipt
get_event_status(event_id, principal) -> EventStatus
attach_context(event_id, snapshot, principal) -> ContextReceipt
retry_job(job_id, expected_version, principal) -> JobReceipt
```

`IngestReceipt` 区分 `accepted`、`duplicate`、`ignored_by_policy`，包含服务端事件 ID、可选任务 ID 和当前状态。`accepted` 只表示事件与任务已可靠持久化，不表示有候选、更不表示 Persona 已改变。

只有写入成功才能返回 accepted。格式错误、同一幂等键对应不同内容、未授权、超过预算分别返回明确错误；失败不会被记录成“模型认为不值得学习”。

### 5.2 首版入口

| 入口 | 作用 |
| --- | --- |
| `ai-persona learning ingest --connection <id>`，stdin 接收标准事件 | 平台无关本地入口，不要求 Studio 在线 |
| `ai-persona learning capture --adapter codex --connection <id>` | Codex 原生事件薄包装，转换后调用上述应用服务 |
| `POST /api/learning/v1/events` | 接收标准事件，成功入队返回 202；重复接收可返回 200 |
| `GET /api/learning/v1/events/{id}` | 查询接收、分析、观察、送审状态 |
| `POST /api/learning/v1/events/{id}/context` | 上传符合边界的规范化上下文快照 |
| MCP `ingest_conversation_event`、`get_conversation_learning_status` | 与 HTTP 共享核心；不提供批准或发布工具 |

首版优先完成本地 CLI 及 Studio 状态页。HTTP／MCP 使用同一契约，不能把业务逻辑只实现在某种入口中。远程 Webhook 的签名校验和网络部署属于未来接入适配器，不通过关闭现有 localhost 限制来实现。

入队调用不调用 LLM，不启动昂贵的历史扫描，不等待知识整理完成。标准 CLI 可输出机器可读回执；Codex Hook 包装器必须截获回执，不直接转发到 Hook stdout。

### 5.3 后台 Worker

采用独立的、每个 Persona 工作区单实例的 Learning Worker，持久队列使用 `conversation-learning.sqlite3`。默认放在机器本地应用状态目录，按解析后的数据目录路径摘要隔离，不同 checkout 不共享 Worker；仅在确认工作区不受云同步或网络文件系统影响时，才允许配置到 `persona-state/`。不将活动 SQLite 数据库及其日志当作 iCloud 等文件同步的跨设备队列。Studio 仅负责设置、状态和审核入口，关闭网页不影响已入队任务。

Worker 与 Pi 模型服务是两种职责：前者调度学习任务，后者执行模型调用。由用户显式启动／停止后台，默认不启动、不创建开机守护进程。停止后台等待当前任务完成；需要阻止当前任务送审时应取消任务或关闭模型分析。

首版使用 SQLite 事务写入事件与任务，并通过 job lease、心跳及 fencing token 防止旧 Worker 的迟到结果覆盖新一轮。每个会话串行处理，可跨会话有限并发；不在调用 LLM 期间持有数据库事务或审核文件锁。

Hook 接收失败时不阻塞用户对话，但必须在本地诊断或采集状态中留下安全错误。磁盘满等无法持久化的情况不能承诺零丢失。可恢复来源由适配器补采；不具备补采能力时显示明确的覆盖缺口。

任务状态与观察状态分开：任务为 queued、running、waiting_context、paused_budget、retryable_failed、failed、completed 或 cancelled；completed 另附 ignored／observed／submitted_review 等业务结果。进程重启只恢复可重试任务；缺少上下文、预算耗尽和语义不确定不作为无限重试理由。首版不支持多台设备并发写同一 Persona，云盘同步也不替代单写者约束。

严格模式中的未确认输入来源另有 waiting_origin，已信任来源不经过逐条来源确认；设置暂停另有 paused。首版由连接器保证消息修改事件按发生顺序提交，服务端不比较不透明 revision 的大小；迟到的 submitted 和撤回后的重新激活被拒绝。任意乱序修改的上游补采与重排属于适配层后续扩展，不宣称已实现。

## 6. 业务流程与 Observation

### 6.1 阶段 A：接收与安全筛选

认证、采集范围授权（限定模式校验项目／会话 allowlist）、内容大小限制、敏感字段过滤、事件幂等校验在模型调用前完成。先处理修改／撤回等生命周期事件；对普通提交事件，去掉确定的自动生成输入和无内容输入，但不能仅因“句子短”就忽略纠正与反馈。

原始事件短期入队不等于已经创建 Observation。即使模型最终忽略该输入，也保留不含原文的最小处理回执，便于用户判断是否漏采。

### 6.2 阶段 B：轻量信号识别

输入当前用户消息和有预算的最近上下文，使用配置的快速模型。结构化输出为：

- `ignore`：没有需要进一步处理的信号，附简短原因代码。
- `observe`：提取一个或多个观察信号，附消息引用及初步适用范围。
- `needs_context`：说明缺少哪个指代／评价对象，提交受限的补读请求。

识别器必须覆盖具体行为要求、修改意见、note 请求和知识讲解请求，不能只寻找不满情绪或“以后”等长期性用词。一次明确要求即可进入候选规划；知识请求不等待 AI 回答完成，也不从回答中扩张用户关注的知识范围。

`needs_context` 是工作状态，不直接创建一个“用户有某偏好”的事实。补读后仍无法判断时进入等待状态；不会自动打断当前 Codex 对话追问。

### 6.3 Observation 数据

| 字段组 | 内容 |
| --- | --- |
| 身份 | observation_id、来源事件、提取版本、状态和乐观锁版本 |
| 信号 | behavior_requirement、correction、positive_feedback、negative_feedback、explicit_statement、note_request、knowledge_explanation_request |
| 内容 | 原子化陈述、候选对象类型、相关概念及场景 |
| 处理来源 | 来源事件和任务 ID；正文与必要上下文仅在临时队列中保存，不提取原话证据或片段定位 |
| 边界 | 适用场景、明确的一次性例外、原话还是推断；长期性可记录未知，不作为必填送审依据 |
| 不确定性 | 对象与含义是否明确、事实核验状态；不以高置信度作为统一送审门槛 |
| 关联 | 相关正式记录、既有观察、待审核候选、拒绝记录、学习批次 |

状态为 `new`、`aggregated`、`waiting_context`、`waiting_origin`、`proposed`、`dismissed`、`superseded`；到期后清除临时观察。其中 proposed 表示已经关联送审结果，不表示获批。审核结果从 Proposal 读取，避免维护第二套审批状态。

已有明确对象和含义的观察可直接规划送审，不要求停留到积累多次反馈。关系建议由新增知识候选派生，关联其学习批次及来源观察，不要求再发现一条用户明确陈述关系的 Observation。

来源重复、Hook 重试、聊天导出重导、分叉会话复制出来的相同输入，都不能被算作多次独立反馈。首版以单次明确输入提案，不依赖重复次数晋级；不实现跨会话重复模式计数。

### 6.4 阶段 C：检索与候选规划

1. 根据观察召回少量相关正式知识、关系、偏好和场景。
2. 检查同类未审核候选、历史观察及用户明确选择的拒绝原因。
3. 对可能更新或复用的对象读取完整当前记录及 revision。
4. 按第 7 节边界生成知识与偏好候选；针对新增知识检索现有知识，补充关系候选。模型输出当前学习批次的完整候选集合，或 merge／wait／ignore；不得把整条长期聊天重新生成一遍。
5. 程序验证类型、引用、按候选类型要求的来源关联、场景范围、个人状态依据、图约束及 Persona 版本；不要求 AI 推断关系具有用户原话断言。
6. 非空且没有阻塞性歧义的候选自动送审；不需要人工先确认观察或草稿。

对象或含义不清楚的观察可以暂存，不应阻塞同一批中其他明确候选。缺失端点的关系暂不提交，但不阻塞独立成立的知识候选；同批包含完整端点依赖时，可将知识与关系一起送审、分别审核。

## 7. 三类候选的判断边界

触发后积极提出候选，不提前替用户决定是否值得长期保存。系统主要负责避免误解、重复和扩大推断，最终取舍交给审核。三类候选使用不同判断标准，不共用“必须多次出现、明确长期有效或高置信度”的送审门槛。

### 7.1 偏好候选

#### 触发条件

用户对 AI 的表达方式、内容组织、呈现形式或工作方式提出具体要求、纠正或修改意见，即可生成偏好 proposal。不满与修改意见是重点信号，但不要求出现负面情绪、“以后”“始终”等词，也不要求重复多次；一次明确要求就可以成为待审核偏好。

| 用户提示词 | 偏好候选 | 适用场景 |
| --- | --- | --- |
| “note 中不要有不必要的换行” | 避免无意义的断行 | note 编写 |
| “每个符号在第一次出现的时候要给出定义” | 符号首次出现时说明其含义 | 当前上下文对应的公式讲解或笔记场景 |
| “图里的元素不要重叠” | 图中元素布局应避免重叠 | 绘图 |
| “不要直接跳到结论，把推导写出来” | 保留必要的推导过程 | 知识讲解 |

#### 判断边界

- 提取具体期望，不把情绪本身保存为偏好。
- 根据当前任务确定场景，不默认扩大成全局偏好；项目设计决策也不能直接泛化为全局工作方式。
- 可以将“这张图的元素不要重叠”归纳成绘图场景的布局要求，不因指向当前产物就一律判为一次性要求。
- 不把具体内容修改当作行为偏好，例如“把这里的 5 改成 6”；知识定义纠正应按知识更新处理。
- 明确限定为一次性例外的要求，默认不提长期偏好，例如“这次为了放进一页，先省略推导”。
- 已有相同偏好时不重复新增；存在补充或变化时提出更新 proposal。
- 需要新场景时，可生成 Preference Context 与 Preference 的依赖组；不能因场景不存在就改成 global。

“太乱了”“不对”等无法确定修改方向的反馈可以进入观察，但不凭空猜出一条具体偏好。只有“谢谢”“很好”而没有明确评价对象和可提取要求时，也不生成具体规则。

### 7.2 新增知识候选

#### 触发条件

用户明确要求生成、整理或补充某个知识主题的 note，或要求解释、讲解、帮助理解某个知识点，即可对用户关注的知识点提出新增 proposal。不要求先证明用户已经学会，也不需要等待 AI 完整生成回答。

#### 知识点识别原则

以用户提示词表达的学习、解释或整理对象为主要依据。

| 用户提示词或上下文 | 可以提出的知识候选 |
| --- | --- |
| “帮我生成一份关于 X 的 note” | X |
| “详细解释一下 X” | X |
| “讲讲 X 和 Y 的区别” | X、Y，分别检查是否已存在 |
| “你刚才提到的 X，再展开讲讲” | X，因为用户明确选择了它 |
| AI 在解释 X 时自行引入 Y、Z | 不因它们仅出现在 AI 回答中就新增 Y、Z |

必要上下文用于消解“这个概念”“第二个方法”等指代，不能成为任意扩充知识点的来源。AI 曾经介绍某个概念并不等于用户学习了它；用户后续明确选中该概念提问时，才按这次用户输入识别。

#### 判断边界

- 候选表达的是“用户主动关注了这个知识主题”，不是“用户已掌握这个知识”。
- 不自动推断知识水平或长期兴趣；新知识的相关字段默认 unspecified。
- 不从 AI 回答中批量抽取用户没有主动关注的知识点。
- 用户仅引用、粘贴或顺带提到一个术语，不等于要求学习它。
- 生成 note 但没有明确知识对象时，不为凑候选而发明主题；依赖指代的请求先用必要上下文定位。
- 先检查现有知识及别名；已有节点直接复用，不重复新增。用户明确纠正现有知识时，仍可提出更新 proposal。
- 知识候选不要求先创建 Material；用户请求 note 不等于 note 已经生成、保存或被用户学习，不能凭空创建材料及其关联。
- 首版不自动上网核验事实，不编造来源，也不把研究猜想和项目假设写成确定性事实；这些约束不构成“必须证明用户掌握或知识已核验才能新增主题”的门槛。

知识点是否值得进入 Persona，由用户审核。

### 7.3 关系候选

#### 触发条件

形成新增知识候选后，自动检索现有知识库，提出新知识与已有知识之间可能存在的关系。关系可以由 AI 推断，不要求用户在提示词中明确说出这条关系。

#### proposal 展示

展示“知识点 A — 关系类型 → 知识点 B”，附一句简短备注，例如“由新增知识与现有知识匹配生成”。不要求展开关系说明、推荐理由、原始证据或置信度，也不增加额外确认步骤；用户直接审核关系是否正确。

#### 判断边界

- 使用项目已有的关系类型及图约束，不临时发明新边类型。
- 不重复提出已经存在的相同关系。
- 不因两个概念仅仅共同出现就机械地建立关系；模型依据检索到的知识内容判断可能的连接，但不要求输出判断说明。
- 没有合适关系时，可以不生成关系 proposal，不为每个新知识强行配关系。
- 新知识与关联关系可以同组提交，但允许分别审核；接受知识不等于接受全部关联关系。
- 依赖新增知识的关系，必须在相关知识获批后才能生效。新端点通过 client_ref 引用，已有端点核对身份和版本。

系统内部保留学习批次和任务关联，便于定位处理状态；不为追溯而长期保存原始聊天，不把 AI 推断伪装成用户原话。

### 7.4 共通规则

用户输入 → 必要上下文识别 → 去重与结构校验 → 自动进入待审核区 → 用户决定是否写入 Persona。

- 不设置“必须多次出现”“必须明确长期有效”“必须高置信度”的统一送审门槛。
- 信息足以构造一个明确候选，就可以送审；对象或含义尚不清楚时保留观察，不新增草稿确认关卡。
- 来源权限、身份、引用、版本及依赖等程序校验仍然执行；积极提案不等于自动写入正式 Persona。
- 三类候选统一附一句简短备注，不附原始证据。内部仅保留任务关联与去重信息，临时分析上下文按保留策略清理。
- 同一输入重试不能反复生成候选；用户拒绝后，没有新信息时不得反复推荐。

## 8. 简短备注与临时上下文

### 8.1 不创建原始证据

偏好、知识和关系 proposal 均使用不超过 300 字符的简短备注。备注概括触发原因或拟议变更，不要求复制用户原话、聊天摘录、行号、片段偏移、原始证据或推理过程。

例如：偏好备注“根据用户对笔记排版的修改要求”；知识备注“用户请求生成该主题的 note”；关系备注“由新增知识与现有知识匹配生成”。

不创建 conversation Source Bundle，不创建 Evidence，不向候选增加 evidence_refs／evidence_candidates，不新增证据审批或发布事务。材料整理等现有功能的原文证据机制不受此次简化影响。

### 8.2 候选与任务关联

conversation 提案上下文仅关联 learning_batch_id；ChangeSet 使用 producer_ref 标明任务归属。简短备注复用 Proposal.reason 展示为“备注”，不要求模型输出置信度。对话候选的 confidence 为 null，旧类型的校验与展示保持兼容。

观察正文、当前输入和必要上下文保存在本机临时队列，供分析、消解指代与失败恢复使用；它们不是正式记忆，也不随候选获批进入 Persona。任务 ID 与处理状态可以保留用于幂等和定位，不以原文长期可用为前提。

### 8.3 修改、撤回与保留

消息改动形成新事件版本。收到修改或撤回时，停止旧任务并将相关尚未审核的候选标记失效；已批准的 Persona 不静默改写，需由用户主动维护。

默认无观察事件的临时正文保留 7 天，观察及关联恢复上下文保留 30 天，均可配置。任务完成送审后也执行临时数据清理；待审候选及已发布记录保留简短备注，不依赖原始聊天。日志仅记录安全状态码。

暂停、退出学习与清理数据是不同操作。清理临时上下文不删除已提交的 proposal 或已发布 Persona；当前运行中的任务不在清理过程中被删除。过期且原文已清理的任务不能直接重跑，需要提交新的输入。

## 9. 幂等、并发与审核组

### 9.1 三层去重

1. 事件去重：来源实例 + 稳定事件 ID，同键异内容报冲突。消息版本另建唯一键，防止不同传输重复导入同一版本。
2. 观察去重：来源事件／消息版本 + 信号标识。提取器升级可生成新的分析版本，不把同一输入计数两次。
3. 候选去重：目标对象、场景、拟变更字段及语义内容，对照正式记录和待审核记录。文本 hash 只做确定性辅助，不替代语义查重。

不同来源的近义陈述可以关联任务，但不要仅因语义相似就删除输入。重新运行学习任务不得绕过用户已作出的拒绝决定。

### 9.2 学习批次与归属

LearningBatch 是一个有限、可追踪的候选生成单元，保存成员观察、生成版本、Persona 基线、输出快照及 ChangeSet ID。会话只是来源，不等于一份永远可覆盖的 ChangeSet。

- 同一批次重试或精炼，复用稳定 ChangeSet ID；每次提交当前批次完整候选快照。
- 已有人工批准、拒绝、暂缓或失效的组冻结，禁止后台覆盖。
- 后续出现真正的新信息时，新建只包含增量内容的批次；生成期间发生人工决定时，也不能自动把整组复制一份绕过保护。
- 来自不同会话、指向同一偏好的观察可以在后续扩展中合并，但需先检查重复输入及来源权限。跨平台聚合不在本地首版默认开启。

现有 assistant_session_id 仅表示维护助手会话。建议增加可选、类型化的 `producer_ref={kind: "assistant_session" | "conversation_learning", id: ...}`，保留旧字段兼容读取；两者同时存在时必须一致。送审服务按 producer_ref 检查归属，不让学习任务借用虚假的 ai_ 会话 ID。

### 9.3 崩溃恢复

队列数据库和 Proposal 文件之间不能假装存在单个数据库事务。送审前持久化批次 ID、内容幂等键和状态；复用并扩展提案恢复日志。恢复时按幂等键查找已生成的 ChangeSet，修复关联，不再创建第二组。

输入 hash、模型路由签名、提示词版本和 Persona 基线绑定每阶段检查点。来源或目标改变则重新分析受影响阶段；只有 Persona 改变时，可复用来源识别结果但重新检索与规划。

LLM 超时或进程退出不等于供应商未计费。输出已经保存时不重复请求；结果未知时采用有预算的重试策略，不宣称模型推理 exactly-once。提交文件失败只重试送审，不重新调用模型。

## 10. 模型接口、提示词契约与预算

继续使用现有 `ModelClient → model_runtime → Pi`，不另建供应商适配层，不读取或复用 Codex 的登录凭据。

拟增加两个业务任务 ID：

- `conversation_signal`：轻量识别与补读决策。
- `conversation_candidate`：相关 Persona 匹配后的候选规划。

在模型设置页独立选择模型／连接；不硬编码某个型号。已有连接及 activation、maintenance、material 配置保持不变。学习总开关默认关闭，启用时确认调用的连接、外发内容范围和预算。

提示词分三层：固定系统规则、严格输出 Schema、作为不可信数据的消息及记录。以下是设计约束，不是最终逐字 Prompt：

| 阶段 | 输入 | 输出 | 核心限制 |
| --- | --- | --- | --- |
| 信号识别 | 当前消息、最小上下文、允许类型 | ignore／observe／needs_context，原子信号及消息引用 | 不下最终事实结论，不调用提案写入 |
| 候选规划 | 当前用户请求、Observation、召回记录及版本、相关待审与拒绝原因 | 当前批次候选集合、每条简短备注、待补充项 | 不发明 ID，不扩大场景，不输出原始证据，不覆盖已审核决定 |

识别与规划提示词必须包含第 7 节的三类边界及正反例：一次具体行为要求即可提出偏好；note／讲解请求按用户选中的主题提出知识；为新增知识建议关联现有知识。候选输出使用 note（简短备注），不要求 explanation、rationale、confidence 或 evidence；候选 Schema 与提交校验都明确禁止原始证据输入。

建议首版默认预算，均为设计值而非性能实测：

- 标准入队事件最大 256 KiB；大记录由适配器分页成受控上下文，不能无声截断用户陈述。
- 信号识别输入最多 12,000 字符，单次输出最多 1,500 tokens；必要上下文最多补读一次。
- 候选阶段输入最多 40,000 字符，输出最多 6,000 tokens；最多一次补读后重试规划。
- 每批最多 10 条变更；首版超限拒绝，由模型优先保留独立知识／偏好，不能截断关系端点。自动拆分是后续扩展。
- 学习 Worker 串行；Pi 服务原有总并发上限为 2。前台优先为后续调度目标，首版不实现严格抢占。
- 配置每日模型调用／token 上限，超额进入 paused_budget，不悄悄切换模型或扩大预算。

不设置统一的模型置信度送审阈值，也不要求关系输出置信度。送审执行来源身份、信号与候选类型关联、范围、字段、依赖及版本校验；关系是否正确、候选是否值得长期保存交给用户审核。每日额度按逻辑模型调用预留，Pi 内部重试与用户已启用的备用连接可能增加供应商实际请求数，因此不是账单硬上限。

## 11. Codex 适配器：首个实现

本节仅约束 Codex 适配器，不要求其他平台实现 Hook、turn_id 或 transcript_path。

### 11.1 已核实的宿主约束

`UserPromptSubmit` 提供 prompt、turn_id 及通用会话信息；普通 stdout 会进入开发者上下文。transcript_path 可缺失，记录格式不是稳定接口。命令 Hook 默认同步，后台 Hook 可能随会话结束取消；MCP Hook 同步使用已连接的服务。非托管 Hook 需要用户审核信任。[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)

本机 CLI 在设计时为 0.149.0，features 检查显示 hooks 启用；这不证明桌面端已加载某个 Hook，也不替代运行时验收。这是初始设计时的环境记录。后续统一入口实现和本机迁移见[偏好应用设计](AI_PERSONA_PREFERENCE_ACTIVATION_DESIGN.zh-CN.md)，新命令仍需要宿主信任后验收。

### 11.2 字段映射与身份

| Codex 数据 | 标准化结果 |
| --- | --- |
| session_id | 来源命名空间中的 conversation_id |
| turn_id | 适配器事件身份材料；不直接假定等于消息 ID |
| prompt | 当前消息 text |
| cwd | 限定模式匹配允许项目；全局模式保留匹配范围或生成路径摘要范围；核心只接收 scope_ref，不据此自动读取目录 |
| transcript_path | 适配器私有 ContextHandle，核心只得到 opaque context.ref |
| hook_event_name | 映射标准事件类型，原生名字留在适配器诊断信息 |

统一入口使用来源、session、turn、规范化工作目录及原始提示形成身份，映射随标准事件持久保存，第一次接收的采集边界保持冻结；无背景时同样可以识别同一事件重传。相同 turn 内可能存在追加输入，不能单用 session_id + turn_id 覆盖所有提示；也不能仅凭文本 hash 把用户两次相同输入合并。

若宿主不提供可靠的发生序号，则保存采集序列并标明身份强度；不能承诺无歧义地区分原生重传和真正重复输入。自动续跑指令、任务转发等输入必须与主动用户消息区分；没有可靠元数据时标 unknown，不让 LLM 猜成人类来源。

### 11.3 推荐接入路径

1. 用户在 Studio 选择目标 Persona，并选择「仅指定项目／会话」或「所有本机 Codex 会话」；可对自己的接入开启「信任来源」，跳过逐条来源确认。来源及学习开关仍需单独启用。全局模式不要求将 `/` 设为允许项目，也不扩大会话记录读取目录。
2. Studio／CLI 生成薄命令 Hook 片段，由用户合并到已有配置并按宿主流程审核信任；首版不自动安装，也不覆盖整个配置文件。
3. 统一 Hook 接收 stdin，验证来源和两项独立开关，一次捕获正文与必要背景；独立学习子进程调用本地应用服务持久入队，主流程不等待入队结束。
4. 学习采集分支不运行 LLM，不输出观察正文或回执到 stdout；若偏好应用开启，统一入口同时执行有截止时间的场景判断，只返回成功准备的偏好 additionalContext。学习入队自身保留 3 秒保护，两个业务分支互不依赖成功。
5. Learning Worker 独立处理，Studio 显示结果；学习失败不会阻断正常 Codex 任务。

优先选择短命令 Hook + 本地队列，避免依赖 Studio 或 MCP 连接恰好在线。未来可替换成 MCP 入队 Hook，但业务服务与事件协议不变。包装器的正常路径、错误路径和标准输出隔离都要独立测试。

用户级 Hook 的加载范围与 Persona 来源的采集范围是两层配置：前者由宿主安装与信任控制，后者由此来源的 `scope_mode` 控制。切换同一来源的采集模式不改变 Hook 命令，也不会代装用户级 Hook。全局只覆盖本机当前用户已加载该 Hook 的会话新输入，不回扫历史或自动扩展到远程、云端及其他账号。全局接收未登记项目时保留不透明 cwd 摘要范围，避免之后切回限定模式时，已入队消息因 scope 缺失而意外落入旧兼容回退。

### 11.4 上下文读取与降级

Codex 记录解析器限制在单独模块，版本化支持识别过的记录格式，只提取许可的消息字段，不读取工具输出、隐藏推理或账号配置。

采集时保存最近必要消息的有界快照；首版 Codex 仅使用采集快照，不自动扩展读取整个会话。未来更远上下文读取器必须在已封存边界内补读。验证路径属于配置允许的会话记录根目录，拒绝路径穿越、符号链接和跨会话读取。核心不能接受任意客户端传来的 transcript_path 并代读。

找不到记录、格式变化、文件截断、无法证明边界或 origin 时，暂存当前输入及缺失标记。自包含且通过来源策略（已验证人工来源、单条确认或用户显式信任来源）的明确陈述可继续；含指代的纠正／反馈不能靠猜测送审，来源信任不能填补上下文缺口。额外 Stop 事件可作为未来补充采集，不是首版必要依赖，也不能让后来的回答污染当前输入的分析窗口。

## 12. Studio 与人工审核体验

增加“对话学习”入口，和主动自然语言维护、材料整理区分：

- 设置：总开关、来源连接、信任来源／严格模式、采集范围、允许项目／会话、学习类型、模型、外发范围、预算及保留期限。全局模式灰显但保留范围列表，显示可能扩大模型外发内容的提示；会话读取目录仍可独立配置。来源列表展示信任状态，保存信任设置会说明恢复任务数量与可能的模型消耗。
- 接入健康：已配置、等待宿主信任、最近接收、Worker 状态、缺失上下文及解析器不兼容。
- 处理列表：已接收、分析中、忽略、等待上下文／输入来源确认、已送审、失败、预算暂停。接收成功不能显示成学习成功。
- 观察详情：原话、必要前文、触发类型、范围、不确定性及相关已有记录；不要求长期性理由，不设必须点击的“确认观察”。
- 知识／偏好审核卡片：候选 diff、简短备注、与现有记录冲突、依赖和返回学习入口；不附原始证据。
- 关系审核卡片：两个知识点、关系类型和方向、简短备注及必要的依赖状态；不要求展开说明或置信度。用户可分别接受知识、拒绝其关系建议。

拒绝原因可选“仅本次适用”“范围过大”“理解错误”“内容不正确”“不希望学习此类信息”。记录其作用范围；普通拒绝不自动变成永久屏蔽规则。用户明确选择屏蔽时保存学习策略，不把策略本身写成行为偏好。

首版不向 Codex 自动追加澄清问题或通知。等待项集中在 Studio，避免每次聊天被学习流程打断。已批准 Persona 如何被宿主读取和应用，继续由独立的场景激活／上下文读取流程负责。

## 13. 安全、隐私与权限

1. 默认 opt-in；采集端和核心都执行范围限制，范围变化时在补读、模型外发及送审前重新检查。
2. 来源连接绑定目标 Persona、可信采集身份及能力。首版 HTTP 仅限本机；未来远程 HTTP 必须补充来源级认证与限流，现有 X-AI-Persona 头不是远程身份凭据。
3. 本地进程属于同一用户的信任边界；不能把本地权限控制宣传为抵御同账号恶意进程的隔离。
4. 模型仅接收被授权的消息片段及相关 Persona；不发送整段历史、凭据或平台日志路径。不保存供审核使用的原始证据。
5. 消息、引文、代码块、网页和 AI 回答始终是待分析数据，不能修改学习器指令、权限或输出 Schema。
6. 上下文只通过受控适配器读取；导出／远程输入不能让服务读取任意文件或下载任意 URL。
7. 队列、观察与快照目录按私人数据保护，日志只记录安全元数据。首版不宣称已实现对话内容加密；模型凭据仍使用既有独立存储。
8. 尚未审核的信息不会进入正常 Persona 检索、激活判断或当前 Codex 上下文。

## 14. 模块与数据落点建议

首版模块如下，后续可按规模调整，但依赖方向必须保持：

```text
src/ai_persona/conversation_learning/
  contracts.py       # 标准事件、上下文、Observation、批次与能力
  service.py         # 平台无关应用服务
  repository.py      # 接收去重、队列、观察、批次与版本
  worker.py          # 调度、租约、预算及恢复
  pipeline.py        # 识别、补读、聚合、检索与规划
  cli.py             # CLI 薄入口与 Hook 配置生成
  web.py             # 本机 HTTP／Studio 薄入口；MCP 挂载在既有 mcp_server.py
  adapters/
    base.py          # 来源与 ContextProvider 协议
    codex.py         # Codex Hook 标准化
    codex_context.py # Codex 记录解析与边界验证
```

本地首版将事件、消息版本、临时上下文、任务状态与阶段检查点合并到 events 表，并使用 connections、observations、model_calls、diagnostics 及 config 表。每个事件对应有限学习批次，审核状态从已有 ChangeSet／Proposal 读取，不新增 observation_evidence 或聊天 Source 表。

对现有文件的实施改动应限于：模型任务配置、公共候选构造／校验、conversation 提案标识、通用 producer_ref、简短备注展示和 CLI／Studio 挂载。不得复制一整份 ai_service.py 后只把名称改成 Codex。

旧会话和 ChangeSet 保持可读；新增字段默认空并检查冲突。先完成读取兼容与可恢复写入，再生成新格式；旧版本程序不支持新来源上下文时应明确拒绝，而非忽略验证。迁移前备份，不能让旧版服务与新版 Worker 混写同一工作区。

## 15. 验收标准

| 类别 | 必须覆盖的场景 |
| --- | --- |
| 平台可替换 | Codex 适配器与无文件路径、无 turn_id 的模拟平台输入，使用同一 pipeline 产出等价业务结果；核心不导入 Codex 模块 |
| 能力降级 | 无上下文、无回复链接、弱身份、未知 origin，状态与策略正确，不伪造完整性 |
| 来源信任 | 新旧配置默认严格；开启后跨平台复用且不改真实 origin；范围内待确认任务复用检查点恢复；已知自动消息被过滤；不扩大采集／模型权限、不绕过预算与最终审核；在途撤销信任能阻止送审 |
| 接收可靠性 | 重传、同键异内容、乱序、同一轮多次输入、真正重复文本、DB 锁和磁盘写失败 |
| 边界一致性 | 后续回答、会话分叉、压缩摘要、文件修改不能替换或越过当前用户输入的上下文边界 |
| 偏好边界 | 无“以后”的换行、符号定义和图中防重叠要求均可一次触发；具体数值修改、明确一次性例外及无对象的情绪反馈不被误写成长期规则 |
| 知识边界 | note／讲解请求按用户选中的知识点提案，无需等待回答或证明掌握；上下文只消解指代，AI 自行引入的知识不扩张候选，已有节点及别名不重复新增 |
| 关系边界 | 新知识触发与已有知识的关联建议，无用户关系断言、说明或置信度仍可送审；无适合关系可返回空，卡片展示端点与类型／方向，端点未获批时关系不生效 |
| 候选质量 | 已有知识纠正、新场景依赖及三类候选结构合法；重复、错误 ID、缺失规定来源关联和过宽范围被拦截，不以多次出现、长期性或高置信度统一筛掉候选 |
| 审核保护 | 生成期间人工决定、批次部分获批、已有拒绝、同组替换和旧审核页面，不覆盖或绕过人审 |
| 恢复 | 识别后崩溃、模型超时、送审文件中断、关联写入丢失、重启及预算暂停；送审重试不调用模型 |
| 隐私 | 禁用来源、排除项目、撤回消息、数据清理、跨来源权限、恶意路径、敏感信息及提示词注入 |
| 全局采集 | 默认及旧配置不扩大范围；全局接收其他项目／worktree／无项目会话，保留原列表但暂不用于过滤；切回限定模式阻止越界旧任务；文件读取、来源身份、开关和审核约束不变 |
| Codex 集成 | CLI 与用户实际使用的桌面端分别验收；Hook 信任、stdout 空输出、Studio 离线、Worker 重启和源格式变化 |
| 模型集成 | 两个新任务继续走 Pi 适配层，不读取 Codex 凭据；已有三种任务不回归 |
| 简短备注 | 三类 proposal 均有简短备注，无 Source／Evidence 新增、无聊天摘录、无置信度门槛；清理临时正文不影响候选审核和正式记录 |

自动化测试先使用隔离数据及本地模型替身。后续语义评测使用经授权的脱敏标注对话，统计观察漏检、候选误报、适用范围错误、重复率、用户修改量及接受率；接受率不替代事实正确性评估。第三方引文、泛泛赞扬、项目决策及自动消息仍需反例测试，候选不因缺少原始证据被计为格式错误。

性能目标为入队常态 P95 不高于 300ms（包含实际包装器开销），LLM 分析不计入 Hook 延迟。该数值须在实际主机验收；不达标时优化采集和持久化，而不是将模型调用藏在同步入口中。

## 16. 实施顺序与开通门槛

1. 契约与模拟平台：完成标准事件、能力矩阵、ContextProvider、去重和持久队列，先证明核心不依赖 Codex。
2. Codex 薄适配器：完成真实事件样本、身份映射、主动用户来源判定和上下文边界测试；此阶段只采集，不外发、不送审。
3. 识别与 Observation：接入配置模型，实现轻量识别、补读、观察聚合及状态页；保留零候选正常路径。
4. 候选与备注：接入相关记录检索、简短备注、类型与依赖校验；不创建原始证据。
5. 审核闭环：通用批次归属、自动送审、重试、历史保护与审核反馈；只对显式启用范围开放。
6. 稳定性与迁移：发布事务、中断恢复、数据保留、安全测试、安装／停用说明及旧功能回归。

开通前必须确认的技术事实：

- 用户实际使用的 Codex 桌面端与 CLI 是否触发同一事件协议；不能由 CLI features 结果推断桌面端行为。
- 该版本如何区分用户主动输入、自动续跑与任务转发；无法可靠区分时，保持 unknown 降级，不放宽核心的身份门槛。
- 原生事件重复与同轮追加如何区分，适配器是否能稳定建立事件身份和上下文边界。
- 临时上下文清理后，待审候选的简短备注、依赖和任务关联仍可用；批准操作不尝试读取已清理的聊天。

上述事项是实现验收门槛，不改变平台无关接口。若某个平台不能提供必要能力，可以只支持自包含输入或手动导入确认；新增平台的工作限于适配器、身份／上下文能力和安装方式。

## 17. 决策摘要

- 接收与模型分析解耦；Observation 自动产生，合格候选自动送审。

- 偏好优先从具体要求和修改意见发现，一次明确表达即可提案；知识主要从用户的 note／讲解请求识别，不批量采集 AI 回答中的知识点。
- 新知识自动触发关系建议，不要求说明或用户原话断言；三类候选均由用户审核决定是否保留。
- 首版实现新增知识、关系、偏好及必要的场景依赖，候选仅附简短备注；范围与版本校验保留，不创建原始证据。
- 更换来源或传输只更换边缘适配层；能力不足显式降级，不复制业务流程。
