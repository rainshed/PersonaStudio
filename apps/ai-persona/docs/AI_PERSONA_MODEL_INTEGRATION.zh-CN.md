# AI Persona 模型接入与 AI 维护

本文保留模型接入的详细行为，安装流程已更新为 PersonaStudio 仓库启动器；可用模型以固定版本适配器及实际账号权限为准。

## 1. 统一模型适配器

AI Persona 使用固定版本 `@earendil-works/pi-ai@0.85.1` 统一模型 SDK。适配层源自相关 Paper Radar 实现，但独立保存模型目录、连接配置、凭据、授权和任务路由；运行时不要求安装 Paper Radar。

调用链：

```text
Studio / MCP
    → Python PersonaAIService
    → ModelClient（本机认证连接）
    → Node Pi 模型服务
    → 用户选择的模型平台

模型维护结果 → 持久化与程序校验 → 自动进入待审核 ChangeSet → 人工审核发布
```

Python Studio 和 MCP 复用同一个本机 Pi 服务。三个业务任务使用固定流程，场景说明、触发条件与偏好本身仍来自用户可编辑并发布的正式记录，不生成固定 Skill 文件。

连接支持范围来自固定版本的 Pi 目录和项目适配配置：OpenAI API、ChatGPT/Codex 账号授权、Anthropic API、Google Gemini、DeepSeek、OpenRouter、Moonshot 国际／中国区域、Kimi For Coding，以及自定义兼容服务。账号授权仅在适配器声明支持时提供；订阅、API 额度及实际模型权限不能相互替代。

## 2. 启动与配置

在 PersonaStudio 仓库根目录执行：

```sh
./scripts/ai-persona models-install
./scripts/ai-persona start
```

- Node.js 要求 22.19 或更新版本，并包含 npm；可用 `AI_PERSONA_NODE` 与 `AI_PERSONA_NPM` 指定可执行文件。
- `models-install` 使用 Node 锁文件与 `npm ci --omit=dev --ignore-scripts` 安装依赖，采用临时目录校验后发布。
- 模型运行时保存在 `~/.cache/ai-persona/model-runtime/<版本摘要>`，遵循 `XDG_CACHE_HOME`。`AI_PERSONA_MODEL_RUNTIME_CACHE_DIR` 可改缓存根目录，`AI_PERSONA_MODEL_RUNTIME_DIR` 可指定精确安装位置。
- Python 包重新安装不会移除已外置的运行依赖或账号存储；代码变更后的运行时摘要不同，需要按诊断提示安装对应版本。
- 模型账号路径保持 `AI_PERSONA_MODEL_DATA_DIR` 或 `~/.local/share/ai-persona/models`。Demo 的账号位于独立 Demo 状态目录，不与真实工作区共用。
- 已运行的 Studio 需要停止后重启才能加载新代码。旧的全局安装与仓库启动器是不同入口，迁移时应明确停止旧入口启动的进程。
- 根启动器使用普通安装方式，以兼容不可靠的可编辑安装环境。缺少依赖时先运行 `./scripts/ai-persona doctor`，无需删除账号或重复授权。
- 页面入口：`/settings/models`。
- 保存连接不代表认证或调用成功。API Key 填写后保存；账号授权在保存后发起。
- Codex 账号授权：点击「账号授权」→选择「浏览器登录」或「设备码登录」→「继续授权」→打开页面提供的平台链接并自行登录。页面支持 Pi 的选择、文本、秘密输入和手动授权码步骤。
- 刷新／重新打开设置页会恢复当前未完成的授权；同一连接再次点击会继续已有流程。也可以在授权面板中取消，再为另一连接授权。授权状态只在本机模型服务内存中保留，超时或服务重启后需要重新开始；不会把授权码或凭据保存到浏览器存储中。
- 模型显示名称与 ID 仅大小写、空格或连接符不同的，界面只显示一次；不同的自定义连接名称仍保留，且不会合并或删除连接记录。
- 「测试」会发出真实模型请求，可能计入使用量。
- 「账号与连接」按账号、平台与接入方式保存一份凭据。内置平台添加账号时无需绑定一个任务模型；在「理解与生成」「快速判定」中分别选择账号连接和模型。更换模型不需要重复输入 API Key 或重新授权。
- 新配置使用 `routingVersion: 3`，默认模型及四项功能分别保存连接 ID 和模型 ID：`maintenance`（AI 维护助手）、`conversation_learning`（对话学习生成）、`conversation_signal`（对话学习判定）、`activation`（偏好场景判定）。选择「跟随默认模型」时同时继承默认账号和默认模型。
- 材料分析和图片识别的 `material` 阶段统一选用维护助手模型；`conversation_candidate` 选用对话学习生成模型，`conversation_signal` 独立选用判定模型。内部阶段仍保留各自的超时、断点、日志与预算。
- 旧加密存储继续保留原路由，页面展示合并建议及有差异的原配置，保存后再切换到四项功能。已保存的第二版配置会让两个学习选项沿用当前学习模型，避免启用曾被搁置的旧判定选择。原阶段选择作为兼容数据保留，账号凭据和连接版本不因合并而改变。
- 自定义兼容连接可声明 `imageModelIds`，一行一个支持图片输入的模型 ID。声明按具体模型生效，不会把同一接口的所有模型都视为视觉模型；实际图片请求会在进入提供方之前检查图片能力。
- 模型目录来自 Pi 适配器，不是账号实时权限清单。「测试连接（真实调用）」只检查选中的模型能否响应，记录其实际结果，不验证图片识别、工具调用或候选生成质量，也不代表同一账号下所有模型都可用。自定义服务可直接填写不同模型 ID，沿用该连接配置的容量上限。
- 备用模型可选同一账号下的另一个模型，也可以选择另一连接。不会重复调用与主配置完全相同的连接和模型。
- 旧版加密存储自动补齐选模字段，保留原凭据、连接 ID、模型与任务分配。已有多条连接不会按平台自动合并，避免混淆不同账号；后续任务可直接选用其中一个已认证连接下的多个模型。
- 变更平台、认证方式、服务地址或兼容协议会清除该连接的凭据及模型覆盖。移除凭据会影响此连接下所有模型，其他账号独立保存。
- 模型切换参与材料处理的配置指纹；不会因共用一个账号而错误命中旧模型的缓存。
- 备用连接默认关闭。开启意味着失败时可能把同一输入发送给另一服务并消耗其额度。
- 没有配置模型、凭据失效或服务不可用时返回明确错误；不会静默借用其他账号。

停止独立模型服务：

```bash
./scripts/ai-persona models-stop
```

Studio 退出会取消其运行中的 AI 草稿任务，但共享模型服务可以继续供 MCP 使用。下次调用时也会按需启动服务。

## 3. 偏好场景判定

### MCP 接口

工具名：`resolve_persona_activation`。

输入示例：

```json
{
  "user_prompt": "帮我把这段研究结果整理成论文中的讨论部分",
  "task_summary": "正在修改一篇论文",
  "recent_messages": [
    {"role": "user", "content": "先保留我的结论，再调整表述。"}
  ],
  "artifact_type": "paper"
}
```

`user_prompt` 必填，其余可选。最多 12 条近期用户／助手消息。消息和摘要有长度限制，不接受 system/tool 消息作为新增指令。

输出包括：

| 字段 | 含义 |
| --- | --- |
| `schema_version` | `ai-persona.activation/v1` |
| `persona_revision` | 判定使用的正式 Persona 版本 |
| `catalog_version` | 场景目录内容指纹 |
| `decision` | `match`、`no_match` 或 `uncertain` |
| `matched_contexts` | 确定匹配的场景 ID、key、名称、版本、简短理由 |
| `uncertain_contexts` | 无法充分确定的场景及理由 |
| `evaluated_context_count` | 实际覆盖的全部有效场景数 |
| `model_run` | 实际连接、模型与用量元数据，无完整偏好或模型原始正文 |

判定读取所有 active 场景的最新描述与 activation 条件，支持多场景命中、排除条件和不确定结果。服务检查模型是否逐一覆盖全部场景，以及是否伪造或重复 key。空目录直接返回无匹配，不调用模型。

“描述”定义场景在什么时候使用；“典型请求示例”提供用户希望触发的请求正例。为兼容已有记录，示例仍保存在 `activation.intents`。模型将示例作为语义参考，相近表达不必逐字命中；示例为空时仍可根据描述判断。示例与描述、排除条件无法协调时保留不确定性。

`prepare_persona_context` 和 `search_preferences` 不再根据示例的字符串包含关系自动触发场景。只读匹配保留显式 `context_key` 和结构化 `artifact_type`；自由文本无法由该路径确定场景时，返回先调用 `resolve_persona_activation` 的提示，不会隐式调用模型。全局偏好仍可正常返回。

失败不会伪装成 `no_match`。目录过大时明确报错，不静默漏掉部分场景。模型的语义质量仍取决于选定模型与场景描述；模拟服务测试只验证契约，不证明实际准确率。

### 判定之后

1. 调用者对每个命中的 `key` 调用已有 `prepare_persona_context`，显式传入 `context_key`。
2. 按记录 ID 去重，控制总上下文预算；全局偏好只保留一份。
3. 比较判定与读取结果的版本。场景或规则有变化时重新判定／读取。
4. 单条偏好的 `condition` 仍须由应用流程判断；场景命中不表示其中每条规则无条件适用。

这一工具提供可调用能力，**不会自行注册宿主 Hook、唤醒外部 Agent 或保证 Agent 调用 MCP**。宿主仍须在消息提交等入口调用它，并接续偏好读取流程。当前实现不向每轮对话自动注入完整偏好，也不创建固定 Skill。

### HTTP 与调试界面

同一业务接口可通过本机 `POST /api/ai/activation` 调用，JSON 输入同上；请求需携带 `Content-Type: application/json` 和 `X-AI-Persona: 1`。

Studio 的 AI 助手页底部提供场景判定测试面板。持久化人工标注测试集、批量回归指标与结果缓存尚未实现。

## 4. 自然语言维护

入口：侧栏「AI 维护助手」`/ai`；材料与记录详情统一链接到这个入口。首版采用“依据、维护对象、自然语言需求”三项输入；新任务使用共用维护循环，以下旧单材料／对话阶段保留供历史任务兼容。实际接口和容量见[统一设计第 17 节](AI_PERSONA_UNIFIED_MAINTENANCE_DESIGN.zh-CN.md#17-首版实现与验证2026-09-09)。

流程：

1. 用户说明希望新增、修改、归档、恢复或关联什么。只是询问时允许零变更回答。
2. 模型先读紧凑目录，再申请相关记录正文；服务最多提供 3 轮读取与生成。
3. 修改已有对象前必须读取其完整当前记录；同时提供已有关系，帮助复用记录、避免重复关联。
4. 输出带理由的候选草稿。服务校验字段、类型、对象引用、版本与依赖；不写正式数据。
5. 有非空候选且没有待澄清问题时，自动生成待审核 ChangeSet，无须先人工确认草稿。问题和零变更留在对话。
6. 用户可进入人工审核页，也可继续对话或展开可选字段编辑。新的完整候选更新同一组尚未审核的 ChangeSet；已有批准、拒绝、暂缓等决定则不能覆盖。下次模型调用仍收到编辑后的草稿。发布权限不交给模型。

新场景和依赖该场景的偏好可以同组提交：使用 `context_client_refs` 引用草稿项，服务分配正式候选 ID 并建立审核依赖。知识与关系同样通过 `source_ref`／`target_ref` 引用新候选。不允许模型猜测最终 ID。

草稿保存在当前 Persona 的 `persona-state/ai-assistant.sqlite3`，刷新或退出页面不会丢失。并发编辑使用草稿版本检测；正式 Persona 已变化时阻止直接提交，要求重新准备。提交使用内容幂等标识；生成失败、取消与进程中断不会直接发布。

内部草稿不是第二个审核关卡。送审失败进入 `submission_failed`，可通过原 `submit` 接口重试，不调用模型。更新保留旧候选历史，使用恢复日志处理文件写入中断。详见[直接进入待审核区](AI_PERSONA_DIRECT_REVIEW.zh-CN.md)。

## 5. 材料智能整理

首版是**手动、单份、已正式导入的 Material**。从材料详情进入「材料智能整理」，不自动分析刚导入的文件，也不直接扫描整个资料库。

- 只读取 Source Manifest 声明且 hash 校验通过的提取文本或文本原文。
- 向模型提供行号；页面显示实际读取行数和是否覆盖全文。
- 支持内容摘要、知识候选、材料—知识联系和知识间关系候选，优先复用已有概念。
- 生成摘要写入 `summary` 候选；不覆盖原始标题、`abstract`、书目信息或 Source。
- 材料中的知识／关系候选必须附实际读取范围内的证据，发布时由原有 Evidence 流程保存。
- 默认禁止修改掌握程度、兴趣、评价、阅读状态、个人笔记和偏好，连“清空已有个人状态”也不允许。
- 用户可以在开始前勾选个人状态／偏好候选，但仍要求明确依据与人工审核。不能把外部论文中的一句话伪装成人工确认或用户明确声明。
- 有效的来源引用继续使用已有 Source；AI 不创建或伪造源文件。

### 分阶段分析与失败后继续

详细设计见 [材料整理优化设计](AI_PERSONA_MATERIAL_ANALYSIS_OPTIMIZATION.zh-CN.md)。

- 带行号的短文本（≤12,000 字符）直接生成候选；较长文本先提取概念、主张、限定条件和原始行号证据，再检索相关记录并生成候选。
- 超过 60,000 字符按原始行号分段，最多 20 段。完成每段立即保存，不静默截去尾部。超过总预算或遇到超长单行时明确报错。
- 分析阶段不带 Persona 目录或数据库 Schema；候选阶段只带任务相关字段契约、相关记录和有预算的证据片段。仍可要求补读原文、记录或补充检索词（最多 3 轮候选生成）。
- 默认材料分析不会发送个人状态字段、正文备注或偏好记录。材料中模型抽取的主张不是独立证据，候选必须回看实际提供的原文片段。
- 分析、补读检查点和阶段运行信息保存在原草稿数据库。失败或取消后点击 **继续分析**，不会重复追加用户消息。新要求请正常发送消息，会启动新一轮分析。
- 继续时核对来源、模型配置和 Persona 版本。来源／模型／要求变化会使分析失效；只改变 Persona 时可复用材料理解，但重新匹配记录。已修改草稿仍会传入下一轮候选提示词。
- 页面显示完成的文本段和实际覆盖范围；阶段记录包含耗时及可观测的首内容事件，供应商不给出的用量不会显示为零。旧版本失败会话没有保存的中间结果无法追溯恢复，第一次继续需要重新分析。

HTTP：`POST /api/ai/sessions/{id}/resume`，JSON 为 `{"version": 当前草稿版本}`，同样需要本机限制与 `X-AI-Persona: 1`。只允许失败／取消分析；继续成功后有效候选自动进入待审核区，但不会自动发布。纯送审失败使用 `submit` 重试。

## 6. 安全、数据与运行约束

- 模型连接和凭据默认位于 `~/.local/share/ai-persona/models`，独立于 Persona、Paper Radar 和其他 CLI。
- 可用 `AI_PERSONA_MODEL_DATA_DIR` 指定另一存储；Studio 与 MCP 要共享连接时必须使用相同位置。`AI_PERSONA_NODE` 可指定 Node 可执行文件。
- 凭据使用 AES-256-GCM 本地文件加密，目录权限 0700，密钥／密文／运行描述文件 0600。密钥同机保存，不等于系统钥匙串，不能抵御已获得同一用户权限的攻击者；不要把整个模型目录同步或提交到版本库。
- 模型服务只监听随机 loopback 端口，以本机私有文件中的随机 Bearer token 认证，拒绝浏览器 Origin 和外来 Host。
- Studio AI API 限制本机客户端、同站请求与 JSON 自定义标头；它不是公网多用户服务。
- 供应商报错会被归一化，避免返回密钥或供应商回显的正文。
- 模型服务运行日志与每个草稿保留最近 100 条调用元数据，不记录提示词、流式正文或内部推理。AI 草稿数据库存储对话、候选和材料分析检查点，需要按个人数据保护和备份；删除草稿的产品入口尚未提供。
- 最多并行 2 个模型请求。场景判定 15 秒、连接测试 30 秒、自然语言维护和材料分析每次最多 420 秒（7 分钟）。逻辑请求（包含重试／显式备用连接）的总预算分别为 15／30／480／480 秒；多阶段材料的整个会话可长于 480 秒。只有完整且通过校验的分段结果才保存为检查点，未完成的流式内容不会宣称已保存。
- 仅尚未收到内容的短暂限流／连接错误可有限重试一次，超时不自动重跑同一请求。备用连接仍须手动启用，且共享该请求的总时间预算。取消与超时分别报告。
- Pi 的流式 start 事件不是首 token；首内容时间仅记录实际内容事件，不能用它确定供应商排队、网络或内部推理各自的耗时。进度显示阶段、耗时和本次等待上限。元数据分别记录首次思考、首次正文、最近事件、终止事件、事件数和字符数，不传输内部推理正文。首次思考事件不能当作首次正文，也不能用于判断模型已经完成。
- 取消会尝试中断模型请求；已经消耗的供应商用量不可撤回。迟到的结果不会覆盖已取消或已开启新一轮的草稿。
- 原文、场景说明和模型输出都作为数据，不成为执行任意工具或绕过审核的指令。

## 7. 测试与当前边界

```bash
PYTHONPATH=src .venv/bin/python -m pytest -q
cd src/ai_persona/model_runtime
```

### 订阅通道的输出预算

当前锁定的 Pi 0.85.1 Codex 订阅适配器不会发送 `max_output_tokens`。因此调用记录中的 `maxTokens` 是应用请求值，并非该订阅通道已经执行的硬上限；`providerOutputLimit` 为 `null` 表示未观察到发送的数值上限。服务端报告的输出 token 还可能包含思考用量。不能仅凭请求的 6,000 token 就预测耗时或宣称已限制生成量。SSE 和 WebSocket 的本地适配器验收均验证：收到正常完成事件即可返回，无须等待连接关闭。
