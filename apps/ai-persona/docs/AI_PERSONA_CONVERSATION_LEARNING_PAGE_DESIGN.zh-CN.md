## 2.0 实施规范（当前版本）

本节取代下方 1.0 中“详情抽屉”“列表内完整反馈表单”“只能跳转审核区”的交互约定。后续各节保留作为第一版设计和验收记录；业务边界仍然有效。

- 桌面采用左侧紧凑任务列表、右侧常驻详情；两侧独立滚动。列表只显示输入摘要、触发结果、反馈状态和审核进度，不再重复放置完整反馈表单。小屏显示单独列表或详情，支持返回与上一条／下一条。
- 默认只展示搜索和「全部／未反馈／已反馈」快捷筛选，来源、处理状态和详细反馈状态收在「更多筛选」。反馈完成后选中任务和当前行保留，不自动跳下一条。
- 详情按用户输入、可折叠上下文、触发反馈、候选内容、可折叠运行信息排列。候选可以原位通过、拒绝、编辑后通过；待审核区仍是跨来源的集中入口，不复制审核记录。
- 类型、默认值、枚举来自 `models.py`；可写权限来自持久化字段契约。`review_field_schema` 同时供原位审核和原有审核表单使用，不另建一份前端字段白名单。知识、偏好、关系、场景的全部业务属性均可查看，允许修改的属性可编辑；来源引用和系统元数据只读，已有关系的身份不能通过更新修改。
- 主属性常显，别名、标签、范围、正文备注等收在更多属性。掌握程度与兴趣独立分组，明确标记只能由用户设置。模型的调用阶段仍禁止推断这些个人属性。
- 前端只提交实际改动，保留未编辑的属性；空列表、空字符串、null 按各字段类型显式处理。后端校验完整合并后的记录，再走原有 `ProposalService` 发布。成功后以服务器读取的持久化值绘制，不用前端草稿冒充保存结果。
- 原始候选改动、审核改动、当前保存数据可折叠查看；未出现在原始 patch 的字段不会伪装成当时 AI 明确生成的值。
- `GET /api/learning/v1/events/{id}/review` 返回候选、属性定义、引用名称和审核依赖。`POST .../review/{proposal_id}` 只接受 action、revision、updates，校验任务归属、候选版本、字段和值；沿用本机访问与防跨站约束。未知属性和字段校验失败不会保存。
- 有依赖的候选按顺序审核；父候选未通过时子候选不能通过，拒绝父候选明确提示关联拒绝。两处共用同一版本与依赖规则，重复／过期请求拒绝。请求结果不确定时只读取最新状态，不自动重复写入。
- 触发反馈与内容审核完全独立。审核不自动添加或反转触发标签；已有明确反馈的样例才同步审核后的内容标准答案。撤回反馈不回滚 Persona。
- 编辑草稿和理由草稿留在页面内存，切换任务不丢失；后台读取不覆盖编辑。离开页面提示未保存；其他位置完成审核时提示冲突，不将旧草稿写回。已通过记录在学习页只读，后续编辑走正式记录入口。

验收使用隔离的虚构 Persona、模拟模型与任务队列，不修改真实任务或实际模型设置。覆盖字段保留、显式清空、字段报错、两处审核同步、依赖顺序、版本冲突、反馈撤回和桌面／窄屏交互。

## 1.0 历史设计与验收记录

## 1. 问题与设计目标

### 1.1 当前问题

1. 点击任务的“查看”后，详情显示在整个列表下方，并调用 `scrollIntoView`。任务越多，触发位置与详情距离越远。
2. 列表主要展示来源、处理状态和时间，不能直接辨认用户输入、触发判断或是否已经反馈。
3. 学习设置、来源配置、任务列表、任务详情纵向堆叠，低频配置挤占日常工作区域。
4. 任务详情的反馈组件没有取消入口。底层已有撤回能力，但用户必须离开任务页，到“反馈与测试样例”中寻找。
5. 当前列表轮询整体替换行节点；增加理由输入和就地反馈后，继续这样刷新会打断输入、丢失焦点。

### 1.2 改版后的目标

- 打开页面首先看到最近任务，常用配置不挡住列表。
- 不打开详情，也能辨认任务、看到本次判断及当前反馈状态。
- 点击任务不跳到页面底部；查看完后仍能定位原来的任务。
- 一次点击完成满意度反馈；改选或取消同样可以原地完成。
- 未完成判定、处理失败、已送审、已反馈各自表达，不相互冒充。
- 查看、展开、筛选、刷新都不创建样例、不调用模型、不改变后台运行状态。

### 1.3 非目标

本次不调整学习提示词，不改变何时触发学习，不增加反馈类型或人工标注字段，不在任务页建设第二套候选编辑／审核系统，不增加批量自动反馈，不自动优化提示词或运行回测，也不调整 Codex Hook 和其他来源适配器。

## 2. 页面信息架构

### 2.1 默认主视图

从上到下只保留：

1. **页头：** 标题“对话学习”、一句简短说明、“学习设置”和“前往待审核区”入口。
2. **紧凑状态栏：** 后台运行状态、单一启停按钮、采集／模型分析开关的状态摘要；仅在异常时显示简短告警。
3. **任务工作区：** 搜索与筛选、任务列表、分页。任务是页面主体。
4. **按需打开的详情抽屉：** 不参与页面纵向排列，不把详情追加在列表末尾。

正常状态下不常驻展开来源信任说明、预算表单、目录配置或 Hook JSON。警告与未完成配置需要可见，但不自动展开长表单。

### 2.2 学习设置区域

“学习设置”打开独立的设置面板，按“学习与预算”“来源连接”分组；选中一个来源后才展开它的表单，Hook 配置继续按需展开。关闭后回到原任务筛选、页码和滚动位置。

保留现有配置能力、权限提示和显式保存步骤。不因为打开设置、进入页面或关闭面板而启用采集、信任来源、允许模型外发或启动后台。任务抽屉和设置面板不叠加打开。

## 3. 任务列表

### 3.1 每条任务的信息层级

| 层级 | 展示内容 | 规则 |
| --- | --- | --- |
| 主标题 | 用户提示词摘要 | 展示一至两行，优先保留开头；不再以来源名称作为唯一识别信息 |
| 次要信息 | 来源、接收时间 | 长来源名截断；完整信息在详情中查看 |
| 处理状态 | 排队中、分析中、处理完成、失败等 | 沿用业务状态；“已送审”表示候选进度，不表示已反馈 |
| 判断结果 | “本次判断：触发学习／不触发学习” | 必须来自该次结果的有效布尔判定，不从是否有候选倒推 |
| 反馈状态 | 未反馈、满意、不满意 | 与处理状态分开显示；当前反馈选项持续高亮 |
| 操作 | 查看详情、满意、不满意；已反馈时显示取消反馈 | 有候选时另提供“审核候选”入口，不与反馈按钮混用 |

列表不展开观察记录、候选正文、模型调用信息和技术错误堆栈。触发判断旁以短提示明确“评价是否应该触发学习，不是评价生成内容”。

摘要仅从仍允许读取的输入派生，不调用模型生成标题，不因列表展示延长未反馈输入的保留期限。输入已清理时显示“输入内容已清理”，不能虚构标题或重新读取原平台聊天。用户明确反馈后保留于本地样例的快照可用于恢复展示，并注明来自样例快照。

### 3.2 搜索、筛选和分页

- 默认按接收时间倒序，每页 20 条；采用服务端分页，不把“显示最近 100 条”作为全部记录。
- 反馈筛选：“全部／未反馈／满意／不满意”，默认“全部”。“未反馈”仅包括已有可评价二元判定、但当前没有有效反馈的任务。
- 处理状态和来源作为独立筛选条件，不与反馈状态混合。搜索按仍可读取的用户输入及来源名称匹配，不搜索隐藏技术快照或不满意理由。
- 条件组合在全部可见记录上生效，而非先截断最近 100 条再筛选。筛选数量与列表使用相同口径。
- 首版不提供批量满意／不满意，不预先勾选任务，不用“全选通过”代替逐条人工反馈。
- 后台出现新任务时提示“有新任务，点击更新”，不直接插入列表顶端挤走当前行。
- 默认列表中提交反馈后任务留在原位。处于“未反馈”等筛选时，刚操作的行暂时保留并提示“状态已更新，刷新列表后移出”；用户刷新、翻页或改变筛选后再重算，不在填写理由时让任务消失。

### 3.3 点击边界

提示词标题和“查看详情”打开抽屉。行内反馈、取消反馈和审核入口各自处理点击，不通过事件冒泡意外打开／切换详情。列表行不整体伪装成一个包含其他按钮的大按钮。

## 4. 任务详情抽屉

### 4.1 展示形式

- 桌面端从右侧打开抽屉，建议宽度约 560–680 px；实际宽度受视口约束，内容独立滚动。
- 视口不足以保留有效列表空间时，切换为全屏详情面板，不强行压缩正文与按钮。
- 列表保持原来的滚动位置，选中任务保持高亮。不得再滚动主页面定位详情。
- 顶部固定显示“任务详情”、来源／时间和关闭按钮；关闭后恢复到触发按钮的焦点。
- 抽屉是单一模态区域；关闭后才能操作背景列表，不允许背景焦点穿透。可提供上一条／下一条，在当前筛选与排序内切换，边界按钮禁用。
- 切换时只更新抽屉内容并回到抽屉顶部，不滚动主页面。未保存理由的处理遵循第 7 节。

### 4.2 内容顺序

1. **本次判断与处理状态：** 分别展示触发／不触发，以及当前任务进度。
2. **用户输入：** 展示实际用于本次判断的输入。较长正文可展开；必要上下文放在独立折叠区，不默认展开完整聊天。
3. **简短说明与触发反馈：** 显示已有的判断／观察备注和共享反馈组件，不额外调用模型生成解释，不展示模型思维过程。
4. **候选概况：** 已生成的知识、偏好、关系数量及审核进度；“进入待审核区”沿用原页面。
5. **运行与来源信息：** 来源确认依据、错误、重试／取消任务等低频内容。技术标识、版本等放入折叠区。

没有候选时明确显示“本次未生成候选”，但不据此把判断改成“不触发”。用户审核候选仍只在既有审核区域完成，不增加“审核草稿”步骤或内容满意度按钮。

### 4.3 可定位与返回

支持使用 `/learning?event=<event_id>` 定位任务并打开详情；筛选条件保留在页面导航状态中。由审核页返回时恢复任务、筛选与列表位置。刷新页面仍能定位同一任务；不存在或已清理的记录显示明确提示，不跳到另一条任务。

URL 只携带任务标识和必要的视图条件，不携带用户正文或理由。

## 5. 就地反馈与取消规则

### 5.1 单一反馈对象

列表与抽屉使用同一份反馈状态、同一个组件逻辑和现有反馈接口。反馈绑定具体 `result_id` 下的 `learning_gate`，不是笼统绑定整个任务，也不是给候选内容评分。

有效判断仍只有触发／不触发两个值：满意表示认可原判断，不满意表示期望相反判断。理由不参与这个映射。未反馈、保存中、读取失败属于界面状态，不是新的模型判断类别。

### 5.2 操作行为

| 当前状态 | 用户操作 | 保存结果与展示 |
| --- | --- | --- |
| 未反馈 | 满意 | 保存有效反馈，创建／激活对应样例，高亮满意 |
| 未反馈 | 不满意 | 保存有效反馈，创建／激活对应样例，高亮不满意；展开选填理由 |
| 满意／不满意 | 点击另一选项 | 修改同一结果的反馈与标准标签，不创建重复样例 |
| 满意／不满意 | 再点当前选项 | 不做额外写入；不是隐式取消，以免误判重复点击 |
| 满意／不满意 | 取消反馈 | 调用撤回能力，恢复未反馈，取消有效样例资格 |
| 已取消反馈 | 重新评价 | 通过明确点击重新激活该结果的样例，不复制成另一条样例 |

只在已有有效反馈时显示“取消反馈”。这是操作入口，不是第三个评价选项。不把取消藏在更多菜单，也不要求跳转到样例管理页面。

提交成功后在当前行／抽屉就近显示“已保存为个人测试样例 · 撤销”。其中“撤销”与“取消反馈”执行同一动作；短暂提示消失后，持久的取消入口仍然可用。切换满意度后提示“反馈已更新 · 取消反馈”，避免把取消全部评价误解为恢复前一个选项。

### 5.3 取消的明确边界

- 不再将该反馈用于之后的回测；旧测试集固定版本也不能绕过撤回。
- 已有回测任务沿用评测系统的撤回校验与取消规则，不继续把该样例算作有效新增评分。
- 恢复“未反馈”与未选中按钮；取消成功后不会因为一次旧轮询又显示为已反馈。
- 不取消学习任务，不删除观察，不拒绝或撤销候选，不回滚已经批准的 Persona 内容，不重新调用模型。
- 取消不需要二次确认，因为可重新评价恢复；操作失败时保留原来的有效反馈状态并显示错误。
- 撤回不是永久擦除。内部仍可保留撤回历史、已有样例快照和审核答案；界面不能声称“所有数据已删除”。彻底删除仍在“反馈与测试样例”中，通过明确的删除操作完成。
- 不改写已经完成的历史报告为“从未使用过此样例”；历史和当前有效性分别表达。

对话学习每个结果只有一个 gate，取消它即退出整个有效样例集合。共享组件若用于偏好场景，应只撤回所操作的场景，不误撤同一次运行的其他场景。

### 5.4 不满意理由

选择不满意即完成反馈，不以填写或保存理由作为入库条件。理由输入框按需出现，文案为“理由（选填，仅用于改进提示词，不参与回测）”，继续使用现有 2000 字上限和独立“保存理由”动作。

列表行与抽屉共享同一份理由草稿，避免两个输入框各自覆盖。保存后的状态为“理由已保存”；未保存时明确提示。后台刷新不得覆盖草稿。

改为满意或取消反馈后，当前理由不再作为有效的不满意参考；已有历史按现有保存规则保留。再次点不满意时不自动把已撤回的历史理由重新提交为新反馈。

## 6. 状态可见性与边界

| 实际情况 | 列表／详情表达 | 是否可评价 |
| --- | --- | --- |
| 排队、分析中且未形成 gate | 暂无判断 | 否，不把空值当作不触发 |
| 已判定不触发，没有候选 | 不触发学习；未反馈或当前反馈 | 是 |
| 已判定触发，候选被去重或未生成 | 触发学习；候选区说明实际结果 | 是 |
| gate 已形成，后续生成失败 | 触发判断与失败状态同时可见 | 是，只评价 gate |
| 等待上下文，仍未形成有效判定 | 等待上下文；暂无判断 | 否 |
| 没有评测快照的旧任务 | 历史结果缺少反馈数据 | 否，不为展示自动创建样例 |
| 未反馈结果的必要快照已清理 | 反馈数据已过期 | 否，不以当前数据补造旧结果 |
| 反馈状态读取失败 | 反馈状态暂不可用，可重试读取 | 暂停写入，不能冒充未反馈 |
| 取消反馈成功 | 未反馈；可短暂提示“已取消” | 可以再次明确评价 |

任务重试产生新运行时，新结果使用新的 `result_id`，不能继承旧结果的满意度。新一轮尚未产生结果时显示“等待本轮判定”，不得把 checkpoint 中遗留的上轮结果当成本轮结果。上轮反馈与样例保留，在详情中通过“历史结果／反馈”入口查看。

后续给已有结果补充候选或审核答案，不是新一次触发判断，不应清空其已有反馈。判断标准以结果身份为准，而不是以任务更新时间变化为准。

## 7. 刷新、草稿与并发交互

### 7.1 页面稳定性

- 列表按任务 ID 保持节点，局部更新状态，避免每轮 `replaceChildren()` 重建全部输入与按钮。
- 轮询只更新已展示行的服务端状态；不自动重排、翻页、打开抽屉、关闭抽屉或滚动页面。
- 抽屉内的展开状态、滚动位置和未保存理由在后台更新时保留。
- 切换任务、关闭面板时将理由草稿暂存于当前页面内存，返回同一结果可继续填写。草稿不因此成为用户 benchmark 数据，也不写入浏览器长期存储。
- 页面刷新或离开时，对未保存的理由／设置提供未保存提示；不能静默将草稿当作已保存。取消该条反馈则同时清理它的本地理由草稿。

### 7.2 防止状态覆盖和重复写入

- 反馈保存期间只禁用当前结果的反馈操作，其他任务仍可查看；列表与抽屉同时显示保存中。
- 成功前不显示“已保存”，失败后提供原地重试。请求结果不确定时先重新读取，不自动发送另一条新的反馈。
- 保存继续使用幂等请求标识和 `expected_feedback_revision`；理由更新、撤回继续使用反馈版本校验。
- 迟到的详情请求不能覆盖用户刚切换到的新任务；迟到的轮询不能覆盖较新的反馈版本。
- 多标签页修改冲突时提示“反馈已在其他位置更新”，读取最新服务端值，不静默覆盖。
- 列表、抽屉在写入成功后立即同步；从样例管理／其他标签页返回时进行只读刷新，不要求用户手动逐页对齐。

## 8. 查询接口与前端状态设计

### 8.1 任务列表读模型

扩展现有 `GET /api/learning/v1/events` 的列表能力，保留 `events` 返回字段及已有任务字段；增加可选分页、筛选和安全的展示摘要。查询参数建议：`limit`、`cursor`、`feedback`、`status`、`connection_id`、`q`，明确校验取值与长度，默认每页 20 条。

每条任务补充以下展示字段；具体命名在实现时与现有契约对齐：

| 字段 | 含义 |
| --- | --- |
| `input_preview`、`input_state` | 有限长度的输入摘要及可用／已清理状态 |
| `current_result_id` | 当前运行的具体判定结果；尚未产生时为空 |
| `triggered` | `true / false / null`；只有前两者是有效判断 |
| `feedback.state` | 未反馈／满意／不满意／暂不可用；不是模型判断字段 |
| `feedback.revision`、`feedback.case_id` | 修改和撤回需要的服务端身份与版本 |
| `feedback.can_rate`、`feedback.can_withdraw`、`feedback.disabled_reason` | 明确当前可执行操作，不靠前端猜测 |
| `review_summary` | 可核验的候选数量与审核进度；不能从任务 outcome 推测通过数 |
| `has_previous_feedback` | 旧运行存在反馈的提示；不冒充当前运行已反馈 |

列表响应提供 `next_cursor`、`has_more` 和与当前筛选同口径的数量信息。排序采用接收时间与任务 ID 的稳定组合；翻页使用固定查询边界，避免新任务插入导致重复或漏行。用户点击更新时建立新的查询边界。

服务端统一组装学习队列与评测存储的摘要，浏览器不为每一行额外发起多个请求。反馈过滤在分页前应用，不能仅筛选已经取出的页面。性能需要时可建立可重建的摘要索引，但反馈和样例的主数据仍只保存在现有评测存储，不维护第二套可写反馈数据库。

### 8.2 写接口复用

- 评价：`POST /api/evaluations/v1/results/{result_id}/feedback`。
- 理由：`POST /api/evaluations/v1/cases/{case_id}/reason`。
- 取消反馈：`POST /api/evaluations/v1/cases/{case_id}/withdraw`，传入明确的 `learning_gate` subject 和反馈版本。
- 重试、取消学习任务、来源确认：继续使用既有学习接口，保持与反馈操作独立。

不新增一个含义模糊的通用 `cancel` 接口同时处理任务和反馈。服务端始终从指定结果读取原判断，浏览器不提交或改写 `actual_trigger`。

### 8.3 前端状态分层

分别维护列表查询与分页、选中任务、详情请求序号、按结果 ID 保存的反馈状态、理由草稿、后台状态及设置草稿。不要把它们全部塞进一次页面刷新流程。

任务 ID 用于定位任务；结果 ID 用于定位被评价的判定；反馈 revision 用于并发校验。三者不能互相替代。

## 9. 可访问性与视觉约束

- 满意／不满意同时使用文字、选中样式和 `aria-pressed`，不只靠颜色表达反馈状态。
- 同一任务的操作区域具备明确名称；多个“取消反馈”按钮可通过所在任务的可访问名称区分。
- 抽屉支持键盘打开、关闭、Esc、焦点约束和焦点返回；存在未保存内容时按第 7 节处理。
- 保存成功与错误使用就近的可访问状态提示，不把所有错误只显示在页面顶部。
- 长提示词、来源名称、错误消息允许换行或受控折叠；390 px 窄屏不出现横向溢出。
- 小屏任务行按“输入、状态、操作”分组堆叠，不把桌面多列强行压缩。
- 收起配置后仍保留异常入口；来源未配置时给出设置引导，不显示伪造的后台正常状态。

## 10. 实现范围与顺序

1. **列表读模型：** 增加输入摘要、判定结果、反馈状态和分页筛选，验证过期数据与旧任务兼容。
2. **共享反馈状态：** 组件增加显式取消、保存状态和理由草稿协调；复用已有反馈／撤回契约。
3. **页面布局：** 紧凑状态栏、任务优先、配置面板、详情抽屉；移除底部详情及强制滚动。
4. **局部刷新与导航：** 保留行、焦点和草稿；加入任务定位、过滤与返回恢复。
5. **联调与验收：** 使用隔离任务库和模拟模型，最后检查正式页面只读展示。

主要涉及 `templates/conversation_learning.html`、`static/conversation-learning.js`、`static/conversation-learning.css`、共享 `static/evaluation-feedback.js` 及其样式、`conversation_learning/web.py`／`service.py`／列表查询实现，以及必要的只读评测摘要接口。若共享组件变化影响偏好场景页面和样例管理页，必须同步回归，不改变它们的反馈语义。

已有个人样例与反馈无需手工迁移，不重新标注历史任务；旧数据缺少新增摘要字段时采用明确的不可用状态，不自动补造结果。

## 11. 验收标准

### 11.1 日常使用

- 页面默认展示紧凑状态栏和任务列表，来源与学习设置不再占据大段主页面。
- 在至少 100 条任务的隔离数据集中，打开任意任务都不会滚到整个列表底部；关闭详情恢复原位置和焦点。
- 列表能够直接识别用户输入、本次判断和是否已反馈，不打开详情也可提交评价。
- 满意度、可选理由、取消在列表和详情中同步；默认列表反馈后不跳行、不消失。
- 分页与筛选覆盖全部可见任务，不仅覆盖最近 100 条；无匹配结果与没有任何任务分别给出提示。
- 从审核页返回可继续查看原任务，设置修改不丢失任务浏览状态。

### 11.2 反馈与数据边界

- 没有明确点击满意／不满意，不创建个人测试样例。
- 有效“不触发”可以评价；尚未判定不能被记录为“不触发”。
- 满意改为不满意只修改原样例；重复点击、网络重试不生成重复样例。
- 取消立即清除有效反馈，旧测试集不能继续使用该反馈；重新评价可恢复，不复制样例。
- 取消反馈不改变任务、候选、正式 Persona 或模型调用次数；撤回与永久删除的文案清楚区分。
- 理由仍为选填，且不进入回测输入、标签计算或评分。
- 新运行不继承旧运行反馈；同一结果补充审核答案不清空原反馈。

### 11.3 异常、并发与响应式

- 反馈保存失败、撤回失败、读取失败和版本冲突都有就近提示，不显示虚假的保存／取消成功状态。
- 后台刷新不覆盖理由草稿、选中任务和抽屉滚动位置；迟到请求不覆盖新状态。
- 在多个标签页和样例管理页修改同一反馈后，返回任务页可正确同步。
- 完成桌面与 390 px 窄屏的实际浏览器点验，检查抽屉、关闭返回、分页、反馈和取消；页面无横向溢出，键盘路径可操作。
- 回归现有后台启停控制、来源设置、偏好场景共享反馈、审核答案关联和撤回后的回测保护。

验收记录须注明使用的是模拟模型还是实际模型。页面交互通过不等于学习判断质量提高；真实语义质量继续由用户反馈形成的 benchmark 评估。
