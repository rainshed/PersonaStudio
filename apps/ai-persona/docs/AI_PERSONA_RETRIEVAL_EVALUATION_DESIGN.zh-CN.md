# AI Persona 中英文召回测试设计

> 设计与历史参考：本文可能包含早期阶段或规划，不是本次发行的验收报告。当前入口与能力以[使用指南](../../../docs/GETTING_STARTED.zh-CN.md)和[兼容矩阵](../../../docs/FEATURE_PARITY.md)为准。

日期：2026-09-07。状态：测试设计；尚未实现完整数据集与评测程序。

## 1. 要验证的产品行为

用户用中文、英文、缩写或自然语言描述一个任务时，系统应在指定范围内找到相关的正式知识、材料与课程，把最有用的记录排在前面，并在上下文预算内保留任务所需的信息。

测试不绑定分词、向量、模型或查询扩展方案。先冻结问题和预期，再比较实现。返回非空不等于成功，返回更多也不等于更好。

第一版聚焦知识、材料、课程的文本召回及上下文装配。偏好场景分类、材料内容理解、最终回答质量分别评测，不混入同一个召回分数。关系过滤、标签范围、版本及状态仍是召回的必要约束。

## 2. 当前实现与测试入口

| 层次 | 入口 | 用途 |
| --- | --- | --- |
| 正式召回 | `PersonaQueryService.search_knowledge` | 主评测入口，保留过滤、排序、分页与版本契约 |
| 上下文装配 | `prepare_persona_context` | 检查命中的记录是否实际进入上下文，及预算造成的遗漏 |
| MCP | `search_knowledge`、`prepare_persona_context` | 少量代表用例验证真实工具参数与返回结果一致 |
| Studio / CLI 底层搜索 | `index.search_index` | 对共有参数作行为对照；独有过滤能力不强求接口一致 |
| 材料整理候选召回 | `material_analysis.retrieve` | 独立附加套件；输入是概念词列表，不能与完整自然语言查询混为一项成绩 |

当前正式召回使用 FTS5 `unicode61`，查询拆分后以 OR 连接，最多保留 20 个词项。现有测试主要覆盖 MCP 契约、范围、分页和版本，不足以衡量中英文任务的召回质量。

主套件从规范化的查询请求直接调用服务，以隔离 Agent 是否正确选工具和构造参数。完整 Agent 工作流可另设套件，不能由 Agent 临时改写失败查询后把成绩算回直接召回。

## 3. 固定测试库与查询集

### 3.1 数据库

建议第一版使用约 48 条人工编写的正式记录：30 个知识点、12 份材料、6 门课程，覆盖物理、数学、统计与 AI。另配必要的标签、关系及测试来源。记录数量可随标注调整，但发布一个数据集版本后冻结。

测试库独立于日常 Persona 和可交互修改的 Demo，使用稳定 ID、固定版本和内容摘要。每次在临时目录编译索引，不读取真实私人材料，不修改正式 Persona。

记录刻意包含：

- 中文名称加英文别名、英文名称加中文别名、缩写与全称。
- 没有记录某种语言别名的概念，用于单独衡量跨语言语义能力。
- 只在摘要、课程大纲或正文里出现目标内容的记录。
- 名称相似但含义不同、共享通用词但主题不同的干扰记录。
- 同缩写不同义的记录，例如 quantum Monte Carlo 与 quasi-Monte Carlo。
- 只顺带提及目标词的材料，以及真正以该概念为主题的材料。
- 不同标签范围内的同名记录、已归档记录，以及尚未发布的候选。

正文长度、关键词频率和中英文比例应有变化。不能让所有正确记录都比干扰记录更短、重复更多关键词或拥有特殊 ID 前缀。

### 3.2 查询规模与切分

建议 40 个意图组，每组各有自然的中文和英文表述，共 80 条；另加 20 条中英混合表述与 20 条格式／措辞变体，首版约 120 条质量查询。接口边界与状态测试另计。

按意图组分为约 2/3 开发集和 1/3 留出集。同一意图的翻译、同义改写和格式变体必须在同一侧；同一概念簇尽量不跨侧，减少针对答案调参。开发集用于定位问题，留出集用于阶段验收。一旦依据留出集逐例修复，应将其视为回归集，并另补新的留出意图。

合成查询用于覆盖边界；后续增加用户实际提出、经整理的查询作为独立真实任务集，单独报告结果。

## 4. 必测场景

以下示例描述预期测试行为，不代表这些记录已全部创建。

| 场景 | 示例查询 | 核心判断 |
| --- | --- | --- |
| 完整名称 | `矩阵乘积态` / `matrix product state` | 找到指定实体；无歧义定位时目标排第一 |
| 已登记别名、缩写 | `MPS` / `Time-Evolving Block Decimation` | 命中同一实体，不仅命中提及它的材料 |
| 中文子词、英文词形 | `张量网络` / `tensor network` / `tensor networks` | 名称不完全一致时仍有合理命中 |
| 大小写与格式 | `mPs`、`ＭＰＳ`、多余空格、连字符及 Unicode 破折号 | 格式变化不丢失明确目标；涉及含义变化的大小写不强行等同 |
| 自然语言 | `给我写一份介绍张量网络的 note` / `Write a note about tensor networks` | 主题目标被找到，通用词不挤掉主题 |
| 中英混合 | `解释 MPS 的 canonical form` | 中英文共同表达的关键意图得到覆盖 |
| 多概念 | `比较 MPS 和 TEBD` / `Compare MPS and TEBD` | 两个必需概念都找到；只命中一个不算完整成功 |
| 长查询 | 将相同目标放在长请求开头、中间、结尾 | 尤其检验目标位于第 20 个词项之后；保持意图不变 |
| 字段召回 | 目标仅见于摘要／课程大纲／正文 | 检查产品声明可搜索的字段，不假设未声明字段一定可搜索 |
| 未登记翻译或语义改写 | 用另一语言或无明显词重合的描述提问 | 单独衡量语义能力，不能伪装成“已支持别名”的测试 |
| 同缩写歧义 | `QMC`、`quantum Monte Carlo`、`quasi-Monte Carlo integration` | 模糊查询允许多个解释；明确限定后正确解释优先 |
| 相似词干扰 | `state`、`network`、`note` 同时存在于不同主题 | 判断任务相关性，不按共有单词判相关 |
| 类型限定 | 搜知识点／材料／课程中的同一主题 | 只在合格类型内召回和排序 |
| 标签范围 | 同一查询分别使用物理、统计、交集与并集范围 | 范围先约束候选，再检索和截取；范围外记录不得返回 |
| 无合适记录 | 固定库中所有记录都与问题无关 | 可以返回空，不应为填满数量而提供无关条目 |
| 一致性 | 同一库重复查询、重建索引、分多页读取 | 无重复和漏页，固定版本下排序可复现 |

自然语言与无别名翻译属于独立切片：前者可包含明确实体名称，后者需要额外语义能力。报告不得把它们合成一个“英文／中文通过率”。

## 5. 如何确定正确答案

在固定的小库上，为每条质量查询完整检查合格记录，标注相关性：

- **3：核心相关**，直接对应请求中的目标概念或指定材料。
- **2：直接有用**，能实质支持本次任务的材料、课程或知识。
- **1：背景相关**，可补充但不应挤掉核心结果。
- **0：无关**，仅共享词语、含义不符，或对任务没有帮助。

相关性与资格分开记录。某记录可以语义高度相关，但因标签、类型或未发布状态而不允许返回；它不进入该请求的召回分母，返回它仍是硬失败。

每个案例另列：必须覆盖的目标组、明确不允许返回的记录、是否允许空结果、标注理由。一个目标可能有多个可接受记录，用替代集合表达；多目标请求要求每个目标组至少命中一个。不能把两种可互换材料误要求为必须全收。

例：

```json
{
  "case_id": "compare_mps_tebd_zh",
  "intent_id": "compare_mps_tebd",
  "language": "zh",
  "query": "请比较 MPS 和 TEBD",
  "filters": {"entity_types": ["knowledge_node"]},
  "required_groups": [["kn_mps"], ["kn_tebd"]],
  "relevance": {"kn_mps": 3, "kn_tebd": 3, "kn_tensor_network": 1},
  "forbidden_ids": ["kn_archived_tebd"],
  "allow_empty": false,
  "reason": "比较请求需要同时找到两个概念；张量网络仅作背景。"
}
```

只有完成全库标注的固定套件，未列出的合格记录才能默认计 0。扩展库出现未标注结果时应标记 unjudged 并补充评审，不能静默计为错误或正确。

人工判断根据任务和记录内容完成，不查看某个实现的分数来决定答案。模型可以辅助起草标注，但不能让被测模型自行生成唯一标准答案。存在争议的案例保留分歧并暂不用于硬门槛。

没有目标实体不等于没有相关背景。只有确定所有合格记录均为 0 的请求，才进入无结果测试；“没查到”也不解释为用户不会该知识。

## 6. 指标与计算口径

| 指标 | 定义与用途 |
| --- | --- |
| Hit@1 / Hit@3 | 无歧义定位请求的可接受目标是否进入前 1／3 名 |
| Recall@5 / Recall@10 | 前 k 名中相关性 ≥2 的记录数，除以该请求所有合格且相关性 ≥2 的记录数 |
| 目标组完整覆盖率@5 | 所有 required_groups 均有命中的查询比例；用于多概念任务 |
| nDCG@5 | 使用 0–3 标注及增益 `2^grade - 1`，衡量核心结果是否排在前面 |
| 无关结果占比@5 | 实际返回的前五条里，相关性为 0 的比例；空返回记 N/A，另由召回与空结果指标评价 |
| 无结果误报率 | 金标准完全无相关记录的请求中，返回至少一条结果的请求比例 |
| 双语成对成功率 | 同一意图的中文与英文都覆盖必需目标的比例，不要求两个排序完全相同 |
| 越界／未发布泄漏数 | 不合格 ID 被返回的次数，必须为 0 |

Recall 的分母不是系统自己返回的 total_count。无正例查询不参与 Recall 和 nDCG 平均值；若相关记录超过 k，同时报告最大可能 Recall@k，避免设定不可能达到的门槛。核心验收查询尽量保证直接相关记录不超过 5 条。

分语言、场景、实体类型、难度分别报告，再按意图组宏平均，避免为一个简单概念生成大量改写而抬高总分。每个分组同时列样本数与实际成功／失败数。小样本百分比不视为精确的普遍质量估计。

排序评价采用常见的 top-k 召回与分级相关性设计，参见 [Introduction to Information Retrieval：Evaluation of ranked retrieval results](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html)。

## 7. 上下文层单独验收

对代表查询同时运行 search 和 prepare，使用一致过滤条件。固定 `knowledge_limit=8`，分别使用 `max_chars=8000` 与 `2000`；上下文内使用固定的少量偏好，另设无偏好对照。

分别记录：直接搜索 Top8、最终上下文 ID、核心目标保留情况、按接口契约计算的内容字符数、完整响应体字符数、截断标记和遗漏原因。内容预算不等于完整 JSON 响应体大小，两者不能混称。

在预先确认全部核心目标可以装下的案例中，要求核心目标保留。装不下的压力案例检查优先级与明确的截断说明，不要求无限预算下的全部结果。

`task` 和 `question` 的输入契约须显式记录。当前知识查询主要来自 `question`；用 `task` 单独表达主题的用例作为产品行为待定案例单列，不能悄悄补写 question 后宣称通过，也不能把尚未确定的参数语义直接判成算法错误。

错误分类至少包括：未进入候选、进入候选但排名靠后、过滤错误、上下文预算丢失、接口传递错误、标签本身有争议。

## 8. 门槛建议

先运行旧实现建立真实基线。以下是建议的验收目标，不是已经测得的成绩：

1. 范围、类型、归档／待审排除、分页、版本一致性：全部通过。
2. 无歧义完整名称和已登记别名：Hit@1 为 100%；格式变体 Hit@3 为 100%。
3. 常见中文／英文自然语言任务：各自 Recall@5 目标 ≥90%，nDCG@5 目标 ≥0.85；同时检查成对失败，不能用英文平均分掩盖中文问题。
4. 明确的多概念请求：目标组完整覆盖率@5 目标 ≥90%。
5. 全部无相关记录的精选反例：不得产生无关结果；普通正例集单独报告无关占比，不强迫填满五条。
6. 无别名翻译、复杂语义改写、歧义缩写、拼写错误：第一版报告能力基线，待产品支持范围确定后再冻结门槛。不能为通过测试而自动给测试库补上所有查询别名。

首轮运行应允许质量目标失败并生成报告，避免把失败标成通过或修改 gold 迎合实现。已有接口不变量继续在常规测试中作为硬断言。后续修复通过的确定性案例提升为回归门槛。

## 9. 可重复运行与性能

评测记录代码提交、语料与查询集 hash、索引版本、配置、返回 ID／排序、截断和耗时。相同输入必须可重放。

离线主套件不需要外部模型。将来引入查询改写、嵌入或重排时，分别报告纯检索、改写后检索与完整链路；固定模型配置和可复放输出，实时模型另测波动、调用量与成本，不能混称为确定性离线测试。

性能独立在约 50、500、5000 条记录规模下测量，记录设备、索引建立时间，以及冷／热请求耗时。主机调度抖动不作为普通 CI 的严格毫秒门槛。若每组有效样本不足，不报告看似精确的 P95；可在预热后运行至少 100 次并保留原始耗时。

扩大性能库不能直接沿用小库的质量标签。新记录可能改变相关集合，质量评分需要重新标注。

## 10. 实施交付物

建议新增独立的 `evals/retrieval/` 目录，包含版本化测试记录、查询、相关性标注、数据校验与运行器。报告写入显式输出目录，不混入正式 persona-data。

实施顺序：

1. 建好一组约 20–30 条的冒烟查询，覆盖中英文对、名称／别名、多目标、干扰词与无结果；冻结记录和标注。
2. 对当前实现生成逐案例基线，包括所有失败，不同时修改检索算法。
3. 扩展为约 120 条质量查询及独立的接口边界套件，按意图组切分开发集和留出集。
4. 改进召回后用同一数据集对照，报告新增命中与新增误召回，再验收上下文层。

失败报告应展示原始请求、预期目标及理由、实际 Top-k 与相关性、漏掉的核心 ID、违规 ID 和错误层次，不能只有一个总分。
