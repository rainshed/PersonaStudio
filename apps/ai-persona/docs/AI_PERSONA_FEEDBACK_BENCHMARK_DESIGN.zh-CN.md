## 1. 核心决策与范围

### 1.1 三条主线

1. **触发判定：** 满意度评价的是“这个触发判断对不对”。系统原判定与满意度共同决定唯一的布尔标准答案。
2. **内容生成：** 对话学习生成的知识、偏好和关系，以用户直接通过或修改后通过时的内容快照作为标准答案，无须另写答案。
3. **不满意理由：** 仅作为后续修改提示词的参考，不生成标签，不进入回测输入，不参与评分。

日常使用不增加原因分类、预期选择、字段标注、候选满意度或标准答案编辑表单。用户只需评价触发是否合理，并继续使用现有审核流程。

### 1.2 入库规则

- 只有明确点击“满意”或“不满意”才建立样例；没有点击就不进入用户 benchmark。
- 点击后立即保存，不要求再点击“加入测试集”，理由可跳过。
- 审核通过只给已有样例补答案，不单独创建样例。
- 若先审核后反馈，创建样例时读取对应的已确认审核结果；若先反馈后审核，审核成功后自动补齐。
- 编辑、拒绝、暂缓、重试、展开详情、工作台 A/B 选择、自动评测或模型自评均不替代满意度点击。
- 保存反馈不调用 LLM，不修改正式 Persona，不自动重跑任务、送审或启用提示词。
- 合成测试、历史记录及旧工作台样例不自动转成个人 benchmark；只保留符合明确反馈规则的数据。

### 1.3 首版边界

首版实现两个业务的触发反馈、个人样例持久化、对话学习审核答案关联、冻结测试集、隔离回放及版本比较。

不接入自然语言维护、材料整理、模型连接测试或其他业务。通用接口预留扩展，但不提前实现它们的反馈页面和评分逻辑。不训练模型，不自动解析理由，不自动优化或发布提示词。

触发布尔答案可以自动评分；内容的结构、引用等可以自动校验。自由文本语义是否等价首版支持人工对照，独立模型裁判留作后续扩展。自动取得内容答案，不等于已经具备可靠的自动语义评分器。

## 2. 触发判断与满意度的唯一映射

### 2.1 映射规则

| 原系统判断 | 用户点击 | 期望判断 |
| --- | --- | --- |
| 触发 | 满意 | 触发 |
| 触发 | 不满意 | 不触发 |
| 不触发 | 满意 | 不触发 |
| 不触发 | 不满意 | 触发 |

服务端计算：

```text
expected_trigger = actual_trigger                 if rating == satisfied
expected_trigger = not actual_trigger             if rating == unsatisfied
```

映射只适用于已经完成的、反馈对象明确的二元触发判断。原判断由服务端从不可变结果取得，不能接受浏览器提交另一份原判断。用户不必再选择期望值，理由无权改变这个公式。

### 2.2 必须明确评价对象

对话学习的文案示例：

> 本次判断：不触发对话学习。你对这个判断是否满意？

偏好场景的文案示例：

> “写作 note”场景：触发。你对这个判断是否满意？

按钮评价的不是“整个任务体验”或“生成内容好不好”。内容错误通过正常审核修改，不通过“不满意”把本来正确的触发判断反转。

### 2.3 只有两个判定值，但处理状态仍需独立

业务字段为 `triggered: true / false`；“排队、处理中、等待上下文、等待来源确认、失败、取消”等属于处理状态，不是第三个业务判定值。

尚未得出判定时 `triggered` 缺省或为空，不能强制转换成 `false`。没有有效判定的结果不显示可提交的触发反馈按钮，也不产生触发标签。已有稳定触发判断但后续生成失败时，可以评价这个已完成的判断。

当前代码仍有场景 `uncertain`、学习 `needs_context` 等表达。实现时应规范为“处理状态 + 可选布尔判定”，并同步契约、界面与测试；旧未决数据只标明未完成，不伪造二元结果。内部允许补充上下文后继续判断，但不能以“不确定”充当错误率更低的免费选项：回测须单列未完成数和覆盖率。

## 3. 两个业务如何应用

### 3.1 偏好场景触发判定

一次请求可以判断多个场景。评价单元是“这一输入下的这一个场景”，不是整份结果。

- 每个场景展示触发／不触发，以及满意／不满意。
- 未触发场景可折叠，但必须可展开评价，否则无法收集漏触发样例。
- 不提供对多场景结果一次点击后全部反转的整体反馈。
- 同一场景的判断与满意度产生一个标签；未评价场景没有标签，不能默认不触发。
- 同一次运行可以保存在一个 case 中，包含多个已评价场景；计分按场景单元进行，统计时同时报告运行数。
- 空场景目录没有可评价的场景单元，不生成伪造的“全局不触发”样例。
- 单个场景仍未决，不阻止同一次运行中其他有效二元判断被评价；整体契约问题另记。

保存原始 `user_prompt`、`task_summary`、必要的 `recent_messages`、`artifact_type`、完整有效场景目录及内容版本。回测仍向模型提供这份完整目录，只对被评价的场景计分。

用户后来修改场景描述、删除或新增场景，不改写旧样例。首版不将最新目录替换进旧输入后继续套用旧标签。

现有 Studio 场景判定区增加反馈与“最近判定”入口；HTTP／MCP 返回兼容的 `run_id`、`result_id`、`feedback_url`。用户通过 Studio 对同一结果评价，MCP 不开放代替用户写满意度的工具。

### 3.2 对话学习触发

“触发”定义为：

> 当前用户输入包含值得进入后续学习分析的信号。

它不等于最后产生了待审核候选，也不等于 Persona 发布成功。

- 存在符合学习边界、可进入候选分析的信号：触发。
- 已完成判断，输入不包含符合条件的信号，或仅有被明确过滤的临时要求：不触发。
- 候选被去重、已有相同知识／偏好、来源策略暂停或后续生成失败，不反向改变已确定的触发判断。
- `observe` 等内部状态不能直接一律映射为触发；应在完成信号校验与临时性过滤的位置记录最终 gate 布尔值。
- 任务页在已经送审与没有送审的情况下，都显示这个独立的触发判断和两个反馈按钮。
- 被策略拒绝且根本未创建的任务，不伪造可评价历史；敏感输入过滤规则保持不变。

不增加知识／偏好／关系类型的人工标注。触发反馈只提供 gate 标签，类型、内容、范围和关系以审核通过的内容作为参考。

### 3.3 内容生成不再增加一套评价表单

生成内容仍进入现有审核区。用户直接通过、修改后通过、拒绝或暂缓，均沿用原流程。

任务或样例页只显示自动生成的状态，例如：

- 已保存触发样例，暂无审核答案。
- 已取得 2 条审核答案，另有 1 条待审核。
- 本任务尚未生成候选，仅参与触发回测。
- 未评价触发判断，审核结果不会单独建立测试样例。

不要求再点击“把审核内容设为答案”，也不要求提供原始聊天证据。

## 4. 审核结果如何成为内容标准答案

### 4.1 采用的内容

| 审核状态 | 标准答案处理 |
| --- | --- |
| 直接通过 `accepted` | 保存审核确认后的有效业务内容 |
| 修改后通过 `edited_and_accepted` | 保存应用人工修改后最终通过的业务内容 |
| 待审核／暂缓 | 没有标准答案，不视为错误 |
| 拒绝 | 不建立正向答案，不自动推断整个任务应不触发 |
| 审核写入失败／回滚 | 不发布答案，等待真正成功的审核 |

答案覆盖知识、偏好、关系及它们必要的依赖。对于更新已有对象，保存本次确认的业务变更和必要上下文，不把原对象的无关字段当成模型此次必须生成的内容。

保存审核成功那一刻的快照，而不是指向未来会变化的正式记录。之后普通编辑 Persona，不自动更新这个 benchmark 答案。审核备注和 `decision_reason` 不是答案内容，也不作为额外判分要求。

原 AI 候选与审核后答案必须分别保存，不能用人工修改后的内容覆盖原输出。

### 4.2 关联到准确的运行与候选版本

使用 `result_id → 候选版本 → proposal_id → 已提交审核修订` 的可核验关联，不仅凭任务 ID 或最终记录 ID猜测归属。

多轮生成可能更新同组待审核 proposal。只有实际被审核的那一版候选所对应的运行，可以自动接收该次内容答案；不能把后来根据新用户输入生成并通过的内容回填为早先输入的答案。

若同一候选在未重新生成的情况下被人工编辑后通过，这是正常答案修正。若候选已被后续运行替换，则原运行标记为“无对应审核答案”，仍可用于触发回测。

### 4.3 先反馈与先审核均支持

**先反馈、后审核：**

1. 点击创建样例并冻结原输入、原判定和当前生成结果。
2. 审核真正提交成功后发出带稳定标识的审核结果事件。
3. 答案关联器只更新已经存在且未撤回的对应样例，形成新的 benchmark 修订。

**先审核、后反馈：**

1. 正常完成审核，不创建样例，也不为此额外保存未授权的长期聊天快照。
2. 用户后来点击触发反馈，创建样例时查询可核验的审核历史。
3. 能恢复对应最终内容则补齐答案；必要输入已过期时标记回放数据不足，不用当前数据假冒旧输入。

首次反馈和审核并发发生时，通过幂等事件与提交后查询补齐；不能因错过通知永久遗漏答案。关联失败不阻塞或回滚已经成功的业务审核，应可恢复、重试并提示“答案同步中”。

### 4.4 部分审核与矛盾处理

- 只通过部分候选时，只能评价这些已确认内容的覆盖与正确性，不能把答案集合当作穷尽全部合理输出的完整金标准。
- 未审核、被拒绝或模型原本遗漏的内容，不自动推导为正向答案；额外输出没有明确判断依据时标为未判定，不伪造精确率。
- 原来不触发、用户点不满意：得到“应触发”标签，但没有凭空产生内容答案。该样例先参与触发测试。
- 触发标签为“不应触发”却存在已通过内容时，保留两项事实，不用审核行为覆盖按钮标签。完整流程按“不应触发”评分，不要求生成这些内容；关联内容单独标明不纳入该样例的端到端正向内容评分。
- 审核结果不能反过来充当触发反馈，也不能补写“满意”。

### 4.5 内容比较

确定性检查包括允许操作、结构、既有对象引用、依赖、关系端点与方向、发布边界等。随机 ID、时间戳、版本号和其他生成元数据不要求与答案一致；既有对象的稳定 ID 不能随意忽略。

偏好检查要求与适用范围；知识检查主题及有效内容；关系检查对应对象与类型。内容可以等义表达，不以逐字匹配判错。

首版提供原输出、回测输出和审核答案的人工对照，不要求日常反馈时再填质量表。未完成语义评审显示“待评价”，不能以结构合格或拥有审核答案代替语义正确率。以后增加独立模型裁判，也只能使用原输入、冻结环境、审核答案和通用规则，不能使用不满意理由。

## 5. 不满意理由的严格边界

理由是可选自由文本，只在点击“不满意”后提供。未填写不影响样例或标签保存；修改理由不重新调用模型、不改变触发标签和内容答案。

理由的唯一用途是供用户或获得明确授权的提示词修改流程查看、归纳问题。它不参与：

- 推导触发期望、建立内容标准答案；
- 回放输入、上下文、检索、模型补读或生成缓存签名；
- 评分规则、裁判输入、通过门槛、自动筛选测试样例；
- 自动触发 Persona 学习、修改线上提示词或训练模型。

理由与评测载荷分开保存。样例管理页可以查看理由，工作台设独立“提示词改进参考”视图；回放器和评分器只读取无理由的评测投影，不能将整个反馈对象序列化后传入。

仅修改理由增加反馈记录修订，不改变 benchmark 的输入／答案修订与执行指纹。在相同输入、版本、输出下，删掉、改写或留空理由应得到相同标签和评分。

切换为“满意”后理由不再作为当前有效不满意理由；历史可以保留，但始终不进入回测。用户数据备份可以包含理由，专用评测导出默认不包含。

## 6. 结果、样例和版本模型

### 6.1 标识

| 标识 | 用途 |
| --- | --- |
| `task_ref` | 原始学习任务；同一任务重试时可保持不变 |
| `run_id` | 某次执行，重试或重新生成产生新标识 |
| `result_id` | 用户实际看到的不可变判定／生成结果版本 |
| `subject` | 单个场景判定，或本次对话学习 gate；不包含候选满意度 |
| `case_id` | 一次结果首次明确反馈后创建的样例 |
| `feedback_revision` | 满意度、理由、撤回等用户反馈历史 |
| `benchmark_revision` | 被测输入、由按钮推导的标签或审核答案发生变化后的修订 |
| `group_id` | 同一原始输入、重试及其评测派生结果的统计分组 |

同一结果从不同页面评价同一 subject，只更新对应反馈；重传相同请求不产生重复样例。满意度变化由原判定重新计算标签，不基于上次标签再次反转。

多个已评价场景共享原始输入和目录，但各自标签独立。修改一个场景反馈不改变其他场景标签。

### 6.2 反馈请求示例

```json
{
  "subject": {
    "kind": "learning_gate"
  },
  "rating": "unsatisfied",
  "reason": "只是这次任务的修改，不是长期偏好。",
  "idempotency_key": "feedback-request-example",
  "expected_feedback_revision": 0
}
```

场景反馈的 subject 使用 `kind: activation_context` 与原目录中的稳定 `context_key`。客户端不提交 `actual_trigger`、`expected_trigger`、候选答案或评分要求，服务端从可信结果推导。

### 6.3 无理由的评测投影示例

```json
{
  "schema": "ai-persona.evaluation-case/v1",
  "case_id": "case_example",
  "capability_id": "persona.conversation_learning",
  "benchmark_revision": 2,
  "group_id": "input_group_example",
  "source": {
    "task_ref": "event_example",
    "run_id": "run_example",
    "result_id": "result_example"
  },
  "input_ref": "sha256:example-input",
  "environment_ref": "sha256:example-environment",
  "original_output_ref": "sha256:example-output",
  "trigger_labels": [{
    "subject": {"kind": "learning_gate"},
    "actual_trigger": true,
    "rating": "satisfied",
    "expected_trigger": true,
    "label_source": "explicit_rating"
  }],
  "content_gold": [{
    "proposal_id": "prop_example",
    "candidate_version_ref": "candidate_example_v1",
    "review_revision": 3,
    "decision": "edited_and_accepted",
    "approved_content_ref": "sha256:example-approved-content"
  }],
  "content_coverage": "approved_items_only",
  "replay_capabilities": ["learning_trigger", "learning_pipeline"],
  "status": "active"
}
```

标识和 hash 为占位。实际数据包含必要时间、格式、提示词／模型／流程版本、缺失项及审核提交身份。理由不在这个投影中。拥有 gate 标签不代表原内部 signals 的具体内容已被人工逐条确认。

稳定能力 ID 为 `persona.activation` 与 `persona.conversation_learning`，不随提示词拆分、模型更换或平台适配器更换而改变。

## 7. 用户数据保存、撤回和备份

### 7.1 目录与数据归属

采用文件优先、版本化 JSON 和内容寻址附件。建议结构：

```text
persona-data/evaluations/
  manifest.json                     # 独立的数据格式与版本
  cases/<case_id>.json               # benchmark 修订、标签及答案引用
  feedback/<case_id>.json            # 反馈与理由；不直接交给评测器
  blobs/<sha256>.json                # 输入、输出、冻结环境、审核答案
  suites/<suite_id>/<version>.json   # 精确的样例与 benchmark 修订
  runs/<eval_run_id>/report.json     # 运行配置、结果、评分，不复制理由

persona-state/evaluations/
  index.sqlite3                     # 可重建索引
  jobs.sqlite3                      # 运行、取消、审核答案同步任务
  traces/                           # 未评价结果的临时快照
  staging/                          # 可恢复原子提交
```

新集合纳入用户数据的备份、迁移与显式导出，不增加 `persona_revision`，不进入 `records/`、正式 Persona 快照、正常检索或日常 Agent 上下文。正式知识和偏好仍只保存业务内容及简单备注，不要求附聊天原始证据。

不顺带迁移所有既有 AI 会话／学习数据库；仅在明确反馈后提升所需数据。私有用户数据默认不提交源代码仓库，合成 fixture 单独保存并单独统计。

### 7.2 临时到持久

- 未评价结果可有短期 trace，用于展示、恢复及点击时取数；它不是样例，不用于回测或自动调参。
- 临时 trace 建议默认保留 7 天，并配置容量上限；不清理正在执行或正在提升的数据，页面显示可用期限。
- 当前工作台 captures 只保留最近 30 条，不能作为样例的长期依赖。
- 首次点击在锁内固定结果，保存必要附件后原子发布反馈与样例。多文件提交用可恢复日志，不能先显示成功再丢失依赖。
- 已保存样例不随对话学习的事件／观察到期清理而消失。
- 输入已过期但原判定可核验时，仍可保存点击和标签，标明“缺少回放输入”；原判定不可恢复时禁用反馈，不让用户评价未知结果。
- 不重新读取已被安全过滤的正文，不扫描宿主日志弥补缺失，不把当前 Persona 冒充历史基线。

### 7.3 冻结到什么程度

场景测试固定原参数与完整场景目录。学习触发测试固定规范化用户事件和原边界内可用上下文；完整学习流程还需冻结可查询 Persona、相关去重与审核前历史、配置和受限上下文提供者。

仅保存原命中的几条检索结果，不能宣称支持新检索策略的完整回放；只有 revision 数字而没有对应内容，也不能恢复旧环境。快照按内容 hash 去重，避免每个样例重复复制相同基线。

各阶段保存实际读取版本；若原运行跨越多份环境，首版如实降低到可支持的阶段回放，不伪造单一基线。后来的审核答案只作为评分参考，绝不能出现在该任务的输入、检索语料或去重基线中。

### 7.4 修改、撤回、删除

修改满意度生成新的标签修订；审核答案补齐生成新的 benchmark 修订；只改理由不变更 benchmark 指纹。

撤回一个 subject 后该标签退出后续测试；撤回最后一个有效反馈后整条样例退出后续测试，审核事件不能重新激活它。恢复需再次明确点击。新运行即使引用旧测试集，也必须检查当前撤回／删除状态，不能继续外发已经撤回的正文。

彻底删除清除样例私有历史与不再共用的附件，同时清理相关报告中可还原该样例的正文。可以保留不含正文的聚合统计和“样例已删除”标记；不承诺撤回用户自行导出的外部备份。

导入校验格式、hash、引用和冲突，保留原明确反馈的来源，不伪造新的人类点击。凭据、本机平台路径、锁和临时 trace 不进入用户评测导出。

### 8.2 内部边界

新建项目内部 `evaluations/` 模块，公共服务负责标识、二元标签公式、事务、持久化、审核答案关联、任务和报告。

两个受信任业务适配器分别提供：

1. 提取有效二元判定与反馈 subject。
2. 固定输入、结果、环境并声明可回放模式。
3. 隔离调用实际业务核心。
4. 对学习业务匹配已提交审核结果、提取业务答案。
5. 校验结构与计算适用指标。

不再设计任意人工期望输入、原因分类或候选反馈适配器。模型桥接只记录调用，业务层决定最终 gate 与用户看到的结果，不能仅靠底层模型日志建立反馈归因。

反馈服务依赖本机显式管理操作，不对普通 Agent MCP 开放写满意度、启动评测或导出数据的工具。记录操作来源但不把客户端声明当作密码学意义的人类证明。未来其他平台只需映射到相同业务结果和人工反馈入口。

## 9. 接口和界面

### 9.1 拟议本机接口

命名空间 `/api/evaluations/v1`，与既有单阶段 `/api/prompts/v1` 分开。

| 接口 | 用途 |
| --- | --- |
| `GET /capabilities` | 两项能力、回放模式与覆盖 |
| `GET /results`、`GET /results/:id` | 结果摘要、布尔判定和处理状态 |
| `POST /results/:id/feedback` | 满意度与可选理由；服务端推导标签，首次点击创建样例 |
| `POST /cases/:id/reason` | 只更新已有不满意反馈的理由，不改变标签或 benchmark 修订 |
| `POST /cases/:id/withdraw` | 撤回指定 subject 或全部反馈 |
| `GET /cases`、`GET /cases/:id` | 样例、标签、审核答案状态与回放能力 |
| `POST /cases/:id/delete` | 彻底删除已解析的明确目标 |
| `POST /suites`、`GET /suites` | 冻结样例 benchmark 修订 |
| `POST /preview` | 只读冻结预览：独立方案、思考档位、重复次数、预算及指纹 |
| `POST /runs`、`GET /runs/:id` | 核验预览指纹后启动；保存每条样例、方案和重复轮次的独立结果 |
| `POST /runs/:id/cancel` | 取消并防止迟到结果覆盖 |
| `POST /runs/:id/review` | 可选的内容语义对照评分，不创建样例 |
| `POST /export`、`POST /import` | 明确区分完整用户备份与无理由评测数据 |

首版不提供 `annotation`、手动设置期望、单独创建无反馈样例或任意上传标准答案的业务接口。审核答案同步是内部提交后事件，不接受浏览器伪造“已经审核通过”的内容。

反馈请求须有 subject、rating、幂等键和预期反馈修订，服务端检查其归属及有效二元判定。过期页面返回版本冲突，不覆盖后来的反馈。理由保存失败与首次反馈保存失败明确显示，不让用户误以为已经持久入库。

### 9.2 页面

2026-09-09 更新：评测页使用「开始检查、测试样例、历史记录」三入口。当前方案作为 A，候选 B 可独立更换提示词、模型和支持的思考档位；每条样例每个方案重复 1–10 次。报告分开展示该触发／不该触发正确率、有效分母、重复一致性以及失败／未判定／未运行。处理流程当前固定，旧候选／完整流程 API 继续保留。具体交互见使用说明。

- 对话学习：触发判定下仅显示两个按钮；不满意可展开一个非必填理由框。内容继续使用原审核页。
- 偏好场景：每个场景判定旁相同组件；不增加全结果反馈或期望选择器。
- 样例管理：查看输入、原判定、自动推导标签、理由和审核答案状态，支持修改满意度／理由、撤回、删除与导出，不提供标注编辑器。
- 工作台：选择两项能力、样例集、模型与提示词版本，运行和比较；提示词改进参考与无理由回测数据明确分离。

界面只在服务端确认成功后显示“已保存为测试样例”。网络失败可以幂等重试；评价本身不受模型可用性影响。

## 10. 回放与计分

### 10.1 模式

| 模式 | 输入与评价 |
| --- | --- |
| 场景判定 | 冻结参数与完整目录，自动比较已评价场景的布尔标签 |
| 学习触发 | 原事件与必要上下文，运行实际 gate，自动比较布尔标签 |
| 学习内容阶段 | 固定原运行的阶段输入，生成内容并与对应审核答案对照；仅用于定位，不证明原 signals 正确 |
| 学习完整流程 | 从原事件开始，检索、生成、校验与模拟送审；触发与内容分别报告 |

首版不要求用户提供“人工确认 signals”。内容阶段若缺少原阶段输入就标为不可回放；不能根据审核答案反推一套输入喂给被测模型。

对期望不触发的完整流程样例，检查不进入学习生成路径、不产生候选。对期望触发但没有内容答案的样例，只能评价 gate 和确定性约束，不制造内容通过率。重复不送审不等于漏触发。

### 10.2 触发指标

对偏好场景的已评价单元、对话学习 gate 分别计算：

- 正确率：二元判断等于期望的数量／获得有效二元输出的已评价单元数。
- 误触发率：期望不触发而实际触发的数量／有有效输出且期望不触发的数量。
- 漏触发率：期望触发而实际不触发的数量／有有效输出且期望触发的数量。
- 判定完成率：有有效二元输出的数量／本次选择的有效标签数量。
- 全量成功比例：二元判断正确数量／本次选择的有效标签数量，未完成和错误不计成功。

无适用分母显示 N/A。失败、未决、取消、数据缺失分别报告，不强塞入 true／false，也不能只显示成功调用上的漂亮正确率。

场景结果额外检查完整目录、未知／重复场景和结构。整次目录全匹配率只在该次全部场景都已明确评价时计算，不把未评价场景当负例。

### 10.3 内容指标

报告审核答案条数、已覆盖条数、明确的结构与引用问题，以及语义待评价／符合／不符合情况。语义评价以审核快照为参考，不包含理由。按知识、偏好、关系分组，不把一条摘要改写差异当作错误实体。

答案仅覆盖审核通过条目：可以统计这些已确认内容的覆盖，不能据此声称对所有潜在内容的完整召回率或精确率。没有答案时显示 N/A；原本不满意的 gate 不能给内容自动打零分。

### 10.4 固定版本、预算与隔离

- 固定测试集与 benchmark 修订、实际输入／环境、提示词内容与依赖、模型选择和参数、流程构建摘要、评测器版本、超时与预算。
- 比较提示词时 A/B 使用同一模型和基线；比较模型时明确模型差异。默认关闭备用连接，防止实际模型悄悄切换。
- 更换流程版本可用同一测试集新运行与历史报告对比，不承诺一个进程同时执行两套历史代码。
- 模型有随机性和供应商变化，不承诺逐字重现；保留实际模型、时间、参数和多次结果。
- 每个样例及 A/B 使用独立沙箱查询基线与模拟 Proposal 输出端口，不改生产任务、checkpoint、待审核记录、正式 Persona 或来源开关。
- 不扫描实时宿主上下文，不调用平台适配器读取当前会话，不开放任意工具、脚本或网络访问；模型外发只走选定连接，运行前展示范围与预算。
- 独立低并发队列，支持取消、总调用／token／时间上限；进程退出标记中断，不无感自动重发。
- 缓存签名包含被测输入、模型、提示词、流程版本，不包含理由；不复用生产 checkpoint 跳过被测阶段。

### 10.5 报告与样例集

报告列出选中数量、有效标签、完成／错误／缺失、自动可评分内容、审核答案覆盖、人工评分，以及 A/B 改善、退步、保持和不可比较的逐例结果。所有百分比显示分子／分母，费用未知显示未知。

用户修改满意度或新增审核答案后生成新 benchmark 修订，旧报告仍引用原修订，不悄悄重算；只改理由不改变旧分数或新回测载荷。

同一输入的重试与评测派生结果按 group 分组，留出集与开发集不跨组泄漏。工作台评测输出仅在用户明确评价其二元触发判断时才可形成派生样例；A/B 胜负、语义评分或运行完成不自动入库。

数据来自自愿点击，报告称为“个人已评价样例表现”，不声称代表全部生产流量。理由不自动决定测试集成员；用户仍可按明确样例标识选择测试范围。

## 11. 实施顺序

1. **共同底座与 gate 记录：** 增加结果标识、布尔判定与处理状态分离、临时快照、反馈事务及自动标签公式。
2. **两个简单入口：** 学习 gate 与逐场景两个按钮、可选理由、最近结果、用户样例保存；移除 v0.1 的额外标注需求。
3. **审核答案关联：** 原候选版本映射、审核提交后事件、先审核后反馈补取、并发幂等、部分答案与快照持久化。
4. **隔离评测：** 两项触发自动评分、学习内容／完整流程回放、版本和预算冻结、内容对照与工作台报告。
5. **数据管理与验证：** 撤回、删除、导入导出、恢复、清理竞态、理由隔离和无生产写入测试。

复用当前 Pi 模型接口、审核事务及版本管理。实现时同步更新使用说明与工作台协议，不顺带启用 Hook、扩大采集范围、改变后台运行状态或替用户运行真实历史评测。

## 12. 验收清单

### 12.1 简单反馈与标签

- 不点击反馈，产生任务、候选或审核通过都不会创建用户样例。
- 四种“原判定 × 满意度”组合严格符合映射表，不需要第二次选择期望。
- 满意无需文字；不满意理由可跳过，标签一致。
- 反馈定位到 gate 或一个场景，不能把生成质量不满或多场景整体不满自动反转标签。
- 连续切换满意度始终从原判定计算，幂等重传、跨页重复点击不重复入库。
- 未决、失败等没有布尔结果时不能评价；已有 gate、后续生成失败时仍可评价 gate。
- 未评价场景不参与标签评分，空目录不创建虚构场景。

### 12.2 理由不参与回测

- 改写、清空或增加理由，不改变标签、审核答案、benchmark 修订、被测请求、生成缓存键或给定输出的评分。
- 评测投影、评分器、未来裁判的输入均不含反馈理由与审核理由。
- 理由与正文中长得相似的正常业务字段分开处理，不能误删原用户输入或正式偏好内容。
- 仅保存理由不能创建新样例；理由不被自动转成信号、期望或提示词。
- 完整用户备份可含理由，评测导出与运行报告不复制理由。

### 12.3 审核答案

- 直接通过、修改后通过均捕获最终内容；原输出保留不变。
- 先反馈后审核、先审核后反馈、并发反馈与审核都能正确补齐，重放审核事件不重复添答案。
- 审核事务回滚不发布答案；答案同步失败不撤销已成功的业务审核且可以恢复。
- 后续运行替换同组候选时，答案不错误回填给旧输入；后续正常编辑 Persona 不改变旧答案。
- 待审核、暂缓、拒绝不生成正向答案；部分通过不当作完备金标准。
- 没有反馈、反馈已撤回或样例已删除时，审核事件不能创建或复活样例。
- 不应触发标签与已通过内容并存时不静默篡改标签，不纳入矛盾的端到端正向要求。

### 12.4 数据与隔离

- 临时 trace／事件／captures 到期清理后，已提升且输入齐全的样例仍可回放；原数据缺失时明确能力限制。
- 反馈提升与清理竞争、进程中断、索引失败均不产生虚假保存成功或丢失已确认样例。
- 备份恢复不依赖原机器的绝对路径和凭据；删除不会误删共用附件。
- 回放前后生产 Persona、待审核、任务与来源配置完全不变，A/B 与各样例的模拟写入彼此隔离。
- 审核答案及反馈后信息不进入原输入或冻结检索基线；样例不参与日常 Persona 查询和对话学习。
- 报告显示完成率、全量成功比例、失败和内容答案覆盖，不用空输出或跳过失败抬高成绩。
- 触发评分与内容语义评分分开；结构合法不等于内容正确，拥有审核答案不等于已经完成语义评分。
- 离线测试使用合成 fixture；真实模型回测须明确发起，不因编写／保存文档或反馈自动运行。

## 13. 结论

首版把用户操作收敛为“评价触发是否正确”和原有的正常审核。满意度自动产生二元触发标签；审核通过快照自动提供内容答案；不满意理由只服务提示词改进。

这两种自动沉淀共享一套用户数据和隔离评测底座，但都不能绕过“点击才入库”、历史版本固定、理由不参与回测以及不修改正式 Persona 的边界。
