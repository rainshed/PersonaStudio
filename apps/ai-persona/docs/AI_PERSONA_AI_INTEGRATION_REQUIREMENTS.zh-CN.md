## 1. 目标与确认状态

### 1.1 产品目标

在 AI Persona 内部接入可配置的 AI 模型，实现以下三项能力：

1. 提供一个接口，根据输入内容与用户配置的场景触发条件，判断哪些偏好场景应当被激活。
2. 允许用户通过自然语言新增、修改和整理 Persona，同时提供 Studio 统一入口与记录详情页入口。
3. 根据用户指定的材料，理解内容、对照已有 Persona，生成有依据、可修改、可审核的维护建议。

这三项能力分别解决“何时使用 Persona”“如何表达维护意图”“如何把材料转化为 Persona 候选”。

### 1.2 已确认的方向

- 三项能力均纳入本次需求。
- 场景匹配使用自然语言语义判断；允许在 `resolve_persona_activation()` 内部调用便宜、快速的模型。
- 触发条件由用户在 AI Persona 中自由维护，不要求为每个场景创建或更新固定 Skill。
- 触发后读取并应用 Persona 的流程保持统一，不由每个场景重新定义工具执行流程。
- 自然语言维护同时提供统一对话入口和记录详情页入口。
- 沿用现有正式记录、Source、Evidence、Proposal、ChangeSet 和人工审核发布机制。

### 1.3 本文建议与待定项

本文使用“应”描述建议纳入实现的验收要求，使用“建议”描述首版取舍。接口示例属于拟议契约，不表示已存在可调用接口。

以下尚未最终决定：具体模型与供应商、性能与费用上限、材料是否在导入后自动分析、首版是否支持批量材料。本文先给出可实施的默认建议，汇总见第 10 节。

## 2. 当前基础与本次变化

| 环节 | 当前基础 | 本次需要增加 |
|---|---|---|
| 场景匹配 | `Activation` 保存 intents、artifact_types、excludes；`_matched_contexts()` 主要做字符串匹配 | 动态读取触发描述，调用模型进行语义判断，提供独立轻量接口 |
| Persona 读取 | `prepare_persona_context`、搜索与详情工具 | 与触发结果衔接；保留已有偏好条件和应用边界 |
| 人工维护 | Studio 表单及 Proposal 审核 | 对话式输入、对象定位、结构化变化草稿和多轮修改 |
| 材料处理 | 材料导入、不可变 Source、可定位文本、材料关系 | 内置材料分析任务与候选生成 |
| 材料整理方法 | 由外部 Agent 按项目 workflow 执行 | 将适用规则实现为项目内部可调用的流程 |
| 变更发布 | 版本检查、引用检查、依赖检查、人工审核 | 从模型草稿提交提案，复用发布流程 |

原有 MCP 设计中“服务端不调用 LLM”的条款描述当前 v1。本需求拟增加模型驱动的判定与分析能力；实施时应同步更新接口文档及工具描述。人工审核不向模型开放、正式记录由发布服务写入等边界继续保留。

## 3. 共用的产品与数据原则

### 3.1 正式数据、草稿与提案

系统应区分：

- **正式 Persona**：已发布的数据，可用于场景判断、正常查询和任务个性化。
- **工作草稿**：一次自然语言维护或材料分析产生的可编辑结果，可在多轮交互中调整。
- **待审核提案**：从草稿生成并交给现有审核机制处理的变化。

工作草稿和待审核提案均不影响有效 Persona。模型回复中的“建议修改”“草稿已更新”“已提交审核”应与“已发布生效”明确对应。

```text
用户要求 / 指定材料
        ↓
读取正式 Persona 与必要来源
        ↓
模型生成工作草稿 ← 用户继续对话或手工编辑
        ↓
程序校验并生成 Proposal / ChangeSet
        ↓
用户在 Studio 审核
        ↓
正式记录、版本及投影更新
```

### 3.2 一次维护围绕同一份草稿

“第二条范围再小一点”“保留前两条”“把这个关联到已有节点”等后续输入应更新同一份草稿，避免每轮创建重复待审核项。

用户手工编辑的字段应被保留。后续模型修改涉及这些字段时，应在预览中显示差异。

草稿提交后需要记录对应的提案 ID。已提交的载荷不能用同一幂等键静默改写；后续修改应进入现有审核编辑流程，或创建有明确承接关系的新草稿。已生效项不得再次提交。

### 3.3 维护依据

- 用户明确陈述：保留原话或消息定位，记录维护意图。
- 材料内容：保留 Source、版本、原文位置和支持的具体结论。
- 模型归纳：标明归纳性质与疑点，不表述为用户已确认事实。
- 模型推测缺乏足够依据：作为待判断项展示，不直接生成确定的个人事实。

用户掌握程度、兴趣和偏好允许保持 `unspecified`。记录或导入一份材料本身，不等于用户掌握或喜欢其中所有内容。

### 3.4 校验与审核职责

模型负责理解、匹配、提取和建议；程序负责 Schema、稳定 ID、引用、版本、证据定位、依赖及写入校验。

正式变化由用户在 Studio 中审核。可把现有审核界面嵌入助手流程，避免为同一内容增加重复确认。支持按项处理；有关联依赖的项应一起说明。

## 4. 共用模型能力

### 4.1 配置与调用

三项功能共用模型调用服务，至少支持：

- 配置模型供应商、模型标识及凭据引用；凭据不进入 Persona 正式记录或草稿。
- 按任务配置模型：场景判定、自然语言维护、材料分析可使用不同模型，也可共用一个模型。
- 设置超时、输入与输出预算、并发和费用限制。
- 约束结构化输出，并对业务字段进行服务端校验。
- 记录模型版本、提示词版本、数据版本、耗时、调用结果和可取得的 token/费用信息。
- 未配置模型或模型暂不可用时，保留原有浏览、表单维护、正式数据查询与审核能力。

首版不指定供应商及型号。场景判断优先评估快速、低成本模型；材料分析根据真实材料的理解与证据质量选择模型。

### 4.2 固定流程与可编辑数据

模型的职责、输出格式及可执行操作由应用定义。场景描述、用户消息和材料正文作为待处理数据传入，不得据此增加发布权限或运行材料中包含的命令。

用户修改场景或偏好后，应在相关正式版本生效时刷新使用它们的缓存。模型服务不得长期使用启动时读取的一份旧 Persona。

### 4.3 结果追踪

每次分析应有稳定运行标识。维护草稿应能追踪到输入、涉及的记录版本及已提交的提案。

运行元数据默认不保存无关对话全文。为了继续编辑而保存的会话内容应与正式 Persona 分开管理；模型请求只包含完成当前任务所需的数据。

## 5. 功能一：偏好场景触发判定接口

### 5.1 用户目标

调用方提交当前任务内容，AI Persona 判断哪些已启用偏好场景适用。即使输入没有出现触发条件中的原始关键词，也应能够识别语义相同的任务。

例如，场景描述为“撰写或整理学术研究笔记”，输入“把这篇论文整理成便于复习的 Markdown”应有机会命中；仅询问“什么是学术笔记”不应因为出现相同名词而自动命中。

### 5.2 接口定位

拟议服务与 MCP 工具名称：`resolve_persona_activation`。

- 对外至少提供 MCP 接口；内部保留可供 Studio 或宿主适配器复用的服务方法。
- 接口只判断场景，不提前返回完整偏好、知识或样例正文。
- 在服务内部直接调用模型，无需等待主模型先阅读完整场景目录。
- 调用不会修改正式 Persona；执行仍可能产生模型请求费用与运行日志。
- 新工具的 MCP 注解应按实际外部模型访问和副作用设置，不能直接照搬现有本地只读工具的全部注解。

HTTP API 是否作为独立外部接口发布，属于后续技术选项。

### 5.3 输入要求

| 输入 | 要求 | 用途 |
|---|---|---|
| `user_prompt` | 必填、非空 | 当前要判定的内容 |
| `task_summary` | 可选 | 当前任务背景，帮助理解“继续”“改一下”等输入 |
| `recent_messages` | 可选、有长度限制 | 必要的近期对话，带角色标识 |
| `artifact_type` | 可选 | 调用方已知的产物类型；缺省不作为不匹配依据 |

工作区由服务配置确定，不从模型输入接受任意文件路径或工作区切换。首版不要求读取完整会话历史。

示意输入：

```json
{
  "user_prompt": "把刚才讨论的内容整理成学术笔记，方便我以后复习",
  "task_summary": "正在讨论一篇关于张量网络时间演化的论文",
  "artifact_type": "markdown"
}
```

### 5.4 场景配置要求

每个参与判断的场景应能提供名称、适用任务描述、触发条件和排除条件。可进一步提供正反例。

触发说明应支持自然语言编辑。现有 `description` 与 `activation` 字段如何承载完整描述，在 Schema 设计时确定；应保留现有数据，不能要求用户重新填写全部场景。

现有 intents 和 artifact_types 可作为辅助线索，不能作为语义模型看到候选前的唯一门槛。场景数量较少时，建议一次输入全部 active 场景的紧凑描述；后续引入检索时，需要评估候选漏召回。

### 5.5 判断规则

1. 只根据本次读取的已生效、active 场景进行判断；paused、archived 和待审核场景不参与。
2. 结合当前请求、必要背景、适用描述和排除条件做语义判断。
3. 支持零个、一个或多个场景命中，不强制选择单一场景。
4. 区分正在执行某种任务、仅讨论任务概念、引用他人的要求及明确否定该任务。
5. 缺少足以判断的上下文时可以返回不确定，不强行构造匹配理由。
6. 模型返回的场景标识必须属于本次输入目录，服务端负责验证。
7. 场景内某条偏好的 `condition` 是否满足，属于后续偏好选择，不等同于场景已命中。

没有 active 场景时，可直接返回未命中，无需调用模型。未命中场景不表示全局偏好也不适用。

### 5.6 输出要求

成功响应应包含：

- 本次使用的 Persona 版本和场景目录版本；
- 已确认命中的场景及简短理由；
- 仍不确定的场景及缺少的上下文；
- 整体判定状态。

整体状态语义：

| 状态 | 含义 |
|---|---|
| `match` | 至少一个场景确认匹配；其他场景仍可单独列为不确定 |
| `no_match` | 处理范围内没有匹配，也没有待判断场景 |
| `uncertain` | 没有确认匹配，且至少有一个候选因语义或上下文不足不能确定 |

示意成功响应，以下 ID 和版本均为示例：

```json
{
  "ok": true,
  "persona_revision": 42,
  "catalog_version": "catalog-v7",
  "decision": "match",
  "matched_contexts": [
    {
      "key": "academic-note",
      "context_revision": 3,
      "reason": "用户要求将论文讨论内容整理为可复习的学术笔记"
    }
  ],
  "uncertain_contexts": []
}
```

模型超时、不可用、输出解析失败、非法场景 ID 或目录处理不完整应返回明确错误，不得包装成 `no_match`。输出预算不足时也不能静默丢弃命中项，返回看似完整的结果。

### 5.7 与偏好应用流程衔接

```text
调用方提交当前任务
→ resolve_persona_activation
→ 得到命中场景
→ 调用方按固定协议调用 prepare_persona_context
→ 读取并应用相关偏好
```

主模型不需要接收用于分类的完整场景目录。分类所消耗的上下文保留在独立模型请求中，调用方只接收紧凑结果。

接口本身不会监听用户输入或唤醒一个未运行的 AI。Hook、应用请求链或其他宿主适配器负责实际调用；接入具体宿主是独立的适配工作。仅注册 MCP 工具不能保证宿主在每轮调用它。

当前 `prepare_persona_context` 接受单个 `context_key`。多场景命中后，需要确定由调用方逐个读取并去重，或扩展批量读取契约；不能只应用第一个场景而忽略其余命中。

“实际执行过判定”“语义判定正确”“主模型加载并应用偏好”是三项分别需要验证的行为。自然语言描述无法保证百分之百正确分类。

### 5.8 场景调试

建议提供测试入口：输入一段任务内容，展示命中、不确定和排除的原因。用户确认预期结果后，可保存为测试样例。

模型可以生成候选正反例，但测试的预期标签不能仅由同一个模型自行决定。更新场景、提示词或模型后应能重新运行已确认样例。

## 6. 功能二：自然语言维护 Persona

### 6.1 双入口

两种入口均为需求范围，不是二选一：

| 入口 | 默认上下文 | 典型任务 |
|---|---|---|
| Studio 统一助手 | Persona 概览，按需检索相关对象 | 一次整理多条偏好、更新知识状态、跨记录维护 |
| 记录详情页助手 | 当前对象、相关对象及必要来源 | 修改当前偏好、补充材料评价、调整当前知识说明 |

两种入口复用服务、会话和草稿模型。详情页发起的维护可在统一助手中继续，保留上下文和已做编辑。跨对象变化应在预览中说明实际范围。

### 6.2 支持的维护内容

| 对象 | 自然语言维护能力 |
|---|---|
| 偏好场景 | 新增或修改名称、任务描述、触发条件、排除条件及启用状态 |
| 偏好规则 | 新增、补充、调整适用范围与条件、暂停、恢复或归档 |
| 参考样例 | 解释已有样例的优点或问题，建议场景关联及正反例用途 |
| 知识点 | 新增或修改名称、别名、说明、个人掌握范围，以及用户明确要求调整的程度和兴趣 |
| 课程 | 根据现有字段维护名称、简介、大纲、掌握程度与兴趣 |
| 材料 | 维护摘要、阅读关系、个人评价、理解范围及已有类型的关联 |
| 知识关系与标签 | 定位相关对象，建议新增、移除或调整现有 Schema 支持的关系与分类 |

参考样例的新文件继续使用受信任上传/Source 流程。AI 不能凭空生成源文件引用。

对于尚未有正式字段的个人事实，先展示待设计的候选，不把职位、经历等强行塞入知识说明或其他无关字段。本需求不默认增加 ProfileFact 等新实体。

语义相同节点的实体合并涉及引用迁移。首版可以识别并提出合并建议，实际合并操作需单独设计，不伪装成一次普通改名。

### 6.3 标准交互

1. 用户输入维护要求，并可选择当前对象或引用已导入材料。
2. 助手判断是查询解释、提出草稿还是修改当前草稿；“看看哪里可以改”可以只分析。
3. 检索和读取可能涉及的正式对象，确认目标、当前值和版本。
4. 生成结构化变化草稿，区分新增、修改、状态调整及未解决疑点。
5. 用户通过继续对话或手工编辑修改草稿。
6. 提交时再次校验目标版本、引用和依赖。
7. 进入现有人工审核流程，并展示已生效、待处理或失败的实际结果。

### 6.4 典型示例

用户输入：

> 以后学术 note 的公式要解释符号含义，涉及推导时写清楚假设，开头摘要保持简短。

拟议结果：

- 定位已有学术 note 场景；不存在时明确建议新增场景。
- 生成或补充“解释公式符号”的规则。
- 生成或补充“推导时说明假设”的条件规则。
- 生成或补充“摘要简短”的规则。
- 与已有偏好比较，展示重复、补充或范围差异。

用户继续说“第二条只针对不显然的假设”，应修改相应草稿。用户说“第三条不要了”，应移除该草稿项，而不是把未生效的草稿当作正式规则归档。

### 6.5 草稿展示要求

每项变化应展示：

- 目标对象、操作类型和影响范围；
- 当前正式值与建议值；
- 建议理由及用户原话或材料依据；
- 重复项、语义冲突和未解决疑点；
- 与其他变化的依赖；
- 是否由用户手工修改。

界面使用用户能理解的场景名称与字段标签。ID、原始结构及调试信息可折叠显示。

### 6.6 意图与范围保真

- 区分“这次”的临时要求和“以后、默认、每次”的长期要求。
- 保留用户表达的强度：建议、必须和避免不能无依据互换。
- 保留适用条件、例外和否定范围，不能在改写时扩大为全局规则。
- 目标或范围不唯一且会导致不同正式变化时，先展示候选并请求澄清；已明确的独立部分可以先准备草稿。
- 只为完成用户要求读取相关对象，避免把整个 Persona 每轮全部发送给模型。

### 6.7 草稿与审核衔接

支持按项选择、修改、放弃和提交。依赖新场景的规则、依赖新节点的关系，必须明确显示依赖。

当正式记录在草稿生成后被其他操作更新，系统应重新读取并展示冲突或刷新差异，不能覆盖新版本。刷新不得丢失用户已经做出的草稿编辑。

用户对某条候选的拒绝仅影响该维护流程，不自动归纳为新的长期偏好。

## 7. 功能三：根据材料智能维护 Persona

### 7.1 用户目标与输入

用户指定材料和整理目标，系统分析内容、对照已有 Persona，生成可复核的维护候选。

建议首版以已正式导入、绑定不可变 Source 的单份 Material 为入口。新上传文件或 URL 先经过现有导入流程；分析任务可与导入界面衔接，但不能绕开来源保存。

支持的输入至少包括：

- `material_id`；
- 可选关注范围，例如“重点关注数值方法”；
- 可选排除范围，例如“不新增基础背景概念”；
- 期望产出：材料整理、知识与关系、个人状态或偏好候选；
- 执行目标：仅分析草稿，或准备待审核提案。

### 7.2 可产生的维护结果

| 产出 | 具体处理 | 所需依据 |
|---|---|---|
| 材料摘要 | 概括核心问题、方法、结论与局限 | 材料原文；区分阅读覆盖范围 |
| 材料与知识关联 | 复用已有节点，说明知识在材料中的角色与重要性 | 材料实际讨论、使用或依赖的内容 |
| 知识补充 | 新增稳定知识点，补充定义、别名及客观说明 | 可定位、足够支持该说明的原文 |
| 知识关系 | 提出上下位、组成、应用或依赖关系 | 明确语义及支持关系方向的证据 |
| 个人状态候选 | 知识程度、兴趣、阅读关系或理解范围 | 用户明确陈述或其他可核对的个人依据 |
| 偏好与参考样例候选 | 从用户认可/否定的样例或明确陈述中整理规则、条件和样例用途 | 用户评价、使用意图或原文中的明确自述 |

不能仅因材料有某种写法，就推断用户偏好该写法。用户明确说“把这份 note 作为我的写作参考”时，可以提炼可能偏好并交其审核；内容偏好与格式偏好应分别表达。

普通外部论文建议默认分析材料内容及知识关联。涉及个人状态或偏好时，应有相应输入依据，不为凑齐所有产出类型生成候选。

### 7.3 材料内容与个人内容的存储

- 作者原始摘要保留在 `abstract`，AI 内容摘要作为 `summary` 的候选。
- 个人阅读笔记、评价、理解范围继续保留其独立字段，不由 AI 摘要覆盖。
- 材料标题保留正式名称；知识名称、摘要语言按现有材料流程约定处理，用户明确指定时遵循用户。
- 个人状态没有充分依据时保持 `unspecified`。
- 尚无正式实体或字段承接的候选应明确说明，不写入无关字段。

### 7.4 分析流程

1. 核对 Material、Source、来源版本和可用提取文本。
2. 读取材料，记录实际覆盖的章节或范围。
3. 结合用户关注范围，形成少量候选与证据位置。
4. 检索相关正式 Persona，读取潜在重复节点或规则的详情。
5. 判断应复用、补充、新建还是不保留候选。
6. 确认关系类型、方向、重要性和证据是否支持结论。
7. 生成分组草稿，展示新增、补充、已有内容及待判断事项。
8. 用户对话或手工调整，复用自然语言维护的草稿体验。
9. 通过结构和版本校验后，提交有依赖关系的 ChangeSet 供人工审核。

模型可以分阶段调用，阶段间保留结构化结果。关系不能仅由名词共同出现推断。

### 7.5 知识准入与去重

沿用现有材料整理流程中的独立性、稳定性、可复用性、粒度、非重复和证据要求。

- 优先复用已有节点，避免为英文名、中文译名和缩写分别建节点。
- 已有节点可以通过补充别名或说明改善，不必一律新建。
- 只维护有意义的直接关系，避免复制已经可由层级路径推导的祖先关系。
- 单篇材料没有值得新增的知识时，允许只建议材料摘要或已有知识关联，也允许没有变化。
- 草稿服务应识别同一运行或同一材料已有的未完成候选，避免重复提交；未审核候选不能因此变成已生效知识。

### 7.6 证据要求

材料型知识和关系候选应绑定真实 Source 的可定位内容。支持行号的文本使用经服务端验证的相对文件名与行号；模型不能自行编造 hash、文件路径或摘录。

服务端核对位置与内容，界面允许从候选跳转原文。模型另行解释该段文字如何支持候选，位置正确不等于语义证据充分。

如果仅完成摘要或部分章节阅读，结果应标明覆盖范围；不能声称已完整分析全文。缺少可定位内容时可以返回分析说明，但不能提交需要该证据的正式知识或关系提案。

当前偏好实体不能直接承接材料型内联 Evidence 的所有形式。实施时需要为偏好候选定义可追踪的消息/Source 依据映射，复用或扩展提案来源契约；不得向现有 Schema 强塞未知字段。具体方案不预设为新增正式 Preference 字段。

### 7.7 结果界面与继续维护

材料详情页提供智能整理入口，可查看运行状态及历史结果。结果至少区分：

- 材料摘要草稿；
- 拟关联的已有知识；
- 拟新增或补充的 Persona 内容；
- 需要人工判断的歧义；
- 已存在或未保留内容的简短说明。

用户可以从候选进入统一助手继续修改。材料分析产生的同一份草稿不应在不同入口复制成互不相干的版本。

新知识点及引用它的关系使用现有 ChangeSet 依赖机制。只引用已有节点的独立关系可以独立审核。

### 7.8 长任务与重复运行

- 分析任务应支持离开页面后继续运行，重新打开后查看状态和结果。
- 展示实际阶段，例如读取、提取、查重、准备草稿；不能用无依据的精确百分比表示进度。
- 支持取消；已经完成的草稿不因取消后续分析而丢失，未执行阶段不得标为完成。
- 区分成功、有范围限制的部分结果和失败；部分结果需标明遗漏范围。
- Source、Persona 或用户关注范围发生变化后，重新分析应重新检查适用性。
- 同一来源和任务的重试应避免重复提案；已生效结果应在后续查重中识别。

首版建议点击“智能整理”启动。导入后自动分析是可配置的后续选项，尚未确认；无论启动方式如何，分析完成都不自动发布正式变化。

## 8. 工程衔接与兼容要求

### 8.1 共用服务职责

| 服务职责 | 消费方 | 主要结果 |
|---|---|---|
| 模型调用与运行记录 | 三项能力 | 结构化输出、调用状态与版本信息 |
| 场景判定 | MCP、Hook/宿主适配器、测试界面 | 紧凑触发结果 |
| 维护会话与草稿 | 统一助手、详情页助手、材料分析 | 可编辑变化及依据 |
| 材料分析任务 | 材料详情页、后续批量入口 | 草稿、覆盖范围与运行状态 |
| 提案转换与校验 | 自然语言维护、材料分析 | 现有 Proposal / ChangeSet |
| 审核发布 | Studio 人工操作 | 正式记录和投影 |

Studio 内部服务可直接调用领域服务，无需为了复用逻辑绕行一遍 MCP。MCP 作为外部调用接口之一，共用同一套领域规则。

### 8.2 需要补齐的接口点

- 新增场景判定工具及结构化输入输出契约。
- 确定多场景触发后的偏好读取方式。
- 新增维护会话、草稿修改和提交能力；对外开放哪些维护工具需在技术设计中明确。
- 新增材料分析任务的创建、状态读取、取消与结果读取能力。
- 补齐自然语言偏好和材料偏好候选的来源追踪。
- 为新场景及引用其 ID 的新偏好设计同组提交和依赖映射，不能要求模型猜测正式 ID。
- 同步更新旧 MCP 设计中与本次新增 LLM 调用相冲突的说明，保持现有查询和审核契约兼容。

### 8.3 版本、缓存和重复提交

场景判定缓存应至少考虑输入及必要背景、场景目录版本、模型和提示词版本。材料分析缓存还应考虑 Source hash、目标记录版本、关注范围和选定产出。

结果缓存与模型供应商的提示词缓存是不同机制。不能因为当前消息文本相同，就复用另一个任务背景下的判定。

提案提交应复用现有幂等及版本检查。超时后重试同一次提交时使用相同载荷和标识；确认输入或草稿已变化后创建新的逻辑提交。

## 9. 验收标准

### 9.1 场景触发判定

| 编号 | 情况 | 预期 |
|---|---|---|
| A1 | 输入与触发描述语义一致但无原始关键词 | 能在已确认测试样例中正确识别 |
| A2 | 仅讨论场景概念，或明确否定执行该任务 | 不因名词重合自动命中 |
| A3 | 同时符合多个场景 | 返回全部适用结果，不静默只保留第一个 |
| A4 | 场景暂停、归档或修改已发布 | 后续判定使用最新有效目录 |
| A5 | “继续改一下”缺少必要背景 | 返回不确定；提供背景后可重新判断 |
| A6 | 模型超时、非法输出或处理不完整 | 返回明确错误，不伪装成未命中 |
| A7 | 判定未命中 | 不修改 Persona，也不据此关闭全局偏好 |
| A8 | 分类成功 | 主模型可只接收紧凑结果，完整偏好经独立读取获得 |

验收应使用人工确认的正例、反例和边界例，记录漏触发、误触发、不确定率、耗时和费用。具体质量与性能阈值待实际模型试验后确定。

### 9.2 自然语言维护

| 编号 | 情况 | 预期 |
|---|---|---|
| N1 | 从统一入口或详情页进入 | 两种入口均可用，能共享草稿继续编辑 |
| N2 | 一句话涉及多个规则或对象 | 正确拆分并展示影响范围 |
| N3 | 后续要求只修改第二项 | 更新对应草稿，不重复提交其他项 |
| N4 | 用户手工修改字段后继续对话 | 保留编辑，显示后续受影响的差异 |
| N5 | 同义偏好已存在 | 展示复用或补充建议，不盲目重复创建 |
| N6 | 范围、条件或否定不明确 | 说明具体疑点，避免扩大为全局要求 |
| N7 | 目标记录在提交前已更新 | 阻止覆盖，保留草稿并展示版本冲突 |
| N8 | 草稿或提案尚未审核 | 正常 Persona 查询及触发结果不受影响 |
| N9 | 审核部分变化 | 正确处理依赖，准确显示实际生效项 |

### 9.3 基于材料维护

| 编号 | 情况 | 预期 |
|---|---|---|
| M1 | 材料中的方法已有正式节点 | 复用节点并建议合适的材料关系 |
| M2 | 发现稳定、非重复的新知识 | 候选包含客观说明、查重结果与来源依据 |
| M3 | 两个术语仅共同出现 | 不据此生成确定的知识依赖关系 |
| M4 | 论文涉及某主题但无用户状态依据 | 不自动提升用户掌握程度或兴趣 |
| M5 | 用户指定某份 note 为写作参考 | 可提出附带依据的偏好或样例候选，等待审核 |
| M6 | 原始摘要、AI 摘要与个人笔记均存在 | 保持各自含义，避免相互覆盖 |
| M7 | 只分析了部分章节或文本不可定位 | 明确覆盖范围，缺证据的变化不提交 |
| M8 | 同一分析重试或重新打开 | 不重复创建同一批提案，可继续编辑已有结果 |
| M9 | 分析期间 Source 或目标记录改变 | 提交前发现变化并要求刷新分析或草稿 |
| M10 | 材料无值得保留的新内容 | 可以返回零候选，并解释原因 |

### 9.4 共用验收

- 模型不可用时，原有手工维护与正式数据查询仍可使用。
- 模型产物只能通过合法领域操作形成提案，不绕过审核直接发布。
- 场景说明或原文中包含工具指令时，不扩大模型权限。
- 能追踪一次结果使用的模型、提示词、Persona 与 Source 版本。
- 评估维护效果时同时观察候选接受率、用户修改量、重复率和证据质量，而非仅统计生成数量。

## 10. 实施分期与待定事项

### 10.1 建议分期

1. **共用基础与场景判定**：配置模型服务，新增判定接口、版本刷新及人工标注测试集。
2. **自然语言维护**：实现统一入口和详情页入口、对象检索、多轮草稿、差异预览与审核衔接。
3. **材料维护**：实现单份正式材料的分析任务、知识查重、来源证据及复用维护草稿。
4. **体验完善**：依据实际使用反馈增加批量处理、可选自动分析及更完整的场景调试界面。

分期是实现顺序；三项能力和自然语言维护的两个入口均属于总体交付目标。

### 10.2 待确认决策

| 问题 | 当前建议 | 状态 |
|---|---|---|
| 具体模型与供应商 | 按分类、维护、材料分析分别测试，可复用同一模型 | 待选型 |
| 触发描述的字段形式 | 优先兼容现有 description 与 activation，提供清楚的自然语言编辑入口 | 待 Schema 设计 |
| 是否提供独立 HTTP 接口 | 首版提供 MCP 与内部服务方法 | 待接入需求 |
| 接入哪个宿主的自动触发 | 判定服务保持宿主无关，具体 Hook/请求链单独适配 | 待集成选择 |
| 多场景偏好读取 | 明确批量读取或逐个读取加去重的契约 | 待接口设计 |
| 导入后自动分析 | 首版手动启动，后续可配置自动分析 | 用户尚未选择 |
| 首版批量材料 | 先单份材料，保留任务队列扩展能力 | 建议待确认 |
| 偏好候选的来源结构 | 消息与 Source 均可追溯，与现有 Evidence/Proposal 协同 | 待存储设计 |
| 性能、费用与质量阈值 | 用真实任务和材料测量后确定 | 待评测 |

### 10.3 本次范围之外

本需求不包含每日扫描全部历史对话、论文推荐系统、研究 idea 自动生成、通用个人事实新模型、多用户协作、自动审核发布或永久删除。

单条偏好 `condition` 的语义求值与复杂冲突裁决，可在后续偏好应用阶段扩展；首版场景判定必须保留这一区别，不能将场景命中解释为其中所有规则均无条件适用。

本次文档交付不代表以上功能已经实现，也不要求现在连接模型账户、启用 Hook 或启动自动分析。
