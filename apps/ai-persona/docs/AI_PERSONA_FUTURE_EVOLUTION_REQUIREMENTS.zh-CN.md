## 1. 文档目的

本文记录 AI Persona 下一阶段可能增加的四组需求及初步设计意见，供后续逐项讨论和拆分实施。

本文不是最终技术方案，也不表示所有建议都已经确定。后续实施前仍需明确数据语义、隐私边界、来源接入方式、自动化权限和验收标准。

## 2. 总体目标

下一阶段希望将 AI Persona 从一份需要主动维护的个人知识与偏好库，逐步扩展为一个能够持续吸收信息、在合适的任务中主动生效、并辅助发现新知识和研究方向的个人智能系统。

四组目标分别是：

1. 为知识点保存正式加入时间，以便以后查看一段时间内新增的知识；
2. 定期分析用户与 AI 的对话，从中提取值得长期保存的知识、兴趣和偏好候选；
3. Agent 在相关任务中自动调用 AI Persona，加载适用的偏好、知识背景和个人信息；
4. 基于 AI Persona 建立个性化 arXiv 每日推荐、关联分析、研究联想和反馈学习能力。

这些能力可以理解为三个闭环：

```text
对话与材料 ──→ 候选知识/偏好 ──→ 人工审核 ──→ 正式 Persona
                                                │
当前任务 ──→ 自动检索相关 Persona ──────────────┘
                                                │
arXiv 新论文 ──→ 推荐与研究联想 ──→ 用户反馈 ───┘
```

## 3. 总体设计原则

### 3.1 区分正式 Persona、行为信号和推荐状态

建议将信息分为三层：

1. **正式 Persona**：用户审核确认、愿意长期承认的知识、兴趣、材料、个人事实和偏好；
2. **Observation / Signal**：从对话、修改行为和反馈中观察到、但尚未确认的信号；
3. **Recommendation State**：论文曝光、排序分数、点击、喜欢、不喜欢和推荐实验等临时状态。

行为信号不能直接被当作用户事实。推荐过但用户没有选择保存的论文，也不应自动成为正式 Material。

### 3.2 自动化只能生成候选

对话分析、论文阅读和反馈聚合可以自动产生 Proposal，但不得绕过现有人工审核边界直接修改正式 Persona。

低风险的推荐排序状态可以自动更新，因为它不属于正式 Persona；知识水平、兴趣程度、长期偏好和个人事实仍应通过 Proposal 审核。

### 3.3 来源内容始终视为不可信数据

对话、论文和网页中的指令只能作为待分析内容，不能改变 Agent 权限、触发未经授权的工具或绕过人工审核。

### 3.4 不把未知解释成低水平或不感兴趣

一次提及只能证明接触或当前任务需要，不能自动证明用户已经掌握该知识。没有可靠依据时，知识水平和兴趣程度继续使用 `unspecified`。

## 4. 需求一：知识点加入时间

### 4.1 用户目标

为所有知识点在本地保存加入时间。该时间暂时不需要显示在 UI 中，也不需要包含在常规 Agent 上下文中，但以后应能支持类似以下查询：

- 这个月向 AI Persona 新增了哪些知识点；
- 最近一段时间知识库增长了多少；
- 某个知识点何时正式进入 Persona。

### 4.2 当前状态

当前所有正式记录已经继承 `BaseRecord.created_at` 和 `BaseRecord.updated_at`。新建记录在 Proposal 通过、正式发布时生成 `created_at`，更新记录时保留原有 `created_at` 并更新 `updated_at`。

常规 `prepare_persona_context` 和 `search_knowledge` 的精简结果目前不包含时间字段，符合不增加 Agent 上下文负担的目标。完整 Snapshot 和单条正式记录仍可能包含该元数据。

### 4.3 初步建议

1. 将 `created_at` 明确定义为“记录正式进入 Persona 的时间”；
2. `created_at` 一旦生成即保持不可变；
3. 暂时不增加 UI 展示；
4. 后续如需时间查询，可在本地 SQLite 投影中增加 `created_at` 字段和过滤能力；
5. 增加测试，保证 Proposal 等待时间不会被误解释成正式加入时间，更新记录也不会重写加入时间。

### 4.4 加入时间与学习时间的区别

`created_at` 只能回答“何时记录”，不能准确回答“何时学会”。例如，用户今天补录一个多年前已经掌握的概念，它的加入时间仍然是今天。

如果以后需要追踪真实学习过程，可以另行设计 `KnowledgeStateEvent`，记录：

- 首次接触某个知识；
- 从 `unspecified` 或 `aware` 变为 `familiar`；
- 从 `familiar` 变为 `proficient`；
- 兴趣程度发生变化；
- 事件实际发生时间 `occurred_at`；
- 系统记录时间 `recorded_at`。

第一阶段不需要为此修改现有知识模型。

## 5. 需求二：从每日对话中提取 Persona 候选

### 5.1 用户目标

设置一个定时任务，例如每天凌晨运行，读取自上次成功处理之后产生的 AI 对话，并从中发现可以加入 AI Persona 的内容。

典型例子：

- 用户说“生成一份详细介绍 QMC 的 note”，系统可以把 QMC 识别为知识候选；
- 用户对生成的 note 提出修改要求，系统可以判断其中是否包含值得长期保存的写作偏好；
- 用户明确表达兴趣、知识程度、材料评价或工作习惯时，系统可以生成相应 Proposal。

### 5.2 建议的数据流

```text
Conversation Source
        │
        ▼
不可变 Source / 受控对话记录
        │
        ▼
Observation / Signal
        │
        ├── 去重与聚合
        ├── 判断是否具有长期意义
        ├── 检查已有正式记录和 Pending Proposal
        └── 生成证据定位与置信度
        │
        ▼
ChangeSet Proposal
        │
        ▼
用户在 Studio 审核
```

### 5.3 建议增加的 Observation

Observation 是未生效的行为信号，可以包含：

- 来源提供者、会话 ID 和消息 ID；
- 原始对话的稳定 Source ID 和内容 hash；
- 信号发生时间与提取时间；
- 信号类型；
- 相关知识、材料、偏好场景或个人事实；
- 原文消息定位；
- 置信度和提取规则版本；
- `new`、`aggregated`、`proposed`、`dismissed`、`expired` 等处理状态。

Observation 不进入正常 Persona 检索结果，也不影响 Agent 行为。

### 5.4 可从对话中识别的内容

| 对话信号 | 候选处理方式 | 默认边界 |
|---|---|---|
| 要求生成某个主题的详细 note | Knowledge Node 候选或短期兴趣信号 | 不自动判断为熟悉或精通 |
| 生成结果被保存、认可或继续深入修改 | Material 候选及 Material–Knowledge Relation | 用户选择保存后再提交 |
| “以后”“每次”“默认”“不要”等长期表述 | Preference Proposal | 明确长期表述可使用较高置信度 |
| 只针对当前结果的修改 | 当前任务约束或 Observation | 默认不形成长期偏好 |
| 多个独立任务中反复出现的同类修改 | `inferred_pattern` Preference Proposal | 必须保留多条证据并人工审核 |
| 用户明确表达喜欢或关注某方向 | Interest Proposal | 区分当前关注与长期兴趣 |
| 用户表示不理解、刚开始学习或已经熟练使用 | Knowledge Level Proposal | 需要明确陈述或较强证据 |
| 用户纠正术语、别名、概念关系或事实 | Alias、Summary 或 Relation Proposal | 不自动覆盖已确认信息 |
| 用户提出研究问题或组合方向 | Idea / Research Question 候选 | 不作为已确认知识事实 |
| 用户提供职位、单位、研究领域或工作环境 | ProfileFact Proposal | 需要隐私和可见范围控制 |
| 用户对论文、note、图或其他产物作评价 | Material feedback、Preference 或参考样例 | 区分内容评价与格式偏好 |

### 5.5 QMC 示例的建议处理

“给我生成一个详细介绍 QMC 的 note”可以支持：

- QMC 作为一个值得检查的知识候选；
- 用户当前对 QMC 有任务需求；
- 如果 note 被保存，可以形成一个 Material 候选；
- Material 可以和 QMC 建立 `covers` 关系。

它本身不能证明用户已经熟悉或掌握 QMC，因此默认 `knowledge_level=unspecified`。是否形成长期兴趣也需要更多上下文或用户审核。

如果用户随后说“这次把推导部分写详细一些”，只修改当前任务。如果用户说“以后所有技术 note 都要保留详细推导”，则可以生成 `note.write` 场景下的 Preference Proposal。

### 5.6 定时任务和增量处理

不建议仅使用自然日边界读取“今天的对话”。系统应为每个来源保存 checkpoint：

- `last_successful_message_id`；
- `last_successful_timestamp`；
- `last_run_id`；
- 来源自身的 cursor 或 revision。

每次处理 `(last_checkpoint, current_watermark]`。这样即使任务延迟、失败或电脑关机，也不会丢失或重复处理对话。

第一版建议只接入一个来源，并支持会话或项目 allowlist。对话来源可以是 Cortex、Codex 或其他系统，但每种来源都需要独立 adapter，负责读取、规范化、定位、去重和保存 checkpoint。

### 5.7 审核体验

每日任务应产生一份简短摘要，例如：

- 发现 2 个知识候选；
- 发现 1 个可能的长期写作偏好；
- 聚合了 3 条重复修改信号；
- 忽略 8 条只与当前任务有关的临时要求；
- 没有发现值得进入 Persona 的内容。

建议按天或按会话生成 ChangeSet，避免让用户逐条处理大量低价值 Proposal。

### 5.8 隐私和保留策略

实施前需要决定：

- 哪些会话允许扫描；
- 是否保存完整对话，还是只保存带 hash 的最小证据片段；
- Source 是否加密；
- 原始对话和 Observation 的保留期限；
- 哪些项目、联系人或主题默认排除；
- 提取是否必须使用本地模型。

## 6. 需求三：Agent 自动加载偏好、知识和个人信息

### 6.1 用户目标

AI Persona 接入 Codex 或其他 Agent 后，在相关任务中自动生效：

- 写 note 时自动应用 `note.write` 偏好；
- 以后增加科研绘图等新任务场景；
- 回答依赖用户背景的问题时，自动查询用户已经掌握哪些知识；
- 需要用户个人信息时，只读取与当前任务相关且允许暴露的信息；
- 不要求用户每次显式提醒 Agent 调用 AI Persona。

### 6.2 推荐的三层触发机制

#### 第一层：MCP 负责提供数据和统一入口

继续使用 `prepare_persona_context` 作为首选入口。Agent 为一个任务只需先调用一次，并提供：

- 当前任务描述；
- 当前问题或主题；
- 可选 `context_key`；
- 可选 `artifact_type`；
- 上下文预算。

建议返回：

- 相关知识及知识水平；
- 相关材料和关系；
- 适用偏好；
- 正反参考样例；
- 允许返回的个人事实；
- 未知项；
- 推荐解释深度；
- `persona_revision`。

只有需要查看更多证据或长材料时，Agent 才继续调用细粒度工具。

#### 第二层：Skill 负责描述任务工作流

建议建立一个全局 `ai-persona-runtime` Skill。其触发描述应明确包含：

- 写作、修改或评审 note；
- 科研绘图和图注生成；
- 论文解释、文献推荐和研究联想；
- 用户要求根据其背景、偏好、已有知识或历史材料回答；
- 回答质量会明显依赖用户知识程度或个人信息的任务。

Skill 同时应明确不触发的场景，例如与个人背景无关的简单文件操作、格式化和一般事实查询。

Skill 只保存“何时和如何查询 Persona”的工作流，不复制具体偏好内容。具体偏好始终由 MCP 动态读取。

#### 第三层：Agent 宿主保存稳定元规则

对于 Codex，可以在全局或项目级 `AGENTS.md` 中加入一条短元规则：

> 当任务结果会因用户的知识背景、个人资料、长期偏好或参考样例而显著变化时，在生成结果前调用 AI Persona 的 `prepare_persona_context`。只使用已审核信息；未知信息不得自行补全。

`AGENTS.md` 不保存“note 应该怎么写”等具体偏好，防止它与 AI Persona 形成两套事实来源。

如果以后构建自有 Agent wrapper，最可靠的方式是由外部路由器在匹配场景下强制执行 Persona preflight，而不是完全依赖模型自主决定是否调用工具。

### 6.3 偏好场景设计

当前 `PreferenceContext` 已支持稳定 `key`、`intents`、`artifact_types` 和 `excludes`。建议继续使用可扩展场景，例如：

- `note.write`；
- `note.revise`；
- `figure.research`；
- `paper.explain`；
- `research.ideate`；
- `recommend.paper`。

Agent 能确定场景时应显式传入 `context_key`。无法确定时，AI Persona 可以根据任务文字和 `artifact_type` 匹配。具体匹配规则需要通过正反例评测，不能只依赖少量英文关键词。

### 6.4 建议新增 ProfileFact

知识和偏好不能完整表达职位、单位、语言、时区、设备、经历或工作环境。建议增加独立 `ProfileFact`：

- 稳定 `key` 和结构化 `value`；
- 事实类别；
- 适用任务场景；
- 来源与 Evidence；
- `valid_from`、`valid_until` 或是否可能过期；
- 敏感级别；
- Agent 可见范围；
- revision 和审核状态。

可见范围可以包括：

- `agent_default`：相关任务中可以自动返回；
- `explicit_only`：只有用户明确要求使用时返回；
- `local_only`：不得进入外部模型上下文。

本地保存不等于可以无条件返回给模型，因此 ProfileFact 必须在检索层执行最小披露。

### 6.5 触发规则建议

以下场景应优先调用 Persona：

- 用户使用“我的”“根据我以前的”“按我的习惯”等表达；
- 任务要求生成长期产物；
- 任务属于已配置的 Preference Context；
- 解释深度应根据用户已有知识调整；
- 需要引用用户已有材料或研究方向；
- 需要个人信息才能正确生成内容。

以下场景通常不需要调用：

- 与用户背景无关的一步式事实查询；
- 简单文件查看、移动或格式化；
- 调用不会改变答案的低价值场景。

### 6.6 需要建立的评测

建议建立一组触发测试：

- 应当调用且成功调用；
- 应当调用但遗漏；
- 不应调用但误调用；
- 场景匹配正确但偏好选择错误；
- 未知知识被错误解释为低水平；
- 敏感 ProfileFact 被不恰当地返回；
- Preference 冲突时没有遵循更具体规则；
- Persona revision 更新后使用了旧缓存。

## 7. 需求四：个性化 arXiv 每日推荐与研究联想

### 7.1 用户目标

系统每天读取 arXiv 新上传或新公布的文章，选择可能感兴趣的论文，并提供：

- 推荐理由；
- 与 Persona 中已有知识点、材料、论文或研究方向的联系；
- 可采取的阅读、验证或研究行动；
- 多篇文章与既有知识结合后产生的研究联想；
- 少量可供用户判断的结构化 idea；
- 根据喜欢、不喜欢和后续行为持续改进的推荐排序。

### 7.2 实现难度判断

| 模块 | 初步难度 |
|---|---|
| 每日获取指定分类的新论文 | 低 |
| 根据标题和摘要进行兴趣筛选 | 中 |
| 与 Persona 知识和材料建立可信联系 | 中等偏高 |
| 阅读全文并生成准确推荐理由 | 中等偏高 |
| 根据长期反馈稳定改进排序 | 中高 |
| 生成新颖、可验证且非空泛拼接的研究 idea | 高 |

获取论文不是主要难点。长期推荐质量、反馈建模、避免信息茧房和保证 idea 有依据才是核心挑战。

### 7.3 与现有 arXiv 导入能力的关系

当前 arXiv 导入模块已经支持：

- 识别和规范化 arXiv ID；
- 读取结构化元数据；
- 下载指定版本 PDF；
- 尝试读取官方 HTML；
- 生成可供 Agent 阅读的提取文本；
- 保存不可变 Source。

新增推荐系统可以复用单篇论文获取和 Source 保存逻辑，但还需要单独实现：

- 每日候选发现；
- feed checkpoint；
- 候选去重和版本处理；
- 排序特征；
- 推荐结果存储；
- 用户反馈；
- 关联解释；
- idea 生成和评估。

### 7.4 建议建立独立 Recommendation Store

```text
arXiv Feed
   │
   ▼
RecommendationCandidate
   │
   ├── 元数据和摘要粗筛
   ├── 去重与已看过过滤
   ├── Persona 相关性排序
   └── 新颖性与多样性控制
   │
   ▼
只阅读排名靠前的全文
   │
   ▼
Daily Recommendation
   │
   ├── 用户反馈 → 推荐模型状态
   └── 用户选择保存 → Material Proposal
```

推荐候选、曝光记录和反馈不属于正式 Persona，可以保存在独立 SQLite 状态中。只有用户点击“加入知识库”或明确保存时，才创建 Material Proposal。

### 7.5 分阶段排序流程

#### 阶段一：候选召回

根据以下信息确定 arXiv 分类、关键词和兴趣主题：

- 高兴趣 Knowledge Node；
- 已喜欢或收藏的 Material；
- 已有论文的作者、方法、模型和研究问题；
- 当前研究项目和 ProfileFact；
- 用户显式配置的关注与排除主题。

不建议将所有兴趣压缩成一个总 embedding。可以维护多个兴趣簇，例如研究对象、理论方法、数值方法和应用方向。

#### 阶段二：低成本粗排

使用标题、摘要、作者、分类和与 Persona 的文本或 embedding 相似度，对较大候选池进行排序。过滤：

- 已推荐且明确不感兴趣的论文；
- 已在 Persona 中存在的相同 arXiv base ID；
- 只是新版本但用户不希望重复推荐的论文；
- 明确排除的主题。

#### 阶段三：全文分析

只对粗排靠前的少量论文下载或读取全文。分析重点包括：

- 核心问题；
- 主要方法；
- 主要结论；
- 与用户已有工作的直接联系；
- 是否提供新的方法、机制、数据或可验证方向；
- 对用户而言是过于基础、难度适中还是需要额外背景。

#### 阶段四：最终推荐

每天只推荐少量论文，例如 3–5 篇。每篇至少说明：

- 为什么推荐；
- 与哪些 Persona Knowledge Node 相关；
- 与哪些已有 Material 相关；
- 关系属于直接证据、语义相似还是推测性联想；
- 推荐精读、略读、保存、复现还是忽略；
- 一个最值得关注的问题。

### 7.6 研究联想和 IdeaCandidate

Idea 不应作为普通推荐文字的一句附加内容。建议使用结构化 `IdeaCandidate`：

- 结合了哪些新论文、已有材料和知识点；
- 核心研究问题；
- 假设或可能机制；
- 为什么对用户有意义；
- 最小可行验证方法；
- 需要的数据、解析、实验或数值工具；
- 预期观察信号；
- 主要风险与可能失败的原因；
- 第一个可立即执行的步骤；
- 哪些部分有来源支持，哪些部分是模型推测；
- 用户反馈和后续状态。

只有用户明确选择追踪时，IdeaCandidate 才进入长期项目或 Persona 相关记录。

### 7.7 用户反馈设计

仅有“喜欢/不喜欢”不足以区分推荐错误的原因。建议支持：

- 主题不相关；
- 主题相关，但论文价值不高；
- 已经读过或已经知道；
- 太基础；
- 太困难或缺少前置知识；
- 偏离当前研究重点；
- 方法有价值；
- 结果有价值；
- 值得精读；
- 值得保存；
- 推荐理由准确或不准确；
- idea 有启发或没有启发。

这些反馈首先更新 Recommendation State。只有多次反馈形成稳定兴趣或偏好模式时，系统才生成 Persona Proposal。

### 7.8 推荐模型演进

第一版可以使用可解释的规则和权重：

- 主题相似度；
- 与高兴趣知识点的关系；
- 与喜欢材料的相似度；
- 作者或方法匹配；
- 新颖性；
- 最近反馈；
- 重复惩罚；
- 多样性奖励。

积累反馈后再增加在线排序模型。系统应保留一定比例的探索候选，避免只推荐与现有兴趣高度相似的论文。

建议记录每次推荐时的候选池、特征、分数、模型版本和展示位置，以便以后离线评估，而不是只保存用户最终喜欢的论文。

### 7.9 调度与 arXiv 使用边界

推荐任务应使用 feed watermark 和 arXiv ID 去重，不依赖固定凌晨时间来判断哪些论文是“今天新增”。

应遵守 arXiv 官方 API 的查询、分页、缓存和请求间隔建议。同一查询每天通常只需要获取一次；大候选池先读取元数据和摘要，不应立即批量下载全部 PDF。

## 8. 建议实施顺序

### 阶段 A：补齐基础语义

1. 明确 `created_at` 是正式加入时间；
2. 增加时间不可变性测试；
3. 决定是否增加 ProfileFact；
4. 定义 ProfileFact 的敏感级别和 Agent 可见范围；
5. 定义 Observation 与 Recommendation State 的边界。

### 阶段 B：先让 Persona 在 Agent 中稳定生效

1. 建立 `ai-persona-runtime` Skill；
2. 增加 Codex/Agent 的稳定元规则；
3. 完善 Preference Context 激活词和 artifact type；
4. 为 note.write 建立端到端触发测试；
5. 验证相关任务会调用、不相关任务不会过度调用。

### 阶段 C：实现对话增量提取

1. 只选择一个对话来源；
2. 实现 source adapter、checkpoint 和幂等处理；
3. 保存 Conversation Source 和 Observation；
4. 第一版只识别显式长期偏好、新知识候选和明确兴趣反馈；
5. 生成每日 ChangeSet 和审核摘要；
6. 评估误报、漏报和用户审核负担。

### 阶段 D：实现 arXiv 推荐 MVP

1. 配置少量 arXiv 分类；
2. 每日拉取元数据和摘要；
3. 使用规则、FTS 或 embedding 粗排；
4. 阅读少量排名靠前的全文；
5. 每天输出 3–5 篇带解释的推荐；
6. 收集结构化反馈；
7. 用户选择后才创建 Material Proposal。

### 阶段 E：增加高级推荐能力

1. 与知识图谱和已有材料建立多跳关联；
2. 增加结构化 IdeaCandidate；
3. 引入在线排序和兴趣衰减；
4. 增加探索、多样性和反信息茧房策略；
5. 建立推荐质量和 idea 有用性的长期评测。

## 9. 后续需要讨论和决定的问题

### 9.1 时间语义

1. “本月新学了什么”是指新加入 Persona，还是知识水平实际发生变化？
2. 是否需要允许用户补填真实的学习时间？
3. 是否需要记录知识水平变化事件？

### 9.2 对话来源和隐私

1. 第一版接入 Cortex、Codex 还是其他来源？
2. 是否保存完整对话？
3. 哪些会话、项目或主题默认排除？
4. 对话内容允许发送给哪些模型？
5. Observation 保存多久？

### 9.3 偏好推断

1. 一次修改是否只形成 Observation？
2. 需要重复多少次才生成 inferred Preference Proposal？
3. 明确使用“以后”“总是”等词时，是否直接生成 Proposal？
4. 用户拒绝某个推断后，多长时间内不再重复提出？

### 9.4 Agent 触发

1. 哪些场景必须调用 Persona？
2. 哪些场景不允许调用？
3. ProfileFact 应有哪些敏感等级？
4. 本地 Agent 与远程模型应使用相同还是不同的可见范围？
5. 是否需要为不同 Agent 配置不同的授权 profile？

### 9.5 arXiv 推荐

1. 第一版关注哪些分类？
2. 每天希望看到多少篇论文？
3. 用户更重视主题相关、方法新颖、潜在合作还是可立即使用？
4. arXiv 新版本是否重新推荐？
5. 是否允许推荐相对陌生但可能有启发的方向？
6. Idea 应只显示，还是可以进入独立的研究想法工作区？

## 10. 当前建议结论

下一阶段最重要的不是让系统收集尽可能多的信息，而是建立可靠的信息升级路径：

```text
一次行为
  → 可追溯 Observation
  → 多次证据或明确陈述
  → 待审核 Proposal
  → 用户确认的正式 Persona
```

正式 Persona 应保持精炼、可信、可追溯。对话分析负责发现候选，Agent 触发负责消费已确认信息，arXiv 推荐负责探索外部知识；三者共享 Persona，但各自的临时状态应相互隔离。

按照“先运行时触发，再对话提取，最后推荐学习”的顺序推进，可以较早获得实际收益，也能避免在消费机制尚未稳定前积累大量低质量信息。
