## 1. 已确定的设计原则

1. 日常处理、正式资产维护、质量评测、系统设置各有明确入口，不按后端模块拆成互相重叠的页面。
2. 结果记录、人工反馈、内容审核、测试样例是四种不同对象；页面可以组合展示，但不能混淆它们的含义。
3. 人工反馈是可选行为，不是阅读结果、审核候选或使用 Persona 的前置条件。
4. 满意／不满意只用于当前已支持的二元触发判断：对话学习、偏好场景判定。不评价模糊的“整体体验”。
5. 材料整理、自然语言维护和其他 AI／MCP 候选继续支持审核，本次不为它们补造反馈或 benchmark。
6. 审核通过、修改后通过、拒绝、暂缓均不能推导满意度或反转触发标签。
7. 只有用户明确点击满意／不满意，才建立个人测试样例。审核成功仅为符合关联条件的已有样例提供内容答案。
8. 同一结果可以从多个上下文进入，但使用同一份反馈、候选和审核状态，不建设第二套可写数据。
9. 普通用户手动维护正式记录仍然保存即生效，不因统一审核入口而重新增加一次审核。
10. 打开、筛选、切换页面和查看详情均不调用模型、不启停后台、不提交反馈、不更改 Persona。

## 2. 当前问题与改版目标

### 2.1 当前页面的问题

| 问题 | 当前表现 | 改版方向 |
| --- | --- | --- |
| 反馈入口分散 | 对话学习、偏好应用记录、评测页最近结果和样例详情都能评价 | 一个日常反馈主入口，多处上下文链接指向同一详情 |
| 相似能力层级不同 | 对话学习有侧栏入口；偏好应用记录位于偏好页内 | 两种能力作为统一工作台的筛选维度 |
| 反馈与评测混排 | 日常满意度与版本、模型、预算、报告出现在同一页 | 日常处理与质量验证分开 |
| 审核体验不统一 | 学习页可原位审核，维护助手主要跳转审核页 | 共用候选详情与审核组件，保留继续对话的入口 |
| 设置归属不清 | 共用来源连接放在对话学习内，偏好应用需返回此处配置 | 共享来源、模型及运行配置进入设置 |
| 状态容易误读 | 完成、已提供偏好、已反馈、已审核互相邻接 | 运行、判断、反馈、审核分别表达 |
| 输入展示不一致 | 部分测试样例标题混入宿主浏览器上下文标签 | 共用用户正文展示投影，不改写原始快照 |
| 首页偏重静态统计 | 知识数量、掌握程度、版本信息优先 | 提升待审核内容、异常与最近更新的可见性 |

问题不在于必须删除所有重复链接，而在于用户缺少唯一、可预期的处理流程。材料页、偏好页可以保留“查看相关结果”，但不再各自维护完整的平行反馈中心。

### 2.2 本轮不做什么

- 不调整学习提示词、触发边界、模型路由、Hook 执行机制或来源信任策略。
- 不新增材料整理、自然语言维护、模型连接测试、知识召回等能力的反馈和评分。
- 不自动优化提示词、运行回测、采纳候选或根据审核结果推断用户满意度。
- 不合并知识、课程、材料、偏好的业务模型，不改动正式数据目录和备份归属。
- 不把技术调用日志、所有阶段输出和每条聊天消息都变成需要人工处理的结果。

## 3. 全局导航与页面职责

### 3.1 目标导航

| 主区域 | 用户目的 | 子页面／功能 |
| --- | --- | --- |
| 总览 | 现在有什么值得关注 | 待审核、异常、最近更新、资产摘要 |
| 我的 Persona | 查看和维护已经保存的信息 | 知识、课程、材料、偏好；关系保留在相应对象与知识图中 |
| 反馈与审核 | 评价一次判断，决定保存哪些内容 | 待审核、可反馈、全部记录 |
| 评测与改进 | 验证提示词或学习方式调整是否有效 | 开始检查、测试样例、历史记录 |
| 设置 | 配置接入与运行方式 | 模型设置、应用接入、自动功能、数据管理 |

“我的 Persona”首先是导航分组，不新增一个必须经过的目录页；知识、课程、材料、偏好仍可直接进入。材料的正式记录与原文仍按既有结构保存，不因导航分组改变语义。

AI 维护助手作为稳定的“让 AI 帮我维护”操作入口保留，并支持从资产详情带上下文进入。它仍有独立的对话页面与任务历史，不再承担另一套日常反馈中心。窄屏也必须能找到此入口，不只依赖鼠标悬停菜单。

### 3.2 各区域的责任边界

- **正式资产区：** 展示当前生效内容；从这里手工编辑仍直接保存。参考示例属于偏好配置，不属于评测样例。
- **反馈与审核：** 处理真实业务结果；反馈只改反馈数据，审核才可能发布 Persona。
- **评测与改进：** 使用明确收录的样例验证版本；评测输出不进入真实待审核队列。
- **设置：** 配置来源、模型、预算与运行；不夹带日常候选编辑。
- **AI 维护助手：** 发起和继续维护对话；已有候选使用同一审核组件或进入同一工作台详情。

## 4. 结果类型与可用操作

### 4.1 能力矩阵

| 结果来源 | 触发反馈 | 内容审核 | 本轮是否支持形成个人测试样例 |
| --- | --- | --- | --- |
| 对话学习 | 有有效二元判断时支持，包括不触发 | 有候选时支持；无候选不显示审核空表单 | 明确反馈后支持；可关联对应审核答案 |
| 偏好场景判定／应用 | 对本轮具体场景分别评价 | 不需要 | 明确评价的场景形成标签 |
| 材料智能整理 | 不支持 | 支持 | 不支持，审核通过不自动收录 |
| 自然语言维护 | 不支持 | 支持 | 不支持，审核通过不自动收录 |
| 其他 AI／MCP 提案 | 未单独接入时不支持 | 沿用现有审核能力 | 不支持，不能仅凭“由 AI 生成”自动接入 |
| 模型连接测试、内部阶段调用日志 | 不支持 | 不需要 | 不支持；保留在设置／诊断记录中 |

能力由业务适配器声明，实际按钮再由本次结果的有效判断、候选、权限和版本决定。不能因为页面共用，就假设每个结果都有 `result_id`、触发判断或反馈接口。

### 4.2 不支持、尚不可用与未反馈的区别

- **不支持反馈：** 该业务没有反馈能力。页面不展示反馈区，不显示“未反馈”，不进入可反馈视图。
- **支持，但尚无有效判断：** 显示处理中或判定未完成，不显示可提交的满意度按钮。
- **有有效判断，未评价：** 显示“未反馈”，允许明确评价。
- **反馈状态读取失败：** 显示“反馈状态暂不可用”，禁用相关写入并提供重试读取；不得冒充未反馈。
- **输入已过期：** 若原判定和身份仍可核验，按既有反馈契约保留明确点击和标签，标明“缺少回放输入”，不加入可执行回测集合；原判定不可恢复时禁用反馈。已有样例快照仍可用时不受临时记录清理影响，禁止重新读取宿主聊天或补造上下文。

后续新增业务时，可以只注册审核，也可以只注册反馈。为新业务定义反馈含义和样例规则属于独立产品需求，不是增加一对通用满意度按钮就算完成。

## 5. “反馈与审核”工作台

### 5.1 页面结构

采用“筛选与记录列表＋常驻详情”的主从布局：

1. 页头：标题、一句说明、必要的运行异常提示。
2. 主视图切换：待审核／可反馈／全部记录。
3. 搜索与业务类型筛选；来源、时间、反馈及运行状态收在更多筛选中。
4. 左侧紧凑记录列表，右侧展示选中记录的完整处理界面。
5. 窄屏改为列表与详情二选一，返回时恢复列表位置。

不在列表底部追加详情，不把模型设置、来源表单和回测配置放进主工作区。来源关闭、模型异常等仅用简短状态和定向链接提示。

### 5.2 三个主视图

| 视图 | 包含的记录 | 默认顺序与交互 |
| --- | --- | --- |
| 待审核 | 存在尚未最终决定的候选；暂缓、依赖未满足单独标识 | 默认按收到时间倒序，组内按依赖顺序；可切换最早优先 |
| 可反馈 | 至少存在一个可评价、当前未评价的有效判断 | 默认按收到时间倒序；包含触发与不触发；不包含不支持反馈的结果 |
| 全部记录 | 各来源可读取的任务、结果与审核历史 | 支持已反馈、审核完成、运行异常、业务类型等筛选 |

首次进入默认“待审核”；有明确深链接时以链接为准。待审核为空时提供“查看可反馈判断”的入口，不自动切换用户选中的视图。

可反馈表示可选择参与，不代表用户欠下的待办；不要求全部清空，不用红色角标累计所有未评价的自动任务。侧栏数字仅表示未最终审核的候选数，按唯一 `proposal_id` 去重，并明确单位“条候选”。视图列表数量以“条记录”计，两者不能混用。

同一记录可同时出现在待审核和可反馈视图，使用同一详情与状态。已反馈记录仍可在全部记录中改选或取消；部分场景已反馈的记录，只要仍有可评价的未反馈场景，就可继续出现在可反馈视图。

### 5.3 列表信息层级

每行仅展示足够识别和决定是否打开的信息：

- 用户正文摘要，最多两行；材料整理可使用材料名称与用户要求，独立提案可使用变更摘要。
- 业务类型、来源名称、收到时间。
- 有有效判断时展示触发结果；场景结果可概括为“命中 2 个场景”。
- 支持反馈时展示未反馈／满意／不满意；多场景展示“已反馈 2／5”，并可标明存在不满意。
- 有候选时展示“待审核 3 条”“审核完成”等独立进度。
- 运行失败或处理中使用独立标记，不覆盖已有反馈与审核事实。

列表不展开完整反馈表单、候选属性、原始 JSON 或模型堆栈；操作集中在详情中，避免一行塞入过多按钮。

### 5.4 记录粒度与身份

- 学习任务、偏好应用请求分别作为记录；业务类型与来源 ID 共同构成稳定身份，不按标题或时间猜测关联。
- 同一用户轮次可能产生学习和场景判断两条记录。首版通过可靠轮次关联提供“相关结果”链接，不强行合并成一个共享满意度的卡片。
- 同一任务重试后可有多个运行与结果，详情明确当前结果和历史结果；反馈始终绑定具体 `result_id` 与评价单元。
- 材料整理和自然语言维护按既有任务／变更集展示；没有任务的提案按变更集或独立提案展示，保证所有待审核候选可达。
- 同一候选从多个入口访问时仅有一份审核状态，不重复进入待审核计数。
- 多轮维护必须能定位产生当前候选的输入与版本，不能将最后一句消息随意当成所有候选的来源。

记录列表是对现有业务数据的聚合视图，不要求所有业务迁入一张新的“通用任务表”。

## 6. 详情：公共结构与按需出现的操作区

### 6.1 公共区域

详情顶部显示业务类型、摘要、来源、时间以及返回／上一条／下一条。

正文优先展示：

1. 本次用户要求或材料／提案摘要。
2. 与理解当前结果直接相关的必要上下文，默认折叠。
3. 本次结果摘要。
4. 按能力出现的反馈区和审核区。
5. 次要区域：运行阶段、历史版本、技术详情、相关结果。

用户正文采用共享展示规则：剥离可确认的宿主自动附加状态块，保留用户主动引用的代码和标签；无法确认时不擅自删改。相同结果在工作台、样例和报告中使用同一正文展示投影。

展示清理不覆盖原始采集记录或冻结回测输入。输入已到期时标明“输入内容已清理”；仅在已有合法保留的样例快照可用时展示，并说明来源。列表、详情和搜索不延长临时数据保留期，也不调用模型生成摘要。

对话学习候选继续只附简短备注，不新增原始聊天证据要求；材料原本具有的来源引用继续保留，二者不强行统一。

### 6.2 对话学习详情

有有效 gate 时，明确展示：

> 本次判断：触发学习／不触发学习。你对这个判断是否满意？

按钮为“满意”“不满意”；说明这是评价是否应进入后续学习，不是评价生成内容好不好。

- 触发但没有候选：说明已完成阶段及业务原因，如去重或后续失败；不反推为不触发。
- 后续生成失败但 gate 有效：仍允许评价已完成的触发判断，并独立展示恢复入口。
- 有候选：同页展示内容审核区，允许跳过反馈直接审核。
- 从待审核视图打开时可以直接定位审核区；反馈摘要与入口仍在同一详情，不另开一页。

### 6.3 偏好场景判断详情

反馈单元是“某次输入下的某个场景”，不是整次偏好应用。

- 明确区分命中和未命中场景，两类均可查看和评价；全部不命中时仍有可用反馈界面。
- 每个场景展示当时的名称、简短触发条件、实际判断与满意度按钮。
- 命中场景优先展示，未命中场景显示数量并支持展开、搜索，避免漏触发反馈入口被埋在技术详情中。
- 场景较多时使用按需展开；不要求评价全部场景，不提供一次点击反转所有场景的整体“不满意”。
- 未评价场景没有测试标签。反馈进度的分母是本轮有效且可评价的场景数，不是当前场景目录数量。
- 使用本轮场景快照。场景后续改名、删除或条件调整，不覆盖历史判断；可链接查看当前配置，并标明版本差异。
- 空场景目录或没有有效判定时，不生成“全局不触发”反馈按钮；全局偏好不是额外的场景标签。

“提供了哪些偏好、参考示例、上下文是否送达”放在反馈之后的次要区域。明确提示：“已提供给 Agent，不代表 Agent 已遵循。”送达失败不自动变成场景不命中；有效场景判断与后续送达状态分开处理。

### 6.4 仅审核的详情

材料整理、自然语言维护和未接入反馈的 AI／MCP 候选，直接展示：

> 用户要求／材料／变更摘要 → 候选内容 → 编辑、通过、拒绝或暂缓

不显示满意度按钮、反馈空卡片、“未反馈”状态或“还差反馈才能完成”的提示。审核完成即完成本次内容处理；不要求再去测试样例页确认。

材料正文、已有来源引用、阅读覆盖范围按需查看。多轮维护提供“继续对话修改”，返回原任务；AI 重新生成仍须沿用已有版本与候选更新保护，不能覆盖已经审核的决定。

### 6.5 候选审核组件

统一使用现有字段契约和发布服务，覆盖新建、更新及其他已有提案操作：

- 显示对象类型、标题、操作、简短备注、必要的旧值与新值，以及候选依赖。
- 原始 AI 候选、人工修改后通过的内容、当前正式记录是不同版本；默认突出当前审核对象，其余可对照查看。
- AI 生成、人工编辑、后端保存使用一致的业务字段定义；只读元数据不伪装成可编辑属性。
- 保留未知于当前折叠区但有效的未编辑字段，显式清空按字段类型校验；掌握程度与兴趣等人工属性继续遵守既有权限。
- 单条“通过”只发布当前候选；编辑后用“保存并通过”，不增加必经的“确认草稿”步骤。
- 拒绝不等同不满意，暂缓不等同不触发；需要连带处理依赖时明确列出影响范围。
- 已通过候选只读，后续修改走正式记录入口。页面打开或展开候选不产生发布动作。

首版不新增“一键全部满意”“自动通过整组”等快捷方式，不绕过原有审核依赖、版本冲突与回滚规则。

## 7. 四个独立状态维度

| 维度 | 示例 | 不能推导的结论 |
| --- | --- | --- |
| 运行 | 排队、处理中、失败、完成 | 完成不等于已反馈或已审核 |
| 业务判断 | 触发／不触发；无有效判断时单独标明未完成 | 失败、无候选、未送达不等于不触发 |
| 人工反馈 | 不适用、尚不可评价、未反馈、部分已反馈、已反馈、暂不可读取 | 不适用不计入未反馈；读取失败不能当成无反馈 |
| 内容审核 | 无候选、待审核、部分审核、暂缓、审核完成 | 审核通过不等于满意；审核完成不一定有内容被保存 |

详情中的“审核完成”应能进一步看到通过、拒绝和暂缓数量；仍有暂缓候选时不能显示全部最终处理完成。反馈与运行状态不改变审核数量。

工作台不引入一个含义模糊的总状态“已处理”，以免强迫用户把可选反馈也做完。历史筛选使用“已反馈”“审核完成”等明确条件。

任务重试的当前结果不继承旧结果满意度；旧反馈和样例保留在历史结果中。后续为同一结果补充候选或同步审核答案，不属于新的触发判断，不能因此清空原反馈。

## 8. 反馈、审核与样例的行为边界

### 8.1 反馈交互

- 点击满意／不满意即保存，不再要求额外点击“加入测试样例”。
- 当前选择持续高亮，提供原位“取消反馈”；首次保存可短暂显示“撤销”提示。
- 不满意后显示选填理由；不填也完成反馈。理由保存状态与满意度保存状态分别表达。
- 理由仅作提示词改进参考，不改变标签、不进入回测输入、不参与评分或样例自动筛选。
- 改选和取消只影响对应评价单元；多场景不能误伤其他已评价场景。
- 保存或撤回不调用模型，不自动修改提示词、重试任务或回滚 Persona。

满意度与期望判断继续由服务端映射：满意保留原布尔值，不满意取反。浏览器不能提交另一份原判断；没有有效二元判断就不产生此类标签。

### 8.2 审核答案与收录

- 仅审核业务的结果不创建测试样例，不因进入统一工作台获得隐式收录资格。
- 对话学习先反馈后审核：审核成功后为对应有效样例补充答案。
- 对话学习先审核后反馈：明确反馈时，按可核验的候选版本关联已经提交的审核内容。
- 原始生成内容与审核答案分开保存；普通正式记录编辑不回写过去的答案快照。
- 部分通过只形成部分答案，不把未审核或被拒绝部分推定为完整的负向答案。
- “不应触发”标签与已通过内容可能同时存在；保留两项事实，不自动纠正用户反馈，端到端评分遵守既有规则。
- 答案关联失败提示“答案同步中／同步失败”，不回滚成功审核，不自动补写满意度。

### 8.3 取消与删除

“取消反馈”表示撤回相应标签的有效性；全部标签撤回后样例退出有效回测集合，历史与原业务记录按既有规则保留。旧冻结测试集也不能绕过撤回继续使用失效标签。

“删除样例”是评测数据管理中的单独破坏性操作，需明确确认及说明影响；不删除原业务记录、已保存 Persona，也不能声称已清除外部备份。日常取消误点不应要求用户执行删除。

## 9. 交互连续性与视觉规范

### 9.1 避免跳转和编辑丢失

- 点击记录在详情区打开，不滚动到页面最底部；选中行与列表滚动位置保持稳定。
- 反馈、审核成功后不自动跳下一条，不自动切换到测试样例详情。
- 当前筛选下刚处理的行暂时原位保留，标注“状态已更新”；用户主动更新、翻页或修改筛选后再移出。
- 新记录到达只提示“有新记录”，不挤走当前行。轮询不重排列表、不覆盖草稿、不关闭展开区。
- 上一条／下一条只在当前筛选结果内导航；浏览器前进、后退恢复记录、视图与筛选。
- 候选编辑和理由草稿保留在当前页面内存，按结果与候选版本隔离；切换后返回可恢复，不自动持久化聊天正文到浏览器长期存储。
- 页面刷新、离开及放弃草稿时提供明确提示。其他位置完成审核或更新反馈时提示冲突，不静默覆盖。

### 9.2 保存与错误反馈

- 提交期间仅禁用相关操作，显示“正在保存”；服务端成功前不显示已保存。
- 写请求使用现有幂等标识、版本与归属校验。结果不确定时先读取最新状态，不自动发起另一条写入。
- 多标签页、旧链接、迟到响应不能覆盖用户当前选择或更高版本状态。
- 失败信息靠近相关区域；统一读取失败不显示虚假的空列表、未反馈或零条待审核。
- 错误区提供用户能执行的下一步，如重试读取、查看模型设置、恢复分析；可能调用模型的动作明确标注，不自动执行。

### 9.3 响应式与可访问性

- 保留现有整体视觉语言，不引入另一套独立设计风格。主要内容优先，英文装饰标题和技术 ID 降低存在感。
- 宽屏列表与详情独立滚动。主内容区不足以容纳约 280 px 列表和 520 px 详情时切换单栏，不能按显示器大小误判嵌入面板宽度。
- 窄屏详情提供明显的“返回列表”，不横向压缩完整表单；展开复杂属性仍可正常编辑。
- 键盘可访问筛选、记录、反馈与审核；按钮使用准确标签，状态不能只靠颜色表示。
- 列表选择、返回和错误处理有清晰焦点，状态更新以温和的可访问通知呈现，不反复抢焦点。
- 原始结构化数据默认折叠；长文本换行，长输入可以展开，不让 JSON 或文件路径撑破布局。

## 10. “评测与改进”页面

### 10.1 页面分区

| 子视图 | 主要任务 | 不承担的任务 |
| --- | --- | --- |
| 测试样例 | 检查有效标签、答案、版本和测试集成员；备份与迁移 | 浏览全部未反馈业务结果 |
| 开始检查 | 选择当前检查或比较，调整候选，确认配置后运行 | 自动启用候选或修改真实 Persona |
| 历史记录 | 查看两类正确率、重复一致性和逐次结果 | 自动决定优胜方案 |

删除当前日常“最近结果”的平行反馈入口，改为“前往反馈与审核”。测试样例列表默认只展示有效样例，已撤回和不可回放样例可通过状态筛选查找。

样例详情展示：用户输入、原判断、期望判断、适用能力、审核答案及其覆盖范围、冻结版本。原输出明确标记“不是标准答案”。

需要改选或取消时，使用“修改原反馈”打开同一个工作台结果详情，并保留返回样例的位置。来源临时记录已清理而样例快照仍存在时，以快照打开只支持合法反馈操作的详情，不创建新的业务任务。

### 10.2 运行与报告

- 常规步骤为选择检查、调整候选（比较时）、确认并运行。检查内容只有对话学习触发和偏好触发。A 使用当前方案；B 从当前方案复制，可分别修改提示词、模型连接／模型和支持的思考档位。每条样例每个方案可重复 1、3、5、10 次。
- 报告分别展示不该触发、该触发的正确率及计数；无对应样例或有效判断时明确提示。失败、未判定、未运行完成分开记录，重复结果不覆盖，A/B 交替先后顺序执行。
- 开始前显示本次实际模型配置、预计调用上限和必要输入外发说明，继续保留显式确认。查看页面不启动回测。
- 测试使用冻结输入、当时场景目录和对应答案，不能暗中替换成当前 Persona 或当前场景目录。
- 报告同时展示有效评分数、未完成／失败数和覆盖情况，不能把超时当成“不触发”。
- 内容生成评测区分结构检查与语义对照；只有部分审核答案时明确标记不完整覆盖。
- 测试候选、模型裁判或 A/B 偏好不自动变成用户满意度，也不生成新的个人样例。

### 10.3 与 Prompt Workbench 的分工

评测与改进管理样例、候选检查和历史报告，在候选配置中可直接编辑并另存提示词版本。所选样例的改进理由在同一区域折叠显示，不进入运行载荷。Prompt Workbench 仍可管理、启用和回退版本，通过现有嵌入视图复用同一评测数据；页面内的保存不会自动启用。

## 11. 设置、总览与资产页面调整

### 11.1 设置

设置分为模型设置、应用接入、自动功能、数据管理几个部分：

- 应用接入保存平台、输入确认方式、接收范围和接入配置，对话学习与偏好应用共同引用。项目范围和输入确认方式直接展示，会话目录、Hook 等接入细节按需展开。
- 能力开关独立：启用来源不等于开启全部能力；开启学习不自动开启偏好应用，反之亦然。
- 后台启停、预算和超时归入相应能力的运行配置；工作台仅展示必要状态与定向入口。
- 模型设置按「账号与连接 → 默认模型 → 理解与生成 → 快速判定」排列，四项功能独立配置；已配置账号收起详情，首次使用展开。连接测试的进行中、成功和失败结果显示在按钮旁，选模变化后清除旧结果。旧阶段选择先保留并展示差异，用户保存后应用新配置；账号认证继续复用。
- 自动学习使用「关闭／仅接收／自动学习」三种运行方式，对应原有采集与分析开关；自动应用偏好独立设置。
- 各分类统一页头、宽度、表单及保存／撤销位置；页内切换保留尚未保存的编辑。
- 设置明确显示已保存、未保存和保存失败。关闭面板不意味着保存，进入页面也不意味着启用。
- 数据保留区说明临时业务正文、反馈样例、审核历史和正式 Persona 的不同归属；不以改版为由延长保留期。
- Codex 首次接入采用五步引导：接收范围、会话前文、安装接入、验证接入、启用功能；其他平台不显示新增入口。安装是用户显式操作，先展示位置和配置片段，保留其他 Hook 并备份原文件。实际验证与配置保存分开显示；验证消息不触发学习或偏好处理。Codex Hook 信任、来源信任、功能开关分别控制。

### 11.2 总览

首页优先展示未最终审核的候选、需要处理的运行异常和最近正式更新；提供可反馈判断的入口，但不以红色欠办数字要求用户逐条评价。

知识数量、掌握程度分布、材料和偏好数量保留为次级资产摘要。无异常时不占用大块诊断区域；首次使用时提供建立 Persona、添加来源等按需引导，不自动配置系统。

### 11.3 资产区与维护助手

- 知识、课程、材料、偏好的浏览编辑结构保持，不把它们压成一张通用表格。
- 偏好页“应用记录”指向工作台的偏好场景筛选；能可靠关联具体场景时保留场景过滤。
- 材料页提供“让 AI 整理”和“查看整理结果”，前者进入现有维护任务，后者定位统一详情。
- 维护助手生成候选后提示“已有 N 条待审核”，可以就地打开共享审核组件或进入统一详情，不要求再确认草稿。
- 原维护助手底部的场景试判入口移到偏好场景配置附近，并可从评测区发现。明确标记调用模型；试判结果沿用现有反馈能力，未明确反馈不收录样例。
- 场景试判默认遵守业务的完整场景目录与快照规则，不能为了只显示当前场景而静默改变判定输入。

术语统一：偏好配置中的示范内容称“参考示例”；回测数据称“测试样例”；AI 提出的未生效变更称“候选”；人确认发布的内容称“已保存内容”；用于评测的确认快照称“审核答案”。

## 12. 路由与旧入口兼容

以下为目标路由建议，实施时可在保持语义的前提下与现有路由约定对齐：

| 入口 | 目标行为 |
| --- | --- |
| `/inbox` | 统一工作台，默认待审核 |
| `/inbox?view=feedback` | 可反馈判断 |
| `/inbox?view=all&type=learning` | 对话学习记录筛选 |
| `/inbox?view=all&type=activation` | 偏好场景判断记录筛选 |
| `/learning?event=…` | 兼容定位原学习任务，不丢失历史运行入口 |
| `/preferences/applications?application=…` | 兼容定位原偏好应用记录 |
| `/review`、`/review?change_set=…`、`/review/{proposal_id}` | 进入同一审核视图，保留变更集与候选定位 |
| `/evaluations` | 评测与改进；保留现有样例／报告深链接和嵌入能力 |
| `/ai?session=…` | 保留维护对话；审核入口定位同一候选 |
| `/settings`、`/settings/models` | 设置入口与模型设置；原模型链接继续有效 |

统一详情的链接携带带业务类型的稳定记录标识；涉及反馈再携带准确结果标识，涉及审核携带候选／变更集标识。不把提示词全文、模型密钥、理由或原始聊天放进 URL。

旧 GET 入口可以重定向或使用共享页面壳；旧写接口不因改版随意改名或改语义。没有新的聚合记录时仍能打开原提案，不能让独立 MCP 候选从导航中消失。

从样例、资产、助手返回时保留安全的站内来源位置；返回地址必须校验，不能成为任意外部跳转。页面切换不产生新的任务、样例或审核动作。

## 13. 实现边界与共用组件

### 13.1 聚合读模型

新增或扩展统一列表读接口，由服务端聚合既有学习、场景结果、维护任务、提案及评测状态。建议每项提供：

- 稳定记录引用、业务类型、来源和时间。
- 共享输入摘要与输入可用状态。
- 当前运行／结果引用及历史入口。
- 业务支持的操作，以及本次结果实际可执行的操作和不可用原因。
- 有效判断数量、未反馈数量、当前反馈摘要。
- 唯一候选的审核进度、依赖与定位信息。

采用服务端筛选与稳定游标分页，默认每页 20 条；先在完整可见集合中筛选，再分页。不先取最近 100 条冒充全部结果，不让浏览器为每行依次拉取多个详情接口。

必要时增加可重建摘要索引，但原业务、提案、反馈和样例仍是各自唯一事实来源。某个来源读取失败应显示局部异常，不能默默把那部分候选算成零。

### 13.2 共享而非重写

优先复用并泛化：

- 对话学习主从工作区的选择、分页、草稿与导航保护。
- 既有满意度组件、版本校验和取消反馈接口。
- 原位候选审核、字段定义、依赖校验与发布服务。
- 评测样例、答案关联、冻结测试集与回放服务。
- 来源与模型配置服务，不创建页面专属配置副本。

“聚合页面”不应拥有绕过既有校验的万能写接口。每次操作继续验证准确的业务对象、结果、候选版本和用户权限；技术 ID 可保留在接口或折叠信息中，不要求用户理解。

## 14. 实施顺序

### 阶段一：统一日常处理入口

- 建立工作台壳、类型能力声明、聚合列表和旧深链接兼容。
- 接入两种已有反馈能力，以及所有现有来源的候选审核；确保仅审核结果从第一阶段起可见。
- 复用主从交互和统一属性组件，保持当前反馈、取消、审核保护。
- 列表与详情使用一致的用户正文展示规则。

### 阶段二：收敛评测与设置

- 评测页拆分四个子视图，移除平行日常结果列表和重复反馈表单。
- 统一修改原反馈的入口，支持只有样例快照的历史情况。
- 共用来源迁入设置，保留独立能力开关、模型配置和运行状态。
- 调整偏好应用、维护助手及场景试判的上下文入口。

### 阶段三：完成全局导航与体验验收

- 完成资产分组、首页优先级与 Prompt Workbench 入口调整。
- 验证全部旧链接、独立提案、窄屏、键盘、并发和数据保留场景。
- 更新使用说明；仅在各能力已迁移且历史入口验收通过后移除旧平行页面壳。

阶段划分只安排交付次序，不允许临时把仅审核结果标成未反馈，或通过复制数据来“暂时接入”。

## 15. 验收标准

| 场景 | 必须满足 |
| --- | --- |
| 材料整理／自然语言维护有候选 | 出现在待审核；可编辑与审核；不显示反馈或自动生成样例 |
| 独立 MCP 提案没有学习任务或评测结果 | 仍能发现、定位和完成审核，不要求补造任务 |
| 对话学习不触发且没有候选 | 可反馈，不显示审核空表单 |
| 对话学习触发但去重后无候选 | 保留真实 gate，不从候选数量推断不触发 |
| gate 完成、后续生成失败 | 既可评价有效判断，也可独立看到失败和恢复入口 |
| 场景全部不命中 | 未命中场景可发现和评价，能够收集漏触发样例 |
| 多场景只评价部分 | 仅对应场景产生标签，其他场景不被默认标记 |
| 场景目录为空或判断未完成 | 不生成全局假标签，不把运行失败记作不触发 |
| 偏好已送达或送达失败 | 与场景反馈分开，不声称最终 Agent 已遵循 |
| 先审核后反馈／先反馈后审核 | 两种顺序均正确关联版本；仅审核不建样例 |
| 只拒绝或暂缓候选 | 不写入满意度，不修改 gate，不新增测试样例 |
| 修改后通过 | 持久化内容与用户确认属性一致；原 AI 输出独立保留 |
| 取消一项／全部反馈 | 相应标签退出有效回测；不影响其他标签、提案或 Persona |
| 任务重试 | 新结果不继承旧满意度；历史结果仍可访问 |
| 同一记录从学习、资产、审核或样例入口打开 | 状态与操作一致；无重复候选、反馈或样例 |
| 在未反馈／待审核筛选中完成操作 | 不自动跳页或移走正在编辑的记录；主动刷新后更新集合 |
| 后台刷新、切换记录、多标签页并发 | 草稿和焦点稳定，冲突明确，旧响应不覆盖新状态 |
| 输入已过期、原任务已清理但样例仍在 | 明确可用范围；可核验标签与可回放资格分开，不补读宿主聊天或补造输入 |
| 样例标题包含宿主附加上下文 | 各页面一致展示用户正文；原始快照不被覆盖 |
| 修改不满意理由 | 标签、回放输入和评分不变 |
| 运行评测 | 明确使用版本与模型；不创建真实学习任务或待审核候选 |
| 大量历史记录 | 服务端筛选、分页和数量一致；不限制为最近 100 条 |
| 未反馈记录很多 | 不形成必须清空的红色待办；不诱导批量满意 |
| 窄屏／嵌入面板与键盘操作 | 无页面底部跳转、表单横向挤压或焦点丢失 |
| 设置与路由迁移 | 配置值、来源范围、模型选择、后台启停和真实用户数据不变 |

使用隔离的虚构 Persona、模拟模型和覆盖三类操作组合的测试数据验收；至少覆盖桌面、约 660 px 的嵌入面板及 375 px 窄屏。真实数据只做必要的只读核查，不为 UI 验收提交满意度、审核提案、运行真实模型或修改全局接入。

完成标准不是“页面能打开”，而是用户能从任一合理入口找到同一结果，在无需理解内部流程的情况下完成适用的操作，并准确知道哪些内容已保存、哪些判断已评价、哪些数据会参与测试。
