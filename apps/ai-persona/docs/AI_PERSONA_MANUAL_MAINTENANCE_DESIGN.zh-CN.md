## 1. 文档目的

本文档定义 AI Persona v0.2 的最小人工维护闭环。该阶段不引入 AI 自动提取或自动更新，重点是在保留现有阅读体验的前提下，使用户能够通过 UI 安全地维护知识、课程、知识关系和任务偏好。

本阶段的核心目标是：

1. 在侧边栏增加独立的课程和材料入口；
2. 保持现有阅读 UI 的整体结构和视觉样式；
3. 支持人工新建、修改和归档知识与课程；
4. 支持人工新增和移除知识节点之间的关系；
5. 支持维护 Preference Rule 和参考样本；
6. 所有正式变化继续统一经过 Proposal、校验、审核和发布；
7. 使用一小批真实个人数据验证维护体验。

## 2. 设计原则

### 2.1 保留现有阅读体验

当前 UI 作为阅读界面已经满足本阶段需要。本阶段不重新设计总览、知识列表、详情页、知识图或审核页面的整体视觉，只增加必要入口和维护动作。

### 2.2 只实现已经明确的对象

课程采用最小字段集合，不提前加入学校、时间、课程内容和证据等属性。材料只增加阅读入口，数据结构与维护方式留待后续单独讨论。

### 2.3 正式记录仍是唯一事实来源

UI 不直接修改 `persona-data/records/`。人工操作先形成 Proposal，通过确定性校验和用户确认后，才能发布为正式记录。

### 2.4 归档优先于删除

普通维护只提供归档，不提供永久删除。归档对象保留稳定 ID、历史记录和已有引用，但退出正常检索和 Agent 上下文。

### 2.5 为后续 AI 更新保留统一入口

本阶段的 Proposal 由人类操作产生。后续 AI 自动提取也必须生成相同格式的 Proposal，不另建一套写入流程。

```text
材料

```

只新增“课程”和“材料”两个入口，其他导航、布局和视觉不变。

### 4.2 页面地址

使用三个独立地址：

```text
/knowledge

```

页面底层复用现有列表、搜索、筛选和详情组件：

- `/knowledge` 只展示 `knowledge_node`；
- `/courses` 只展示 `course`；
- `/materials` 只展示 `material`。

总览继续统计三类对象。侧边栏必须根据当前地址正确显示选中状态。

## 5. 课程设计

### 5.1 课程语义

Course 表示用户接触、学习或掌握过的一门课程或系统性学习单元。`knowledge_level` 表示用户对课程整体内容的掌握程度，不表示是否结课或学习进度。

掌握程度支持 `unspecified`（未设置），新建时默认使用该值；知识点、课程和材料采用一致的程度枚举。用户可以在 UI 审核中补充程度或改回未设置，未设置状态可以直接审核发布。

本阶段不增加独立的 `learning_status`。

### 5.2 字段集合

```yaml
---
schema: ai-persona.course/v1
id: crs_...
entity_type: course
status: active
revision: 1
created_at: 2026-09-02T12:00:00Z
updated_at: 2026-09-02T12:00:00Z
title: 量子力学
aliases:
  - Advanced Quantum Mechanics
knowledge_level: familiar
interest_level: high
description: 系统介绍量子力学的基本理论与常用计算方法。
syllabus: |-
  第一章 波函数与薛定谔方程
  第二章 角动量
tags:
  - tag_physics
---
```

用户维护字段只有：

| 字段 | 含义 |
|---|---|
| `title` | 课程名称 |
| `aliases` | 课程别名或其他语言名称 |
| `knowledge_level` | 对课程整体内容的掌握程度 |
| `interest_level` | 对课程主题的兴趣程度 |
| `description` | 课程简介，可选 |
| `syllabus` | 课程大纲，可选，支持多行文本 |
| `tags` | 课程分类和检索标签 |

系统维护字段包括：

- `schema`；
- `id`；
- `entity_type`；
- `status`；
- `revision`；
- `created_at`；
- `updated_at`。

以下内容不属于 v0.2 的 Course 支持字段或 UI：

- provider、学校或平台；
- 开始时间和结束时间；
- 学习状态和学习进度；
- 课程涵盖的知识；
- 个人总结和正文备注；
- 证据引用；
- 课程材料。

未来确有需要时，再通过新的 schema 版本增加其他课程属性。

### 5.3 课程列表

课程列表沿用现有知识列表样式，展示：

- 课程名称；
- 课程简介（已填写时）；
- 掌握程度；
- 兴趣程度；
- Tag；
- 更新时间。

支持现有的搜索、掌握程度和兴趣筛选能力。

### 5.4 课程详情

课程详情沿用现有详情样式，展示：

- 名称；
- 别名；
- 课程简介；
- 课程大纲；
- 掌握程度；
- 兴趣程度；
- Tag；
- 状态；
- 版本信息。

提供：

- 编辑；
- 归档；
- 返回课程列表。

## 6. 材料设计冻结

材料在 v0.2 中只获得独立阅读入口，不重新设计。

本阶段遵守以下约束：

1. 保留现有 `Material` schema；
2. 保留已有 Demo 材料和现有生成投影；
3. 提供材料列表和详情阅读；
4. 不增加或删除字段；
5. 不提供新建、编辑或归档入口；
6. 不实现文章、PDF、Note 或其他材料导入；
7. 不实现材料与知识或课程的关系维护。

材料页面可以显示说明：

> 当前版本仅支持浏览材料，材料维护功能将在后续版本开放。

材料的用户关系、阅读状态、来源、原文保存和证据模型将在后续版本中单独讨论。

## 7. 知识维护

### 7.1 新建知识

知识页面增加“新建知识”入口。表单包含：

- 名称；
- 语义角色；
- 掌握程度；
- 兴趣程度；
- Tag；
- 别名；
- 知识说明（解释概念本身）；
- 掌握范围；
- 个人笔记。

提交后生成：

```text
operation: create
entity_type: knowledge_node
```

新知识在 Proposal 被接受前不进入正式记录、生成投影和 Agent 上下文。

### 7.2 修改知识

人工维护无需填写修改原因。所有维护表单提供折叠的“添加备注（可选）”，留空可提交；审核中的人工修改同样无需写原因。备注原样留存，系统根据原始 `patch` 与最终 `review_patch` 自动展示实际变化，例如“掌握程度：未设置 → 熟悉”。AI 提案仍须提供 `reason` 作为提议依据。

审核列表、详情、总览收件箱和处理历史应突出操作与对象类型，例如“新增知识点”“新增材料 · 论文”“修改课程”。AI / 人工来源、状态和时间作为次要信息；人工提案不展示置信度。

知识点使用“知识说明”，材料使用“内容摘要”。知识说明介绍概念是什么、解决什么问题和适用场景；个人掌握范围、掌握程度和个人笔记分别记录。继续使用现有 `summary` 存储字段，不自动重写旧记录。

继续使用现有编辑表单和 `update` Proposal 流程。发布前检查目标对象 revision 和内容 hash，防止过期 Proposal 覆盖新版本。

### 7.3 归档知识

知识详情页增加“归档”操作。归档前展示：

- 引用该知识的关系；
- 归档后不再进入正常检索；
- 历史和证据仍会保留。

确认后生成：

```text
operation: archive
```

## 8. 课程维护

### 8.1 新建课程

课程页面增加“新建课程”入口，表单只包含：

- 名称；
- 别名；
- 掌握程度；
- 兴趣程度；
- 课程简介（可选）；
- 课程大纲（可选）；
- Tag。

提交后生成：

```text
operation: create
entity_type: course
```

### 8.2 修改课程

课程编辑表单与新建表单使用相同的用户字段。提交后生成 `update` Proposal。

### 8.3 归档课程

课程详情页提供归档操作，确认后生成 `archive` Proposal。本阶段不提供永久删除。

## 9. 知识关系维护

### 9.1 支持范围

本阶段只维护 Knowledge Node 之间的关系：

| 关系 | 人类含义 |
|---|---|
| `broader_than` | 包含 |
| `requires` | 依赖 |
| `related_to` | 相关 |
| `applied_in` | 应用于 |

不提供课程或材料关系编辑。

### 9.2 添加关系

知识详情页现有关系区域增加“添加关系”。表单支持一次增加多行，每行只要求：

- 关系类型；
- 目标知识。

提交前显示自然语言预览，例如：

```text
TEBD 依赖 矩阵乘积态
```

整批内容先统一校验；任一行无效时不生成任何提案。校验通过后，每一行分别生成：

```text
operation: relate
```

### 9.3 移除关系

每条已有关系提供“移除”操作，确认后生成：

```text
operation: unrelate
```

正式 Relation 在 Proposal 发布前保持不变。

### 9.4 校验要求

- 关系不能指向自身；
- 两端知识必须存在且处于可引用状态；
- 相同关系不能重复；
- `broader_than` 不能形成有向环；
- `related_to` 的端点按统一顺序保存；
- 移除不存在的关系必须失败并提示过期。

知识图在本阶段继续作为只读视图，不支持拖拽编辑。

## 10. Preference 维护

### 10.1 设计目标

偏好区从空白数据开始，不沿用旧的 Pack、Rule 和 Example 结构。第一版完全由用户手动维护，不调用 AI 提取、改写或合并偏好。

用户面对的主对象是“偏好”，无需先创建偏好包。每条偏好都直接回答“我希望 AI 怎样做”，并通过行为类型和适用范围表达约束。

### 10.2 偏好场景 `PreferenceContext`

偏好场景用于描述一组任务，例如“写研究笔记”“做代码审查”或“准备课程复习”。场景独立保存，包含：

- 名称（人工表单必填）；
- 描述（人工表单必填）：说明场景在什么时候使用，包括适用任务和范围；
- 稳定的 `key`，供 API 和 Agent 匹配；新建时自动生成，界面不展示输入框；
- 典型请求示例（可选）：用户希望触发这个场景的请求例子，逐条添加或删除，作为语义正例；
- 可选的“不适用情况”和“产物类型”，每行一项；
- 状态与版本。

典型请求示例不要求逐字匹配，也不穷举所有可以触发的请求。现有 `activation.intents` 存储键保持兼容；界面不再称为“用户意图”。

新建和编辑共用单列表单，分为“必填项”和默认展开、可折叠的“选填项”。页面移除“激活条件”分类、“补充说明”输入框以及右侧保存流程栏；底部提供取消、保存场景和一句生效提示，编辑时保留归档或恢复入口。空白必填项在保存前提示，保存错误保留已填写内容。

已有记录中未填写的描述仍可读取、归档和恢复，人工编辑保存时需补齐。隐藏的历史 Markdown 正文与稳定场景键不因表单保存而清空；版本检查与修改历史继续沿用已有机制。

场景不是偏好规则的容器。一条偏好可以同时关联多个场景。参考样本则直接属于场景，而不是属于某条偏好；用户创建全局偏好时无需先创建场景。

### 10.3 偏好 `Preference`

偏好是一等对象，支持新建、修改、暂停、恢复和归档。字段包括：

- `behavior`：`required`、`preferred` 或 `avoid`；
- `instruction`：希望 AI 遵守的具体要求；
- `scope`：`global` 或 `contexts`；
- `context_refs`：指定场景时选择一个或多个场景；
- `condition`：可选的使用条件；
- `rationale`：可选的设置原因；
- Markdown 正文：可选的补充说明；
- `status`：`active`、`paused` 或 `archived`。

创建表单默认选择 `preferred` 和 `global`，用户只填写一条具体要求即可生成第一份待审核提案。相同适用范围内完全重复的有效偏好会被拒绝。

### 10.4 参考样本 `PreferenceExample`

参考样本是任务场景下可供参考的文件或文件夹，支持正面与反面两种类型，并可同时关联多个场景。字段包括：

- 标题；
- 正面或反面类型；
- `context_refs`：一个或多个任务场景；
- `source_ref` 与 `content_hash`：指向不可变 Source Bundle；
- 可选使用条件；
- 可选原因列表；
- `active`、`paused` 或 `archived` 状态。

创建样本时选择上传文件或一个完整文件夹。文件夹作为一条样本保存，保留文件字节和相对目录；上传前显示名称、文件数量、总大小和可展开的文件清单。标题默认采用文件夹名称，用户可修改，场景默认沿用当前场景。单次最多 500 个文件，文件总大小与打包后的大小均不超过 50 MB；空目录不上传。路径越界、重复或大小写/Unicode 等价冲突、文件与目录重名均拒绝保存，失败时清理暂存文件并保留表单文字及关联场景。

原文件以不可变 Source Bundle 保存，文件夹保留一个可下载的 ZIP 快照及可逐项打开的成员文件，样本记录正文保持为空；内容发生变化时可新建样本。主页面仅展示一张文件夹卡片及文件数，可进入目录页、打开单个文件、复制文件或整个文件夹的本地路径，并下载整个文件夹。目录页保留返回原场景的入口。此阶段只扩展人工上传与浏览，不增加 AI 按需读取目录的逻辑。样本不会被当作系统指令，也不会授予工具或权限。

### 10.5 页面与运行时行为

偏好页面以场景为主入口，在同一个页面显示该场景关联的偏好、所有任务的通用偏好，以及对应参考样本。默认显示使用中的内容；多场景共用的偏好和样本只展示一次。通用偏好单独分组，“所有任务”仅展示通用偏好，“全部偏好”则用于跨场景管理，二者含义保持独立。

桌面采用偏好与样本并列的布局，窄屏下样本收成紧凑文件列表，放在偏好上方。偏好正文和使用条件完整展示，原因与补充说明可折叠。图片样本支持小预览，其他格式提供打开文件入口；所有样本均可展开并复制实际本地路径。

页面记住当前工作区上次查看的场景；失效或已归档的场景选择会在重新打开主页时回退到可用场景。场景少时使用直接切换入口，场景较多时提供可搜索的选择器。新增偏好和样本默认关联当前场景，保存、暂停或归档后返回原场景；没有指定返回位置时，进入保存记录所属的场景。搜索、行为类型和状态筛选折叠在“筛选”中，其中状态同时影响偏好和样本，文本和行为筛选只影响偏好。归档场景仍可通过归档筛选或直接链接查看并恢复。

页面和审核界面使用用户可读名称，不要求用户直接维护内部 ID。

运行时始终加载所有 active 全局偏好，再加载命中场景的 active 偏好；paused 和 archived 内容不会进入运行时。参考样本根据命中的场景独立选择，即使该场景没有规则也可以返回样本文件引用。发布后重新生成确定性的偏好 Markdown、人格快照和 SQLite 索引。

## 11. Proposal 与审核

### 11.1 支持的操作

v0.2 支持：

```text
create
update
archive
relate
unrelate
```

暂不支持：

```text
merge
split
batch changeset
```

### 11.2 人工维护流程

```text
用户填写或修改表单
          │
          ▼
执行确定性校验
          │
          ▼
生成 Pending Proposal
          │
          ▼
用户查看变更预览
          │
    ┌─────┼─────┐
    ▼     ▼     ▼
  接受   拒绝   暂缓
    │
    ▼
写入正式记录并重新构建投影
```

### 11.3 确定性校验

本阶段不接入 AI 语义审批，先实现：

- Schema 校验；
- ID 格式与唯一性校验；
- 引用完整性校验；
- Tag 存在性校验；
- 重复名称和别名提醒；
- 知识层级环路检查；
- 重复关系检查；
- Proposal base revision 和 base hash 检查；
- 归档影响检查。

AI 审核未来可以加入同一 Proposal 流程，但不改变用户拥有最终发布权的原则。

## 12. Demo 数据与真实数据试运行

本阶段保留现有 Demo 数据，不立即重构 Demo 数据目录。

建议先补充：

- 5～10 个真实知识节点；
- 2～3 门真实课程；
- 3～5 条真实知识关系；
- 3～5 条 `note.write` Preference Rule；
- 1～2 个 Preference Example。

材料暂不录入新的真实数据。

试运行重点观察：

- 新建对象是否过于繁琐；
- 三级掌握程度是否够用；
- Tag 是否容易选择和维护；
- 关系类型是否容易理解；
- Proposal 审核步骤是否过多；
- Preference Rule 是否足够清楚；
- 归档和历史是否让用户有安全感。

待人工维护流程稳定后，再决定是否把 Demo 数据移动到 `examples/demo-persona/`。

## 14. 验收标准

v0.2 完成时必须满足：

1. 用户可以从侧边栏直接进入课程和材料；
2. 知识、课程和材料列表不会相互混淆；
3. 材料保持只读，现有数据结构没有被重新设计；
4. 用户可以通过 UI 新建知识和课程；
5. 用户可以修改和归档知识与课程；
6. 课程表单只包含本设计规定的最小字段；
7. 用户可以新增和移除知识节点之间的关系；
8. 系统能够阻止重复关系、自引用和知识层级环路；
9. 用户可以维护 `note.write` 的 Rule 和 Example；
10. 所有变化在发布前都表现为 Pending Proposal；
11. 被拒绝或暂缓的 Proposal 不影响正式人格；
12. 接受 Proposal 后增加 revision 并重新构建所有投影；
13. 归档对象不再进入正常列表、搜索和 Agent 上下文；
14. 现有阅读 UI 的整体布局和视觉没有被重新设计；
15. 自动化测试覆盖主要创建、修改、归档、关系和偏好流程。
